TL;DR

Concurrency is a decoupling strategy — it separates what gets done from when. But it's genuinely hard: correct concurrency is complex even for simple problems, and its bugs aren't repeatable. Defend yourself by keeping concurrency code separate (SRP), limiting the scope and sharing of data, and making threads independent. Know your library (java.util.concurrent) and the classic execution models. Keep synchronized sections small, treat graceful shutdown as hard, and write tests engineered to expose threading failures — never dismiss a spurious failure as a one-off.

13.1Why Concurrency?

"Objects are abstractions of processing. Threads are abstractions of schedule." — James O. Coplien

Concurrency decouples what from when. In single-threaded apps, what and when are so coupled that the whole state can be read from the stack. Decoupling them improves throughput and structure — the app becomes "many little collaborating computers" rather than one big loop (e.g. the Servlet model). Beyond structure, some systems need it for response-time and throughput constraints: a single-threaded web aggregator that exceeds 24 hours, a one-user-at-a-time service that queues, or large data sets processed in parallel.

13.2Myths and Misconceptions

Three dangerous myths

"Concurrency always improves performance" — only when there's significant wait time to share, and neither situation is trivial. "Design doesn't change" — a concurrent design can differ dramatically from single-threaded. "You don't need to understand concurrency with a container" — you'd better know what your container does and how to guard against concurrent update and deadlock.

Balanced sound bites

Concurrency incurs overhead (performance and extra code); correct concurrency is complex even for simple problems; its bugs aren't usually repeatable so they get ignored as one-offs; and it often requires a fundamental change in design strategy.

13.3Challenges

Consider this trivial class shared between two threads after lastIdUsed is set to 42:

public class X {
  private int lastIdUsed;
  public int getNextId() {
    return ++lastIdUsed;
  }
}
One line, many paths

Two threads calling getNextId() can produce 43/44, 44/43, or 43/43 — the surprising third result happens when threads step on each other. That single line of Java has 12,870 possible execution paths for two threads (and over 2.7 million if lastIdUsed is a long). Most paths are valid; the problem is that some are not.

13.4Concurrency Defense Principles

Single Responsibility Principle

Concurrency design is complex enough to be a reason to change on its own, so it deserves to be separated from the rest of the code. It has its own life cycle and its own (harder) challenges. Keep your concurrency-related code separate from other code.

Corollary: Limit the Scope of Data

Two threads modifying the same shared field can interfere. Use synchronized to protect critical sections, but restrict their number — the more places shared data is updated, the more likely you forget protection, duplicate guarding effort (DRY violation), and struggle to find failures. Take data encapsulation to heart; severely limit access to shared data.

Corollary: Use Copies of Data

Avoid sharing in the first place: copy objects as read-only, or collect results in per-thread copies and merge in one thread. If copies let you avoid synchronizing, the saved lock cost usually outweighs the creation/GC overhead.

Corollary: Threads Should Be as Independent as Possible

Write each thread to live in its own world, sharing no data — processing one request with all data from an unshared source in local variables (like an HttpServlet using only local variables). Partition data into independent subsets operated on by independent threads.

13.5Know Your Library

Use the tools Java gives you

Use the provided thread-safe collections, the executor framework for unrelated tasks, and nonblocking solutions where possible — and remember several library classes are not thread-safe. ConcurrentHashMap outperforms HashMap in nearly all situations and allows concurrent reads/writes; start there on Java 5+.

Other concurrency classes worth knowing: ReentrantLock (acquire in one method, release in another), Semaphore (a lock with a count), and CountDownLatch (waits for N events before releasing all waiting threads). Become familiar with java.util.concurrent, .atomic, and .locks.

13.6Know Your Execution Models

TermMeaning
Bound ResourcesFixed-size/number resources in a concurrent environment (DB connections, buffers).
Mutual ExclusionOnly one thread can access shared data/resource at a time.
StarvationA thread (or group) is blocked from proceeding for too long or forever.
DeadlockThreads waiting on each other; each holds a resource the other needs.
LivelockThreads in lockstep, each "in the way," making no real progress.
Three classic problems

Producer-Consumer — producers fill a bound queue and signal "not empty"; consumers drain it and signal "not full." Readers-Writers — balance throughput vs. stale data when a shared resource is mostly read, occasionally written. Dining Philosophers — threads competing for shared resources (forks) risk deadlock, livelock, and throughput degradation. Learn these algorithms and their solutions — most problems you meet are variations of them.

13.7Beware Dependencies Between Synchronized Methods

Multiple synchronized methods

Dependencies between synchronized methods cause subtle bugs. Avoid using more than one method on a shared object. When you must, make it correct with one of three locking strategies: Client-Based Locking (client locks the server across all calls), Server-Based Locking (server method locks, calls all, unlocks), or Adapted Server (an intermediary does the locking when the server can't be changed).

13.8Keep Synchronized Sections Small

As few, as small as possible

Locks are expensive (delays + overhead), so don't litter code with synchronized — but critical sections must be guarded. Naive programmers make their critical sections very large; extending synchronization beyond the minimal critical section increases contention and degrades performance. Keep synchronized sections as small as possible.

13.9Writing Correct Shut-Down Code Is Hard

Graceful shutdown deadlocks

A parent waiting for child threads can wait forever if one child deadlocks. A producer/consumer pair can hang when the producer shuts down quickly and the consumer blocks waiting for a message that never comes — preventing the parent from finishing too. Think about shut-down early and get it working early — it takes longer than you expect; review existing algorithms.

13.10Testing Threaded Code

Testing can't prove correctness but can minimize risk. Write tests with the potential to expose problems and run them frequently across different configurations and loads; if a test ever fails, track it down — never dismiss it because a later run passes. Fine-grained recommendations:

Treat spurious failures as candidate threading issues

Threaded bugs may surface once in a million runs. Assume one-offs don't exist — the longer ignored, the more code builds on a faulty approach.

Get your nonthreaded code working first

Make logic work as thread-unaware POJOs called by threads, testable outside the threaded environment. Don't chase threading and nonthreading bugs at once.

Make it pluggable & tunable

Run in many configurations (1 thread, many, real vs. test double, fast/slow). Allow thread counts to be tuned — even at runtime, even self-tuning.

Run with more threads than processors; on different platforms

More threads than cores encourages task swapping, exposing missing critical sections and deadlocks. Different OSes have different threading policies — run on all target platforms early and often.

Instrument your code to force failures

Flaws hide during normal processing. Force different orderings by inserting calls to wait(), sleep(), yield(), priority() — better that broken code fails early and often. Hand-coded instrumentation:

public synchronized String nextUrlOrNull() {
  if(hasNext()) {
    String url = urlGenerator.next();
    Thread.yield(); // inserted for testing.
    updateHasNext();
    return url;
  }
  return null;
}
Hand-coding has problems

You must manually find places, guess the right call, it slows production unnecessarily, and it's a shotgun approach. Better to automate with an AOP framework, CGLIB, or ASM — e.g. a ThreadJigglePoint.jiggle() sprinkled through the code and randomized only during testing:

public class ThreadJigglePoint {
  public static void jiggle() {
  }
}

13.11Principles & Rules

Separate Concurrency (SRP)

Keep threading code isolated from domain logic.

Limit & Avoid Shared Data

Encapsulate tightly; prefer copies and independent threads.

Know Your Library & Models

Use java.util.concurrent; learn producer-consumer, readers-writers, dining philosophers.

Small Synchronized Sections

Few and minimal; beware multi-method dependencies; plan shutdown early.

Engineer Tests to Fail

Run broadly, instrument to force orderings, never ignore a spurious failure.

13.12Common Mistakes

Threading code tangled into logic

Mixing concurrency concerns with domain code violates SRP and hides bugs.

Over-large synchronized blocks

"Lock everything" kills throughput through contention.

Dismissing one-off failures

Spurious failures are real threading defects waiting to recur.

Ignoring shutdown until late

Graceful shutdown deadlocks are common and hard — design for them early.

One-liner Takeaway

Concurrency is a powerful decoupling tool — keep it isolated, share as little as possible, and write tests built to make the rare failure happen.
