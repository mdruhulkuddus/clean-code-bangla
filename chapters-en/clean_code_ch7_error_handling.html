TL;DR

Throw exceptions instead of returning error codes so the caller's logic isn't tangled with checks. Write the try-catch-finally first to define the transaction scope. Prefer unchecked exceptions (checked ones break encapsulation and violate OCP). Give every exception enough context, and define exception classes around how they'll be caught — often by wrapping third-party APIs. Keep the happy path clean with the Special Case pattern, and never return or pass null. Robust and clean are not in conflict: treat error handling as a separate concern.

7.1Use Exceptions Rather Than Return Codes

Error codes clutter the caller, which must check immediately after each call — and it's easy to forget. Throwing an exception keeps the calling code clean and separates two tangled concerns: the algorithm and the error handling.

❌ Listing 7-1 — return codes 
public class DeviceController {
  ...
  public void sendShutDown() {
    DeviceHandle handle = getHandle(DEV1);
    // Check the state of the device
    if (handle != DeviceHandle.INVALID) {
      // Save the device status to the record field
      retrieveDeviceRecord(handle);
      // If not suspended, shut down
      if (record.getStatus() != DEVICE_SUSPENDED) {
        pauseDevice(handle);
        clearDeviceWorkQueue(handle);
        closeDevice(handle);
      } else {
        logger.log("Device suspended. Unable to shut down");
      }
    } else {
      logger.log("Invalid handle for: " + DEV1.toString());
    }
  }
  ...
}
✅ Listing 7-2 — exceptions 
public class DeviceController {
  ...
  public void sendShutDown() {
    try {
      tryToShutDown();
    } catch (DeviceShutDownError e) {
      logger.log(e);
    }
  }
  private void tryToShutDown() throws DeviceShutDownError {
    DeviceHandle handle = getHandle(DEV1);
    DeviceRecord record = retrieveDeviceRecord(handle);
    pauseDevice(handle);
    clearDeviceWorkQueue(handle);
    closeDevice(handle);
  }
  private DeviceHandle getHandle(DeviceID id) {
    ...
    throw new DeviceShutDownError("Invalid handle for: " + id.toString());
    ...
  }
  ...
}

The device-shutdown algorithm and the error handling can now be read and understood independently.

7.2Write Your Try-Catch-Finally Statement First

Exceptions define a scope: the try can abort at any point and resume at the catch. Like a transaction, the catch must leave the program in a consistent state. So start with the try-catch-finally — it defines what the caller should expect no matter what goes wrong. Drive it with TDD, starting from a test that forces the exception:

@Test(expected = StorageException.class)
public void retrieveSectionShouldThrowOnInvalidFileName() {
  sectionStore.retrieveSection("invalid - file");
}
public List<RecordedGrip> retrieveSection(String sectionName) {
  try {
    FileInputStream stream = new FileInputStream(sectionName);
    stream.close();
  } catch (FileNotFoundException e) {
    throw new StorageException("retrieval error", e);
  }
  return new ArrayList<RecordedGrip>();
}

With the transaction scope defined, you can build the rest of the logic between the open and the close, pretending nothing goes wrong.

7.3Use Unchecked Exceptions

The debate is over. … checked exceptions aren't necessary for the production of robust software.

C#, C++, Python, and Ruby write robust software without checked exceptions. The price of checked exceptions is an Open/Closed Principle violation:

The cascade of changes

Throw a checked exception three levels below its catch, and every method in between must declare it. A change at a low level forces signature changes — and rebuilds/redeploys — all the way up. Encapsulation breaks because every function in the throw's path must know about a low-level exception. Checked exceptions can help in a critical library, but for general applications the dependency cost outweighs the benefit.

7.4Provide Context with Exceptions

Informative messages

A stack trace tells you where but not what the failed operation intended. Create informative messages — mention the operation and the type of failure — and pass enough information to log the error in your catch.

7.5Define Exception Classes in Terms of a Caller's Needs

You can classify errors by source or type, but the most important concern is how they're caught. Poor classification produces duplicated catch blocks for a third-party call; wrapping the API into one common exception type fixes it:

❌ Catch every vendor exception 
ACMEPort port = new ACMEPort(12);
try {
  port.open();
} catch (DeviceResponseException e) {
  reportPortError(e);
  logger.log("Device response exception", e);
} catch (ATM1212UnlockedException e) {
  reportPortError(e);
  logger.log("Unlock exception", e);
} catch (GMXError e) {
  reportPortError(e);
  logger.log("Device response exception");
} finally {
  …
}
✅ Wrap into one exception type 
LocalPort port = new LocalPort(12);
try {
  port.open();
} catch (PortDeviceFailure e) {
  reportError(e);
  logger.log(e.getMessage(), e);
} finally {
  …
}

public class LocalPort {
  private ACMEPort innerPort;
  public LocalPort(int portNumber) {
    innerPort = new ACMEPort(portNumber);
  }
  public void open() {
    try {
      innerPort.open();
    } catch (DeviceResponseException e) {
      throw new PortDeviceFailure(e);
    } catch (ATM1212UnlockedException e) {
      throw new PortDeviceFailure(e);
    } catch (GMXError e) {
      throw new PortDeviceFailure(e);
    }
  }
  …
}
Wrapping is a best practice

Wrapping a third-party API minimizes dependence on it (you can switch libraries), makes mocking easier in tests, and frees you from a vendor's API design choices. Often a single exception class per area of code is fine; use multiple only when you must catch one and let another pass.

7.6Define the Normal Flow

Separating error handling pushes detection to the program's edges — usually great, but sometimes you don't want to abort at all. This billing code lets an exception clutter the logic:

❌ Exception as control flow 
try {
  MealExpenses expenses = expenseReportDAO.getMeals(employee.getID());
  m_total += expenses.getTotal();
} catch(MealExpensesNotFound e) {
  m_total += getMealPerDiem();
}
✅ Special Case pattern 
MealExpenses expenses = expenseReportDAO.getMeals(employee.getID());
m_total += expenses.getTotal();

public class PerDiemMealExpenses implements MealExpenses {
  public int getTotal() {
    // return the per diem default
  }
}

Special Case pattern — configure an object to handle the special case so the client never deals with exceptional behavior. ExpenseReportDAO always returns a MealExpenses object; when there are none, it returns one whose total is the per diem.

7.7Don't Return Null

Null checks invite errors

Returning null creates work for callers and foists problems on them — one missing check sends the app out of control. The real problem with null-check-laden code isn't a missing check; it's that there are too many. Throw an exception or return a Special Case object instead; wrap null-returning third-party methods.

❌ Null guard 
List<Employee> employees = getEmployees();
if (employees != null) {
  for(Employee e : employees) {
    totalPay += e.getPay();
  }
}
✅ Empty list 
List<Employee> employees = getEmployees();
for(Employee e : employees) {
  totalPay += e.getPay();
}

public List<Employee> getEmployees() {
  if( .. there are no employees .. )
    return Collections.emptyList();
}

Returning Collections.emptyList() removes the guard and minimizes NullPointerException risk.

7.8Don't Pass Null

Passing null in is worse than returning it. Neither a thrown InvalidArgumentException (you still need a handler) nor an assert (still a runtime error) truly solves it:

public double xProjection(Point p1, Point p2) {
  assert p1 != null : "p1 should not be null";
  assert p2 != null : "p2 should not be null";
  return (p2.x – p1.x) * 1.5;
}
Forbid null by default

Most languages have no good way to handle an accidentally-passed null. The rational approach is to forbid passing null, so that a null in an argument list signals a real problem — leading to far fewer careless mistakes.

7.9Principles & Rules

Exceptions, Not Codes

Throw exceptions to keep the caller's logic clean and separate from error handling.

Scope First

Write try-catch-finally first to define a transaction-like scope; drive it with TDD.

Prefer Unchecked

Checked exceptions break encapsulation and violate OCP across call levels.

Special Case Pattern

Encapsulate exceptional behavior in an object so the client sees only the normal flow.

No Nulls

Don't return or pass null; use exceptions or special-case/empty objects.

7.10Common Mistakes

Error codes as predicates

Forcing callers to check immediately, cluttering and easily forgotten.

Duplicated catch blocks

Catching every vendor exception instead of wrapping into one type.

Exceptions for normal flow

Using a catch where a Special Case object belongs.

Returning / passing null

Spreading null checks and inviting NullPointerExceptions.
