TL;DR

There's a natural tension: providers build broad interfaces, but you want a focused one. So don't pass a boundary interface (like Map) around your system — wrap it and keep it inside one class. Learn unfamiliar APIs by writing learning tests that double as a safety net against future library changes. When code you depend on doesn't exist yet, define the interface you wish you had and bridge to reality later with an Adapter. The rule: depend on what you control, not on what you don't.

8.1Using Third-Party Code

A broad interface like java.util.Map is powerful but a liability: anyone holding your Map can clear() it, and it won't constrain the types stored in it. Worse, passing Map liberally means many places to fix if its interface changes (as it did when generics arrived in Java 5).

❌ Map passed around & cast everywhere 
Map sensors = new HashMap();
...
Sensor s = (Sensor)sensors.get(sensorId);

// even with generics, Map still exposes
// more capability than we want:
Map<Sensor> sensors = new HashMap<Sensor>();
...
Sensor s = sensors.get(sensorId);
✅ Wrap the boundary 
public class Sensors {
  private Map sensors = new HashMap();
  public Sensor getById(String id) {
    return (Sensor) sensors.get(id);
  }
  //snip
}

The Map is hidden inside Sensors, free to evolve with little impact. The interface is tailored to the app's needs, easier to understand and harder to misuse — and Sensors can enforce business rules.

Don't pass boundary interfaces around

Not every Map must be wrapped — but don't pass Map (or any boundary interface) around your system. Keep it inside the class, or close family of classes, that uses it. Avoid returning it from, or accepting it into, public APIs.

8.2Exploring and Learning Boundaries

It's not our job to test third-party code, but it's in our interest to. Learning and integrating a new library at the same time is doubly hard. Instead, write learning tests: call the API the way you expect to use it, as controlled experiments that check your understanding.

Learning log4j step by step — each test reveals the next requirement (an Appender, then an output stream, then a layout) — ends in encoded knowledge:

public class LogTest {
  private Logger logger;
  @Before
  public void initialize() {
    logger = Logger.getLogger("logger");
    logger.removeAllAppenders();
    Logger.getRootLogger().removeAllAppenders();
  }
  @Test
  public void basicLogger() {
    BasicConfigurator.configure();
    logger.info("basicLogger");
  }
  @Test
  public void addAppenderWithStream() {
    logger.addAppender(new ConsoleAppender(
      new PatternLayout("%p %t %m%n"),
      ConsoleAppender.SYSTEM_OUT));
    logger.info("addAppenderWithStream");
  }
  @Test
  public void addAppenderWithoutStream() {
    logger.addAppender(new ConsoleAppender(
      new PatternLayout("%p %t %m%n")));
    logger.info("addAppenderWithoutStream");
  }
}

That knowledge can then be encapsulated in your own logger class, isolating the rest of the app from the log4j boundary.

8.3Learning Tests Are Better Than Free

Positive return on investment

You had to learn the API anyway, so the tests cost nothing — but they keep paying off. When a new version of the third-party package ships, rerun the learning tests to detect behavioral differences immediately. Without these boundary tests, you'd be tempted to stay on an old version longer than you should.

8.4Using Code That Does Not Yet Exist

Another boundary separates the known from the unknown. On a radio-communications system, the "Transmitter" subsystem had no defined interface yet. Rather than be blocked, the team defined the interface they wished they had — a Transmitter with a transmit(frequency, stream) method — and worked behind it.

The interface you wish you had

Writing the interface you want keeps it under your control and keeps client code (the CommunicationsController) readable and focused on intent. Once the real API existed, a TransmitterAdapter (the Adapter pattern) bridged the gap — a single place to change when the API evolves.

This design also creates a convenient seam for testing: a FakeTransmitter lets you test the controller, and boundary tests verify correct use once the real API arrives.

8.5Clean Boundaries

It's better to depend on something you control than on something you don't control, lest it end up controlling you.

Interesting things — especially change — happen at boundaries. Good designs accommodate change cheaply. Manage third-party boundaries by having very few places that refer to them: wrap them (as with Map) or convert with an Adapter. Either way, your code reads better, usage stays internally consistent, and there are fewer maintenance points when the third-party code changes.

8.6Principles & Rules

Hide Boundary Interfaces

Wrap broad third-party types; don't pass them through your public APIs.

Learning Tests

Explore unfamiliar APIs with tests that also guard against future version changes.

Interface You Wish You Had

Define your ideal interface for not-yet-existing code; bridge later with an Adapter.

Depend on What You Control

Concentrate boundary references in few places to limit the blast radius of change.

8.7Common Mistakes

Passing boundary types around

Sprinkling Map (and casts) throughout — many places to fix on change.

Learning & integrating at once

Debugging a new API inside production code instead of with learning tests.

Being blocked by undefined code

Waiting on an external team instead of defining the interface you wish you had.

Letting third-party details leak

Too much of your code knowing the vendor's particulars.
