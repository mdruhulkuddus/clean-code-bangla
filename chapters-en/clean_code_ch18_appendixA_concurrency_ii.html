TL;DR

Keep all thread management in one well-controlled place (a ClientScheduler), so a server's other responsibilities stay testable and threading-free. Understand the memory model: assignment to a 32-bit value is atomic but to a 64-bit (long) is not, and ++ is never atomic. Prefer server-based locking over client-based (clients forget to lock). Deadlock needs all four of mutual exclusion, lock & wait, no preemption, and circular wait — break any one to prevent it (breaking circular wait via a global resource ordering is the most common). Threading bugs may surface once in a billion runs, so instrument and Monte-Carlo test (tools like ConTest) to make them fail fast.

A.1Client/Server Example & the SRP

A naive threaded server spawns a new thread per request — it works, but it's unbounded (could exhaust the JVM under load) and, worse, the tiny process function holds four responsibilities at mixed abstraction levels: socket connection management, client processing, threading policy, and server-shutdown policy.

SRP violation in concurrent code

The server has several reasons to change. To keep concurrent systems clean, thread management should live in a few well-controlled places, and code that manages threads should do nothing else — tracking down concurrency bugs is hard enough without unwinding unrelated issues at the same time.

❌ Everything in one place 
// process() mixes connection mgmt,
// client processing, threading, and
// shutdown — and spawns unbounded threads
✅ Thread policy isolated 
public void run() {
  while (keepProcessing) {
    try {
      ClientConnection clientConnection = connectionManager.awaitClient();
      ClientRequestProcessor requestProcessor
        = new ClientRequestProcessor(clientConnection);
      clientScheduler.schedule(requestProcessor);
    } catch (Exception e) {
      e.printStackTrace();
    }
  }
  connectionManager.shutdown();
}
public interface ClientScheduler {
  void schedule(ClientRequestProcessor requestProcessor);
}

All thread concerns now funnel through clientScheduler — one place to look when there's a concurrency bug. Swapping the policy (thread-per-request → a Java 5 Executor pool) is just writing a new class and plugging it in:

public class ExecutorClientScheduler implements ClientScheduler {
  Executor executor;
  public ExecutorClientScheduler(int availableThreads) {
    executor = Executors.newFixedThreadPool(availableThreads);
  }
  public void schedule(final ClientRequestProcessor requestProcessor) {
    Runnable runnable = new Runnable() {
      public void run() {
        requestProcessor.process();
      }
    };
    executor.execute(runnable);
  }
}

A.2Atomicity & Possible Paths of Execution

An atomic operation is one that is uninterruptable. Per the Java Memory Model, assignment to a 32-bit value is atomic — but assignment to a 64-bit value (a long) requires two 32-bit assignments, so another thread can sneak in between them.

public class Example {
  int lastId;
  public void resetId() {
    value = 0;        // atomic for int, NOT for long
  }
  public int getNextId() {
    ++value;          // pre-increment is NOT atomic
  }
}
Why ++ loses an increment

In byte-code, ++value is several instructions (GETFIELD, ICONST_1, IADD, PUTFIELD) operating on the operand stack. Starting from 42: Thread 1 runs through GETFIELD (reads 42), then is interrupted. Thread 2 runs the whole method, storing 43. Thread 1 resumes with 42 still on its stack, adds one, and stores 43 again. One increment is lost. Making getNextId() synchronized fixes it.

What you actually need to know

You don't need to master byte-code — just internalize that ++ isn't atomic and the memory model has rules. Then know: where shared values exist, which code causes concurrent read/update issues, and how to guard against them.

A.3Knowing Your Library

Executor framework & Futures

If you're creating threads without a pool (or with a hand-written one), use the Java 5 Executor framework: it pools and resizes threads, recreates them if needed, and supports Futures. It works with Runnable and with Callable (a Runnable that returns a result). A Future lets you launch independent work and block only when you need the result:

Future<String> result = executorService.submit(makeExternalCall);
String partialResult = doSomeLocalProcessing();
return result.get() + partialResult;  // get() blocks until done
Nonblocking solutions & thread-safe collections

Java 5's AtomicBoolean, AtomicInteger, AtomicReference, etc. use processor-level CAS for reliable nonblocking updates — faster than synchronization and never deadlock. And the java.util.concurrent collections add safe composite operations like ConcurrentHashMap.putIfAbsent(key, value) that you can't do safely with check-then-act on a plain map.

A.4Dependencies Between Methods Can Break Concurrent Code

Even when each method is synchronized, a client that calls two of them can break:

public class IntegerIterator implements Iterator<Integer> {
  private Integer nextValue = 0;
  public synchronized boolean hasNext() {
    return nextValue < 100000;
  }
  public synchronized Integer next() {
    if (nextValue == 100000)
      throw new IteratorPastEndException();
    return nextValue++;
  }
}
The race at the last element

Thread 1 calls hasNext() → true, then is preempted. Thread 2 calls hasNext() → true, then next() (which makes hasNext() false). Thread 1 resumes, still believing hasNext() is true, calls next() — and runs off the end. It only faults on the final iteration, so it surfaces long after the system is in production. You have three options: tolerate the failure, client-based locking, or server-based locking.

A.5Client-Based vs Server-Based Locking

❌ Client-Based Locking 
IntegerIterator iterator = new IntegerIterator();
while (true) {
  int nextValue;
  synchronized (iterator) {
    if (!iterator.hasNext())
      break;
    nextValue = iterator.next();
  }
  doSometingWith(nextValue);
}
✅ Server-Based Locking 
public class IntegerIteratorServerLocked {
  private Integer nextValue = 0;
  public synchronized Integer getNextOrNull() {
    if (nextValue < 100000)
      return nextValue++;
    else
      return null;
  }
}
// client just null-checks:
while (true) {
  Integer nextValue = iterator.getNextOrNull();
  if (next == null)
    break;
  // do something with nextValue
}

Client-based locking forces every client to lock correctly (DRY violation) — and one forgotten lock causes nightmares. (Schuchert's 1971 trucker's-union war story: a single unprotected ring-buffer use locked random terminals for weeks. "Client-based locking really blows.")

Prefer server-based locking

It reduces repeated code, improves performance (swap in a non-thread-safe server for single-threaded deployment), reduces error (one forgotten lock can't happen), enforces a single policy in one place, and shrinks the scope of shared variables. If you don't own the server, wrap it with an Adapter that adds the locking, or use a thread-safe collection with an extended interface.

A.6Increasing Throughput

Reading many web pages and accumulating statistics is I/O-bound — most time is spent waiting on sockets. A shared, server-locked PageIterator hands out URLs while each thread uses its own PageReader to fetch and parse in parallel.

Where concurrency actually pays off

Single-threaded, total time ≈ the sum of all page-read times. Multithreaded, total time ≈ the longest single read plus overhead, because the waiting is shared across threads. This is exactly the situation concurrency helps — lots of wait time to overlap. (CPU-bound work with no wait sees little or no gain.)

A.7Deadlock's Four Conditions

Deadlock is the kind of bug that freezes a system every other week and takes weeks to reproduce. The good news: all four of these conditions must hold simultaneously — break any one and deadlock becomes impossible.

ConditionWhat it means
Mutual ExclusionMultiple threads need the same resources, which can't be used by more than one thread at a time and are limited in number (DB connection, write-locked file, semaphore).
Lock & WaitOnce a thread acquires a resource, it won't release it until it has acquired all the others it needs and finished its work.
No PreemptionA thread can't take a resource away from another; the holder must release it voluntarily.
Circular WaitThe "deadly embrace": T1 holds R1 and needs R2; T2 holds R2 and needs R1.

A.8Breaking Deadlock

Break Mutual Exclusion

Use resources that allow simultaneous use (e.g. AtomicInteger), increase the resource count to meet or exceed competing threads, or check that all resources are free before seizing any. Often impractical — most resources are limited and single-use.

Break Lock & Wait

Refuse to wait: check each resource before seizing it, and if any is busy, release everything and start over. Risks starvation (low CPU use) and livelock (high, useless CPU use) — but it's better than nothing and can almost always be implemented.

Break Preemption

Let a thread ask the owner to release a busy resource; if the owner is itself waiting, it releases all and starts over. Fewer start-overs than the above, but managing the requests is tricky.

Break Circular Wait — the most common fix

Impose a global ordering on resources and have all threads acquire in that order; circular wait becomes impossible. Usually just a convention all parties agree to. Caveats: acquisition order may not match use order (locks held longer than needed), and ordering may be infeasible if one resource's identity comes from operating on another. TANSTAAFL — every strategy has a cost, so isolate the thread code to tune and experiment.

A.9Testing Multithreaded Code

To prove a class like takeNextId() is broken: remember the current value, run two threads that each call it once, and assert the value rose by two — looping until it only rose by one. But running it once usually passes; the failure is rare.

Monte Carlo testing

Make tests flexible and tunable, then run them over and over on a server with randomly varied tuning values; any failure means the code is broken (log the failing conditions). Run on every target platform, repeatedly and continuously, and under varying loads close to production. Even so, the most insidious bugs occur once in a billion opportunities — the terror of complex systems.

A.10Tool Support for Testing Thread-Based Code

IBM ConTest

ConTest instruments classes to make non-thread-safe code more likely to fail. After instrumenting, the authors' failure rate jumped from roughly 1 in 10,000,000 iterations to roughly 1 in 30 — the bugs surfaced far earlier and far more reliably. Write tests that simulate multiple users under varying loads, instrument both test and production code, and run.

A.11Principles & Rules

Isolate Thread Management

One well-controlled place (a scheduler); thread code does nothing but threading (SRP).

Respect Atomicity

32-bit assignment is atomic; 64-bit and ++ are not — guard shared read/update.

Lock at the Server

Server-based locking beats client-based; Adapter a server you don't own.

Break One Deadlock Condition

Mutual exclusion, lock & wait, no preemption, or circular wait — usually order resources globally.

Instrument to Expose Bugs

Monte-Carlo across platforms/loads; use tools like ConTest to make rare failures frequent.

A.12Common Mistakes

Threading mixed with other responsibilities

A process function juggling connections, processing, threading, and shutdown.

Assuming ++ (or long assignment) is atomic

A common misconception that silently loses updates.

Client-based locking

Every client must remember to lock; one slip causes rare, brutal bugs.

"Fixing" deadlock with debug statements

The added code shifts timing so the deadlock hides — it isn't actually solved.

A.13Conclusion & Takeaway

This was a brief sojourn through a large, treacherous territory — barely the surface. The emphasis throughout was on disciplines that keep concurrent code clean: clean synchronization and locking to prevent concurrent update, threads to boost an I/O-bound system's throughput, clean strategies to prevent deadlock, and instrumentation to expose concurrent problems. For deeper study, start with Doug Lea's Concurrent Programming in Java.

One-liner Takeaway

Corral threading into one place, lock at the server, break a deadlock condition by design, and instrument your tests so the billion-to-one bug fails today instead of in production.
