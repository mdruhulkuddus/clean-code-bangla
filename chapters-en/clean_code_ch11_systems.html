TL;DR

Like a city, a system works through separation of concerns and levels of abstraction. Separate constructing the system (wiring objects in main, factories, or a Dependency Injection container) from using it. Architecture can grow incrementally — there's no getting it "right the first time," and Big Design Up Front is harmful. Keep domain logic in POJOs and weave in cross-cutting concerns (persistence, security, transactions) non-invasively with aspects. Defer decisions to the last responsible moment, use standards only when they add value, and reach for domain-specific languages to express intent. Always use the simplest thing that can possibly work.

11.1How Would You Build a City?

"Complexity kills. It sucks the life out of developers, it makes products difficult to plan, build, and test." — Ray Ozzie, CTO, Microsoft

No one person could manage all the details of a city — yet cities work, because teams own particular parts (water, power, traffic) and the city has evolved appropriate levels of abstraction and modularity. People and the components they manage work effectively without understanding the whole. Software teams are organized this way too, but their systems often lack the same separation of concerns. Clean code achieves this at low levels; this chapter aims for it at the system level.

11.2Separate Constructing a System from Using It

Construction is a very different process from use — like a hotel under construction (crane, hard hats) versus the finished, glass-walled building in operation. Software should separate the startup process (constructing objects and wiring dependencies) from the runtime logic that takes over afterward. Most applications don't: startup code is ad hoc and tangled into runtime logic.

Lazy Initialization mixed into runtime 
public Service getService() {
  if (service == null)
    service = new MyServiceImpl(...); // Good enough default for most cases?
  return service;
}

The LAZY INITIALIZATION idiom has merits (no construction cost until needed, never returns null), but it hard-codes a dependency on MyServiceImpl and its constructor's needs — you can't compile without resolving them. It complicates testing (you must inject a TEST DOUBLE), mixes two responsibilities (a small SRP break), and assumes one type is right for all contexts. One occurrence is fine; scattered across an app, the global setup strategy becomes duplicated and unmodular.

Key Insight

Don't let convenient little idioms cause modularity breakdown. Modularize the startup process separately from runtime logic, with a global, consistent strategy for resolving major dependencies.

11.3Separation of Main

Build in main, use everywhere else

Move all construction into main (or modules it calls), then design the rest of the system assuming everything is already built and wired. main builds the objects and passes them to the application. All dependency arrows point away from main — the application has no knowledge of main or the construction process; it simply expects everything to be ready.

11.4Factories

Sometimes the application must control when an object is created — e.g. an order system creating LineItem instances to add to an Order. Use the Abstract Factory pattern: give the application control of timing while keeping construction details out of it.

Direction of dependencies

Dependencies still point from main toward the application. The app is decoupled from how a LineItem is built (that lives in LineItemFactoryImplementation on the main side), yet stays in full control of when items are built and can pass app-specific constructor arguments.

11.5Dependency Injection

DI = Inversion of Control for dependencies

Dependency Injection (DI) applies Inversion of Control (IoC) to dependency management. IoC moves secondary responsibilities to objects dedicated to that purpose, supporting SRP. An object should not instantiate its own dependencies; it passes that responsibility to an authoritative mechanism — usually main or a special-purpose container.

A JNDI lookup is a partial DI — the object still actively resolves its dependency:

MyService myService = (MyService)(jndiContext.lookup("NameOfMyService"));

True DI goes further: the class is completely passive, providing setter methods or constructor arguments that the DI container uses to inject dependencies (specified in config or a construction module). The Spring Framework is the best-known Java DI container: define wiring in XML, then ask for objects by name.

Lazy init still has a place

Most DI containers won't construct an object until needed, and many provide factory/proxy mechanisms for lazy evaluation — so the virtues of lazy initialization survive (but remember it's just an optimization, possibly premature).

11.6Scaling Up

It is a myth that we can get systems "right the first time."

Cities grow from settlements; roads are narrowed then widened. We can't justify a six-lane highway through a tiny town. Likewise, implement only today's stories, then refactor and expand tomorrow — the essence of iterative, incremental agility. Unlike physical systems, software architecture can grow incrementally if we maintain proper separation of concerns.

The counterexample: EJB2 failed to separate concerns, imposing barriers to organic growth. A Bank entity bean tightly coupled business logic to the container:

❌ Listing 11-2 — EJB2 Entity Bean (excerpt) 
package com.example.banking;
import java.util.Collections;
import javax.ejb.*;
public abstract class Bank implements javax.ejb.EntityBean {
  // Business logic...
  public abstract String getStreetAddr1();
  public abstract String getCity();
  public abstract void setStreetAddr1(String street1);
  public abstract void setCity(String city);
  public abstract Collection getAccounts();
  public abstract void setAccounts(Collection accounts);
  public void addAccount(AccountDTO accountDTO) {
    InitialContext context = new InitialContext();
    AccountHomeLocal accountHome = context.lookup("AccountHomeLocal");
    AccountLocal account = accountHome.create(accountDTO);
    Collection accounts = getAccounts();
    accounts.add(account);
  }
  // EJB container logic
  public abstract void setId(Integer id);
  public abstract Integer getId();
  public Integer ejbCreate(Integer id) { ... }
  public void ejbPostCreate(Integer id) { ... }
  // The rest had to be implemented but were usually empty:
  public void setEntityContext(EntityContext ctx) {}
  public void unsetEntityContext() {}
  public void ejbActivate() {}
  public void ejbPassivate() {}
  public void ejbLoad() {}
  public void ejbStore() {}
  public void ejbRemove() {}
}
✅ Listing 11-5 — EJB3 Bank (POJO + annotations) 
package com.example.banking.model;
import javax.persistence.*;
import java.util.ArrayList;
import java.util.Collection;
@Entity
@Table(name = "BANKS")
public class Bank implements java.io.Serializable {
  @Id @GeneratedValue(strategy=GenerationType.AUTO)
  private int id;
  @Embeddable // An object "inlined" in Bank's DB row
  public class Address {
    protected String streetAddr1;
    protected String streetAddr2;
    protected String city;
    protected String state;
    protected String zipCode;
  }
  @Embedded
  private Address address;
  @OneToMany(cascade = CascadeType.ALL, fetch = FetchType.EAGER,
    mappedBy="bank")
  private Collection<Account> accounts = new ArrayList<Account>();
  public int getId() { return id; }
  public void setId(int id) { this.id = id; }
  public void addAccount(Account account) {
    account.setBank(this);
    accounts.add(account);
  }
  public Collection<Account> getAccounts() { return accounts; }
  public void setAccounts(Collection<Account> accounts) {
    this.accounts = accounts;
  }
}

EJB2 forced you to subclass container types, implement many empty lifecycle methods, write XML deployment descriptors, and use behaviorless DTOs — making isolated unit testing hard and reuse effectively impossible. EJB3 is much cleaner: a near-pure POJO where entity details live only in annotations (which can even move to XML), so it's easy to test-drive and maintain.

11.7Cross-Cutting Concerns

Concerns like persistence tend to cut across natural object boundaries — you want one consistent strategy (same DBMS, naming conventions, transactional semantics) across all objects. In principle modular, in practice the same code gets spread across many objects: a cross-cutting concern. The problem is the fine-grained intersection of two otherwise-modular domains.

Aspect-Oriented Programming (AOP)

AOP restores modularity for cross-cutting concerns. Modular constructs called aspects declaratively specify which points in the system should have their behavior modified for a particular concern. Behavior changes are applied non-invasively to the target code by the AOP framework — e.g. declare which objects/attributes to persist, then delegate to the persistence framework.

11.8Java Proxies

Java proxies suit simple cases (wrapping method calls), but JDK dynamic proxies work only with interfaces (to proxy classes you need byte-code libraries like CGLIB or Javassist). A JDK proxy for persistence on the Bank app:

// BankProxyHandler.java — InvocationHandler required by the proxy API
public class BankProxyHandler implements InvocationHandler {
  private Bank bank;
  public BankHandler(Bank bank) {
    this.bank = bank;
  }
  public Object invoke(Object proxy, Method method, Object[] args)
      throws Throwable {
    String methodName = method.getName();
    if (methodName.equals("getAccounts")) {
      bank.setAccounts(getAccountsFromDatabase());
      return bank.getAccounts();
    } else if (methodName.equals("setAccounts")) {
      bank.setAccounts((Collection<Account>) args[0]);
      setAccountsToDatabase(bank.getAccounts());
      return null;
    } else {
      ...
    }
  }
  protected Collection<Account> getAccountsFromDatabase() { ... }
  protected void setAccountsToDatabase(Collection<Account> accounts) { ... }
}
// Somewhere else...
Bank bank = (Bank) Proxy.newProxyInstance(
  Bank.class.getClassLoader(),
  new Class[] { Bank.class },
  new BankProxyHandler(new BankImpl()));
Why raw proxies hurt clean code

Even for this simple case there's a lot of complicated code. The code volume and complexity are two drawbacks of proxies — they make clean code hard. Proxies also can't specify system-wide execution "points" of interest, which a true AOP solution needs.

11.9Pure Java AOP Frameworks & EJB3

Fortunately, frameworks like Spring AOP and JBoss AOP handle most proxy boilerplate automatically. You write business logic as POJOs — focused purely on their domain, with no enterprise-framework dependencies — making them simpler to test-drive and evolve. Cross-cutting concerns are added via declarative config:

<beans>
  ...
  <bean id="appDataSource"
    class="org.apache.commons.dbcp.BasicDataSource"
    destroy-method="close"
    p:driverClassName="com.mysql.jdbc.Driver"
    p:url="jdbc:mysql://localhost:3306/mydb"
    p:username="me"/>
  <bean id="bankDataAccessObject"
    class="com.example.banking.persistence.BankDataAccessObject"
    p:dataSource-ref="appDataSource"/>
  <bean id="bank"
    class="com.example.banking.model.Bank"
    p:dataAccessObject-ref="bankDataAccessObject"/>
  ...
</beans>
XmlBeanFactory bf =
  new XmlBeanFactory(new ClassPathResource("app.xml", getClass()));
Bank bank = (Bank) bf.getBean("bank");
The "Russian doll" of decorators

Each bean is a nested doll: a Bank domain object proxied by a DAO, itself proxied by a JDBC data source. The client thinks it calls getAccounts() on a Bank, but it's talking to the outermost of a set of nested Decorator objects. So few Spring-specific lines are needed that the app is almost completely decoupled from Spring — eliminating EJB2's tight-coupling problems. This is why EJB3 was overhauled to follow Spring's declarative, annotation-driven model.

AspectJ Aspects

The most full-featured tool is the AspectJ language, an extension of Java with first-class aspect support. Pure-Java approaches (Spring/JBoss AOP) cover 80–90% of useful cases; AspectJ handles the rest but requires learning new tools and language constructs (eased by its annotation form and Spring's integration).

11.10Test-Drive the System Architecture

No Big Design Up Front

If domain logic is written as POJOs decoupled from architecture concerns, you can test-drive the architecture — evolving it from simple to sophisticated, adopting new technologies on demand. BDUF is unnecessary and even harmful: it inhibits adapting to change. Unlike building architects (who must do BDUF), software can change radically and economically when concerns are well separated.

Start with a "naively simple" but nicely decoupled architecture, ship working stories fast, then add infrastructure as you scale. A good API should largely disappear from view so the team focuses creative effort on user stories.

An optimal system architecture consists of modularized domains of concern, each implemented with Plain Old Java Objects, integrated by minimally invasive Aspects or Aspect-like tools. This architecture can be test-driven, just like the code.

11.11Optimize Decision Making

Defer to the last responsible moment

Modularity and separation of concerns enable decentralized decision making. Give responsibilities to the most qualified people — and postpone decisions until the last possible moment. That's not lazy; it lets you decide with the best possible information (customer feedback, reflection, implementation experience). A premature decision is made with suboptimal knowledge.

11.12Use Standards Wisely, When They Add Value

Standards obsession

Many teams used EJB2 simply because it was a standard, even when lighter designs would suffice — losing focus on delivering customer value. Standards help reuse, recruiting, and wiring components, but creating them can take too long, and some lose touch with adopters' real needs. Use a standard only when it adds demonstrable value.

11.13Systems Need Domain-Specific Languages

Close the communication gap

A DSL — a small scripting language or fluent API — lets code read like prose a domain expert might write, minimizing the gap between a domain concept and the code that implements it. Implementing domain logic in the expert's own language reduces the risk of mistranslation. DSLs raise the abstraction level above code idioms and design patterns, letting every level and domain be expressed as POJOs.

11.14Principles & Rules

Separate Construction from Use

Wire dependencies in main / factories / a DI container; the app just uses them.

Dependency Injection (IoC)

Objects stay passive; an authoritative container injects their dependencies (SRP).

Grow Architecture Incrementally

No BDUF — ship today's stories, refactor and expand tomorrow.

POJOs + Aspects

Keep domain logic pure; weave cross-cutting concerns non-invasively.

Defer Decisions; Use Standards/DSLs Wisely

Decide late with the best info; reach for DSLs to reveal intent.

11.15Common Mistakes

Construction tangled into runtime

Scattered lazy-init idioms with hard-coded dependencies and no global strategy.

Objects resolving their own dependencies

Breaks SRP and makes testing/wiring rigid; invert control instead.

Invasive architecture / Big Design Up Front

Container coupling (EJB2) and BDUF overwhelm domain logic and block change.

Adopting standards for their own sake

Using a heavyweight standard when a simpler design would deliver more value.
