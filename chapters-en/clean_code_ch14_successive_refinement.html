TL;DR

This chapter is a case study in successive refinement: an Args command-line parser that started clean, grew into a "festering pile" as argument types were added, and was then refactored back to clean. The lesson: to write clean code you must first write dirty code and then clean it — like rough drafts of an essay. The discipline that makes it safe is TDD + incrementalism: a suite of tests plus a long series of tiny changes, each keeping the system working. It's not enough for code to work; bad code rots and ferments, so never let the rot get started.

14.1Args: The Clean Result

Args is simple to use: construct it with the input args and a schema string, then query for values.

public static void main(String[] args) {
  try {
    Args arg = new Args("l,p#,d*", args);
    boolean logging = arg.getBoolean('l');
    int port = arg.getInt('p');
    String directory = arg.getString('d');
    executeApplication(logging, port, directory);
  } catch (ArgsException e) {
    System.out.printf("Argument error: %s\n", e.errorMessage());
  }
}

The schema "l,p#,d*" declares a boolean -l, an integer -p, and a string -d. The clean implementation parses the schema into ArgumentMarshaler objects and is trivially extensible:

public class Args {
  private Map<Character, ArgumentMarshaler> marshalers;
  private Set<Character> argsFound;
  private ListIterator<String> currentArgument;
  public Args(String schema, String[] args) throws ArgsException {
    marshalers = new HashMap<Character, ArgumentMarshaler>();
    argsFound = new HashSet<Character>();
    parseSchema(schema);
    parseArgumentStrings(Arrays.asList(args));
  }
  private void parseSchemaElement(String element) throws ArgsException {
    char elementId = element.charAt(0);
    String elementTail = element.substring(1);
    validateSchemaElementId(elementId);
    if (elementTail.length() == 0)
      marshalers.put(elementId, new BooleanArgumentMarshaler());
    else if (elementTail.equals("*"))
      marshalers.put(elementId, new StringArgumentMarshaler());
    else if (elementTail.equals("#"))
      marshalers.put(elementId, new IntegerArgumentMarshaler());
    else if (elementTail.equals("##"))
      marshalers.put(elementId, new DoubleArgumentMarshaler());
    else if (elementTail.equals("[*]"))
      marshalers.put(elementId, new StringArrayArgumentMarshaler());
    else
      throw new ArgsException(INVALID_ARGUMENT_FORMAT, elementId, elementTail);
  }
}
Easy to extend

Adding a new argument type (say, a date) requires only a new ArgumentMarshaler derivative, a new getXXX function, and a new case in parseSchemaElement — a trivial amount of effort. But Martin did not write it this way from the start.

14.2How Did I Do This?

To write clean code, you must first write dirty code and then clean it.

Programming is a craft more than a science. Just as grade-school teachers taught us to write a rough draft, then a second, then subsequent drafts, writing clean code is a matter of successive refinement. Most freshman programmers (like most grade-schoolers) believe the goal is to get the program working — then they move on, leaving it in whatever state it happened to "work." Seasoned programmers know that's professional suicide.

14.3Args: The Rough Draft

An earlier version "works" — and it's messy. As argument types were added, separate maps and scattered error state piled up:

❌ Listing 14-8 — Args.java (first draft) 
public class Args {
  private String schema;
  private String[] args;
  private boolean valid = true;
  private Set<Character> unexpectedArguments = new TreeSet<Character>();
  private Map<Character, Boolean> booleanArgs =
    new HashMap<Character, Boolean>();
  private Map<Character, String> stringArgs = new HashMap<Character, String>();
  private Map<Character, Integer> intArgs = new HashMap<Character, Integer>();
  private Set<Character> argsFound = new HashSet<Character>();
  private int currentArgument;
  private char errorArgumentId = '\0';
  private String errorParameter = "TILT";
  private ErrorCode errorCode = ErrorCode.OK;
  private enum ErrorCode {
    OK, MISSING_STRING, MISSING_INTEGER, INVALID_INTEGER, UNEXPECTED_ARGUMENT}
  public Args(String schema, String[] args) throws ParseException {
    this.schema = schema;
    this.args = args;
    valid = parse();
  }
  private boolean parse() throws ParseException {
    if (schema.length() == 0 && args.length == 0)
      return true;
    parseSchema();
    try {
      parseArguments();
    } catch (ArgsException e) {
    }
    return valid;
  }
  // ...a separate map, parse, set, and get for
  // every single argument type...
}
✅ The end state (Listing 14-2) 
public class Args {
  private Map<Character, ArgumentMarshaler> marshalers;
  private Set<Character> argsFound;
  private ListIterator<String> currentArgument;

  public Args(String schema, String[] args) throws ArgsException {
    marshalers = new HashMap<Character, ArgumentMarshaler>();
    argsFound = new HashSet<Character>();
    parseSchema(schema);
    parseArgumentStrings(Arrays.asList(args));
  }
  // One polymorphic ArgumentMarshaler hierarchy
  // replaces all the per-type maps and methods.
  // Error handling moved out to ArgsException.
}

After adding String and integer types, the mess was "starting to get out of hand" — three separate maps and three sets of parse/set/get methods, with two more types still to add.

14.4So I Stopped

Stop and refactor at the right moment

With two more types to add, Martin could see they'd make things much worse. Bulldozing forward would leave a mess too large to fix. If the structure was ever going to be maintainable, now was the time. Each argument type required new code in three places — parse the schema element, parse & convert the command-line value, and a getXXX method. "Many different types, all with similar methods — that sounds like a class to me." And so the ArgumentMarshaler concept was born.

14.5On Incrementalism

One of the best ways to ruin a program is to make massive changes to its structure in the name of improvement.

Some programs never recover from such "improvements" because it's hard to get them working the same way again. The discipline that prevents this is TDD: never make a change that breaks the system. Martin had a suite of unit tests (JUnit) and acceptance tests (FitNesse) he could run on a whim.

Many tiny changes

He made a large number of very tiny changes, each moving the structure toward ArgumentMarshaler while keeping the system working. The first change just appended a skeleton class to the end of the festering pile:

private class ArgumentMarshaler {
  private boolean booleanValue = false;
  public void setBoolean(boolean value) {
    booleanValue = value;
  }
  public boolean getBoolean() {return booleanValue;}
}
private class BooleanArgumentMarshaler extends ArgumentMarshaler {
}
private class StringArgumentMarshaler extends ArgumentMarshaler {
}
private class IntegerArgumentMarshaler extends ArgumentMarshaler {
}

Then the simplest possible modification — changing the boolean HashMap to hold an ArgumentMarshaler — broke a few statements (and a test, via a moved null check). Incrementalism demanded he get it working again quickly before any other change.

14.6Partitioning & Separation of Concerns

Good design is partitioning

The majority of the final changes were deletions — code moved out of Args into ArgsException, and each ArgumentMarshaler moved into its own file. Much of good software design is simply partitioning: creating appropriate places to put different kinds of code. Putting error-message formatting into Args violated SRP (Args should process arguments, not format messages); moving it to ArgsException is a reasonable compromise that ships convenient canned messages.

14.7Principles & Rules

Successive Refinement

Clean code is reached by drafting then refining, not by getting it perfect in one pass.

Stop Before the Mess Sets

When you sense a structure won't scale, stop adding features and refactor now.

Incrementalism via TDD

Keep the system working at all times; make many tiny, test-verified changes.

Partition for Separation of Concerns

Create the right places for different kinds of code (Args vs ArgsException vs marshalers).

14.8Common Mistakes

Stopping at "it works"

Leaving the program in whatever state it happened to work — professional suicide.

Bulldozing forward

Adding more features onto a structure you know won't scale, until the mess is too big to fix.

Massive "improvement" rewrites

Big structural changes without tests; the program may never work the same again.

Misplaced responsibilities

E.g. error-message formatting living inside the argument processor (SRP violation).

14.9Conclusion & Takeaway

It is not enough for code to work. … Nothing has a more profound and long-term degrading effect upon a development project than bad code.

Bad schedules can be redone and bad requirements redefined, but bad code rots and ferments, dragging the team down. Cleaning it later is very expensive as tangled dependencies accumulate; cleaning it now is cheap. If you made a mess this morning, it's easy to clean this afternoon — and if you made it five minutes ago, easier still.

One-liner Takeaway

Write it dirty to make it work, then refine it clean in tiny test-protected steps — and never let the rot get started.
