Chapter 02

Meaningful Names

by Tim Ottinger

Names are everywhere in software. A handful of simple, disciplined rules turns cryptic code into something that reads like plain language.

TL;DR

A good name answers why something exists, what it does, and how it's used — if it needs a comment to explain it, it has failed. Choose names that reveal intent, avoid false clues (disinformation), and make every distinction meaningful. Names should be pronounceable, searchable, and free of cryptic encodings. Classes are nouns, methods are verbs, and each concept gets exactly one word. When a name isn't meaningful on its own, give it context with a well-named class — not a clumsy prefix.

2.1Use Intention-Revealing Names

Intention-revealing name — a name that states why a variable, function, or class exists, what it does, and how it's used. Choosing good names takes time but saves far more than it costs.

If a name requires a comment, the name does not reveal its intent:

❌ Before 
int d; // elapsed time in days
✅ After 
int elapsedTimeInDays;
int daysSinceCreation;
int daysSinceModification;
int fileAgeInDays;

d evokes nothing. A good name specifies what is measured and its unit.

The same principle transforms an opaque function. What does this code do?

❌ Before 
public List<int[]> getThem() {
  List<int[]> list1 = new ArrayList<int[]>();
  for (int[] x : theList)
    if (x[0] == 4)
      list1.add(x);
  return list1;
}
✅ After 
public List<int[]> getFlaggedCells() {
  List<int[]> flaggedCells = new ArrayList<int[]>();
  for (int[] cell : gameBoard)
    if (cell[STATUS_VALUE] == FLAGGED)
      flaggedCells.add(cell);
  return flaggedCells;
}

The complexity is identical — same operators, constants, and nesting. Only the names changed (a mine-sweeper board, a status of 4 meaning "flagged"), yet the intent is now explicit. Wrapping the array in a Cell class with an isFlagged() method goes one step further and hides the magic numbers entirely.

2.2Avoid Disinformation

Disinformation — a name that leaves false clues or whose entrenched meaning differs from your intent. Avoid words with established meanings: hp, aix, and sco are poor names (they're Unix platforms). Don't call a grouping accountList unless it really is a List — prefer accountGroup, bunchOfAccounts, or just accounts.

Beware names that vary only slightly — spotting the difference between XYZControllerForEfficientHandlingOfStrings and XYZControllerForEfficientStorageOfStrings takes real effort. The worst offenders are lowercase l and uppercase O, which look like 1 and 0:

Disinformative single letters 
int a = l;
if ( O == l )
  a = O1;
else
  l = 01;

The author once suggested fixing this with a different font, passed down as oral tradition. The real fix is a simple rename.

Spelling Conveys Information

Spelling similar concepts similarly is information; inconsistent spelling is disinformation. With auto-completion, names for similar things should sort together and differ obviously.

2.3Make Meaningful Distinctions

If names must differ, they should also mean something different. Satisfying the compiler with arbitrary changes — misspellings, number series, or noise words — creates problems.

Number-series naming

❌ Before 
public static void copyChars(char a1[], char a2[]) {
  for (int i = 0; i < a1.length; i++) {
    a2[i] = a1[i];
  }
}
✅ After 
// rename a1 → source, a2 → destination
public static void copyChars(char source[], char destination[]) {
  for (int i = 0; i < source.length; i++) {
    destination[i] = source[i];
  }
}

a1, a2, …aN are noninformative — they give no clue to intent. source and destination read far better.

Noise words

Noise words like Info, Data, variable, table, Object add length without meaning. ProductInfo and ProductData differ from Product in spelling only. How would a programmer ever choose among these?

Indistinguishable names 
getActiveAccount();
getActiveAccounts();
getActiveAccountInfo();

Likewise moneyAmount vs money, customerInfo vs customer, theMessage vs message — distinguish names so the reader knows what the difference offers.

2.4Use Pronounceable Names

Programming is a social activity. If you can't pronounce a name, you can't discuss it without sounding like an idiot ("the gen-why-emm-dee-aich-emm-ess field").

❌ Before 
class DtaRcrd102 {
  private Date genymdhms;
  private Date modymdhms;
  private final String pszqint = "102";
  /* ... */
};
✅ After 
class Customer {
  private Date generationTimestamp;
  private Date modificationTimestamp;;
  private final String recordId = "102";
  /* ... */
};

Now intelligent conversation is possible: "the generation timestamp is set to tomorrow's date — how can that be?"

2.5Use Searchable Names

Searchable name — a name long and distinctive enough to grep for. Single-letter names and raw numeric constants are nearly impossible to locate: searching for the number 7 turns up file names, other constants, and unrelated expressions. The name e appears in nearly every passage of English text.

❌ Before 
for (int j=0; j<34; j++) {
  s += (t[j]*4)/5;
}
✅ After 
int realDaysPerIdealDay = 4;
const int WORK_DAYS_PER_WEEK = 5;
int sum = 0;
for (int j=0; j < NUMBER_OF_TASKS; j++) {
  int realTaskDays = taskEstimate[j] * realDaysPerIdealDay;
  int realTaskWeeks = (realdays / WORK_DAYS_PER_WEEK);
  sum += realTaskWeeks;
}

The named version is longer, but finding WORK_DAYS_PER_WEEK is trivial compared to hunting every literal 5 and filtering by intent.

Name Length ∝ Scope

The length of a name should correspond to the size of its scope. Single-letter names are acceptable only as local variables in short methods.

2.6Avoid Encodings

Encoding type or scope into a name adds a deciphering burden, forces each new hire to learn another "language," and is easy to mistype.

Hungarian Notation & Member Prefixes

Old, type-poor languages needed type encoding as a crutch. Modern languages have rich type systems and IDEs that flag type errors before compile, so Hungarian Notation is now just an impediment — it makes names harder to change and can mislead:

PhoneNumber phoneString;
// name not changed when type changed!

You also don't need m_ prefixes for members anymore:

❌ Before 
public class Part {
  private String m_dsc; // The textual description
  void setName(String name) {
    m_dsc = name;
  }
}
✅ After 
public class Part {
  String description;
  void setDescription(String description) {
    this.description = description;
  }
}

Readers quickly learn to ignore prefixes — they become unseen clutter and a marker of older code.

Interfaces & Implementations

Prefer to leave interfaces unadorned. The leading I in IShapeFactory is a distraction; users needn't know they're handed an interface. If you must encode one side, encode the implementation (ShapeFactoryImp), not the interface.

2.7Avoid Mental Mapping

Readers shouldn't have to mentally translate your names into names they already know. A loop counter may be i, j, or k (never l!) in a tiny scope, but elsewhere a single letter is just a placeholder the reader must map to a real concept.

Clarity Is King

Smart programmers sometimes show off by juggling cryptic names in their heads. The professional understands that clarity wins — they use their powers for good and write code others can understand.

2.8Class Names & Method Names

Classes = Nouns

Classes and objects take noun or noun-phrase names: Customer, WikiPage, Account, AddressParser. Avoid Manager, Processor, Data, Info. A class name should never be a verb.

Methods = Verbs

Methods take verb or verb-phrase names: postPayment, deletePage, save. Accessors, mutators, and predicates follow the JavaBean standard with get, set, and is.

String name = employee.getName();
customer.setName("mike");
if (paycheck.isPosted())...

For overloaded constructors, prefer static factory methods that describe the arguments — and consider making the constructors private to enforce their use:

❌ Before 
Complex fulcrumPoint =
  new Complex(23.0);
✅ After 
Complex fulcrumPoint =
  Complex.FromRealNumber(23.0);

2.9Don't Be Cute & Don't Pun

Cuteness over clarity

Clever names are memorable only to those who share the joke. HolyHandGrenade should be DeleteItems; don't use whack() for kill() or eatMyShorts() for abort(). Say what you mean. Mean what you say.

Punning

Don't use one word for two purposes. If many classes have an add method that combines values, don't reuse add for a method that merely puts one item into a collection — call it insert or append. Using add there is a pun.

2.10Pick One Word per Concept

Pick one word for one abstract concept and stick with it. Having fetch, retrieve, and get as equivalent methods across different classes is confusing — you end up memorizing which team wrote which library. The same applies to mixing controller, manager, and driver: what's the real difference between a DeviceManager and a ProtocolController?

Function names must stand alone

A consistent lexicon is a great boon. IDE method lists rarely show your comments, so the function names themselves must be consistent enough to pick correctly without extra exploration.

2.11Solution & Problem Domain Names

Solution Domain Names

Your readers are programmers, so use CS terms, algorithm names, pattern names, and math terms where they fit. AccountVisitor means a great deal to anyone who knows the VISITOR pattern; everyone knows what a JobQueue is.

Problem Domain Names

When there's no "programmer-ese" for something, draw the name from the problem domain so a maintainer can ask a domain expert. Separating solution-domain from problem-domain concepts is part of a good designer's job.

2.12Add Meaningful Context

Few names are meaningful by themselves. state seen alone could be anything; alongside firstName, lastName, street, city, and zipcode it's clearly part of an address. You can add prefixes (addrState), but a far better solution is a well-named Address class. Consider the unclear-context example and its refactoring:

❌ Before — Listing 2-1 
private void printGuessStatistics(char candidate, int count) {
  String number;
  String verb;
  String pluralModifier;
  if (count == 0) {
    number = "no";
    verb = "are";
    pluralModifier = "s";
  } else if (count == 1) {
    number = "1";
    verb = "is";
    pluralModifier = "";
  } else {
    number = Integer.toString(count);
    verb = "are";
    pluralModifier = "s";
  }
  String guessMessage = String.format(
    "There %s %s %s%s", verb, number, candidate, pluralModifier
  );
  print(guessMessage);
}
✅ After — Listing 2-2 
public class GuessStatisticsMessage {
  private String number;
  private String verb;
  private String pluralModifier;
  public String make(char candidate, int count) {
    createPluralDependentMessageParts(count);
    return String.format(
      "There %s %s %s%s",
      verb, number, candidate, pluralModifier );
  }
  private void createPluralDependentMessageParts(int count) {
    if (count == 0) {
      thereAreNoLetters();
    } else if (count == 1) {
      thereIsOneLetter();
    } else {
      thereAreManyLetters(count);
    }
  }
  private void thereAreManyLetters(int count) {
    number = Integer.toString(count);
    verb = "are";
    pluralModifier = "s";
  }
  private void thereIsOneLetter() {
    number = "1";
    verb = "is";
    pluralModifier = "";
  }
  private void thereAreNoLetters() {
    number = "no";
    verb = "are";
    pluralModifier = "s";
  }
}

Wrapping the three variables as fields of a GuessStatisticsMessage class gives them an unambiguous context and lets the long method break cleanly into small, well-named pieces.

Don't Add Gratuitous Context

Over-qualified names

In an app called "Gas Station Deluxe," prefixing every class with GSD defeats your IDE — type G and get a mile-long completion list. A MailingAddress named GSDAccountAddress wastes 10 of 17 characters and won't fit a customer-contact app. Shorter names are better, as long as they're clear. Add no more context than necessary.

2.13Principles & Rules

Intention-Revealing

If a name needs a comment, it doesn't reveal its intent. Rename it.

No Disinformation

Never leave false clues; spell similar things similarly, different things differently.

Meaningful Distinctions

If names differ, they must mean something different — no number series, no noise words.

Pronounceable & Searchable

You should be able to say it out loud and grep for it. Name length scales with scope.

One Word per Concept

A consistent lexicon; no puns, no cuteness.

2.14Common Mistakes

Encoding types into names

Hungarian notation and m_ prefixes are noise the IDE already handles.

Naming just to please the compiler

Misspelling or appending digits to dodge a name clash produces meaningless distinctions.

Single letters outside tiny scopes

Forces the reader into mental mapping; reserve i/j/k for short loops only.

Fearing renames

Refusing to rename for fear of upsetting others — modern tools make renaming cheap, and clarity pays off long-term.
