TL;DR

Martin reviews and refactors SerialDate — genuinely good code from a competent author — to show that critique is a normal, welcome part of the craft (doctors, pilots, and lawyers do it too). The discipline is "first make it work, then make it right." First he raises test coverage from ~50% to 92% (fixing real bugs along the way), then walks the class top-to-bottom: delete the change-history comment, shorten imports, rename SerialDate → DayDate (a name at the right level of abstraction), turn constant classes into enums, move behavior to where it belongs, collapse duplication, extract a DateUtil, and kill magic numbers. The result is smaller, clearer, and better-tested — the Boy Scout Rule in action.

16.2First, Make It Work

The existing tests pass but don't test everything — a "Find Usages" search shows monthCodeToQuarter is never used [F4], and a Clover coverage run reveals only 91 of 185 statements (~50%) are executed [T2]. To understand and refactor the class, Martin writes his own independent suite, raising coverage to 92% — with some tests deliberately left commented out to express behavior the class should have.

16.3Then, Make It Right

Walking from top to bottom — running all of JCommon's tests after every change — the early fixes:

Top-of-file smells

The change-history comment is a 1960s leftover that source control handles now — delete it [C1]. The import list can be shortened with java.text.* and java.util.* [J1]. The Javadoc mixes four languages (Java, English, Javadoc, HTML) which is hard to keep straight [G1].

Rename SerialDate → DayDate

"Serial" leaks the implementation (a serial number = days since 1899-12-30). The term isn't descriptive [N1], and worse, since the class is abstract, the name implies an implementation it shouldn't — the wrong level of abstraction [N2]. Date and Day are taken, so DayDate is the chosen compromise.

16.4Constants Become Enums

Why does DayDate inherit from MonthConstants? Inheriting from a constants class is an old trick to avoid writing MonthConstants.January — but it's a bad idea [J2]. It should be an enum:

public abstract class DayDate implements Comparable, Serializable {
  public static enum Month {
    JANUARY(1), FEBRUARY(2), MARCH(3), APRIL(4),
    MAY(5), JUNE(6), JULY(7), AUGUST(8),
    SEPTEMBER(9), OCTOBER(10), NOVEMBER(11), DECEMBER(12);
    Month(int index) {
      this.index = index;
    }
    public static Month make(int monthIndex) {
      for (Month m : Month.values()) {
        if (m.index == monthIndex)
          return m;
      }
      throw new IllegalArgumentException("Invalid month index " + monthIndex);
    }
    public final int index;
  }
Enums kill error-checking code

The conversion took about an hour, but now any function that took an int month takes a Month enumerator — so the isValidMonthCode method and all the month-code error checking (like in monthCodeToQuarter) can be deleted entirely [G5]. Three other constant groups become enums the same way.

16.5Moving Behavior Where It Belongs

The weekday parsing and stringifying don't belong in DayDate — they're really about a Day. So they move into the Day enum (as parse and toString), which then moves into its own file since Day doesn't depend on DayDate [G13]:

public enum Day {
  MONDAY(Calendar.MONDAY), TUESDAY(Calendar.TUESDAY),
  WEDNESDAY(Calendar.WEDNESDAY), THURSDAY(Calendar.THURSDAY),
  FRIDAY(Calendar.FRIDAY), SATURDAY(Calendar.SATURDAY),
  SUNDAY(Calendar.SUNDAY);
  public final int index;
  private static DateFormatSymbols dateSymbols = new DateFormatSymbols();
  Day(int day) {
    index = day;
  }
  public static Day make(int index) throws IllegalArgumentException {
    for (Day d : Day.values())
      if (d.index == index)
        return d;
    throw new IllegalArgumentException(
      String.format("Illegal day index: %d.", index));
  }
  public static Day parse(String s) throws IllegalArgumentException {
    String[] shortWeekdayNames = dateSymbols.getShortWeekdays();
    String[] weekDayNames = dateSymbols.getWeekdays();
    s = s.trim();
    for (Day day : Day.values()) {
      if (s.equalsIgnoreCase(shortWeekdayNames[day.index]) ||
          s.equalsIgnoreCase(weekDayNames[day.index])) {
        return day;
      }
    }
    throw new IllegalArgumentException(
      String.format("%s is not a valid weekday string", s));
  }
  public String toString() {
    return dateSymbols.getWeekdays()[index];
  }
}

Two getMonths functions (one only ever called by the other) collapse into a single, vastly simpler method that's also renamed to be self-descriptive [G9][G12][F4][N1].

16.6The Final Pass

One more pass over the whole class to see how it flows:

The cleanup checklist

Shorten and update the stale opening comment [C2]; move remaining enums into their own files [G12]; extract the static variable and three static methods into a new DateUtil class [G6]; move abstract methods to the top where they belong [G24]; rename Month.make → Month.fromInt (and add a toInt() accessor, making index private) [N1]; eliminate duplication in plusYears/plusMonths by extracting correctLastDayOfMonth [G5]; and replace the magic number 1 with Month.JANUARY.toInt() or Day.SUNDAY.toInt() [G25].

A surprising coverage number

Coverage dropped to 84.9% — not because less is tested, but because the class shrank so much that the few trivial uncovered lines now carry more weight (45 of 53 statements covered). Smaller code, higher per-line significance.

16.7Principles & Rules

Code Review Is Professional

Critiquing and being critiqued is how craftspeople learn — welcome it.

First Work, Then Right

Get full test coverage and a passing system before you refactor for cleanliness.

Tests Enable Fearless Change

Run the whole suite after every tiny change so refactoring can't break behavior.

Names at the Right Abstraction

Don't leak implementation in names (SerialDate → DayDate).

Prefer Enums; Move Behavior Home

Replace constant classes with enums; put methods on the class whose data they use.

16.8Common Mistakes (and the heuristics they hit)

Change-history comments [C1]

Hand-maintained logs that source control already provides.

Inheriting from a constants class [J2]

An old trick to dodge qualification — use an enum instead.

Implementation-revealing names [N2]

"Serial" exposed how an abstract class was built.

Magic numbers & duplication [G25][G5]

Bare 1s and repeated logic in plusYears/plusMonths.

16.9Conclusion & Takeaway

Once again the Boy Scout Rule is satisfied: the code was checked in a bit cleaner than it was checked out. It took a little time, but it was worth it — coverage increased, bugs were fixed, and the code was clarified and shrunk. The next person will find it easier to deal with — and will probably clean it up a bit more still.

One-liner Takeaway

Make it work with solid tests first, then make it right top-to-bottom — and leave even good code a little cleaner than you found it.
