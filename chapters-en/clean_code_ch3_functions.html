TL;DR

Functions should be small — rarely 20 lines, ideally two to four — and they should do one thing at a single level of abstraction, so the code reads like a top-down narrative (the Stepdown Rule). Use long, descriptive names; keep arguments to a minimum (zero is best, three is suspect); avoid flag arguments and output arguments; have no side effects; separate commands from queries; prefer exceptions to error codes; and ruthlessly eliminate duplication. You won't write them this way the first time — you refactor your way there with tests passing.

3.1Small!

Martin opens with a long, multi-level FitNesse function (Listing 3-1) that almost nobody can understand in three minutes — nested ifs controlled by flags, arcane strings, and mixed abstraction levels. The First Rule of Functions

Functions should be small. The second rule is that they should be smaller than that. Functions should hardly ever be 20 lines long — Kent Beck's Sparkle program had functions of two, three, or four lines, each transparently obvious, each leading to the next.

Blocks and Indenting

The body of an if, else, or while should be one line long — probably a function call. This keeps the enclosing function small and adds documentary value through the called function's name. Functions shouldn't hold nested structures, so the indent level should not exceed one or two.

3.2Do One Thing

FUNCTIONS SHOULD DO ONE THING. THEY SHOULD DO IT WELL. THEY SHOULD DO IT ONLY.

The trouble is defining "one thing." Listing 3-3 arguably does three: decide if it's a test page, include setups/teardowns, render HTML. But those steps are all one level of abstraction below the function's name. Described as a "TO paragraph":

TO RenderPageWithSetupsAndTeardowns, we check to see whether the page is a test page and if so, we include the setups and teardowns. In either case we render the page in HTML.
The Extraction Test

A function does one thing if you cannot extract another function from it with a name that isn't merely a restatement of its implementation. Functions that do one thing cannot be reasonably divided into sections (declarations, inits, etc.).

3.3One Level of Abstraction per Function

To ensure a function does one thing, all its statements must sit at the same level of abstraction. Listing 3-1 mixed high-level (getHtml()), mid-level (PathParser.render(pagePath)), and low-level (.append("\n")) — confusing the reader about what's essential vs. detail. Like broken windows, once details intrude they accrete.

The Stepdown Rule

Code should read like a top-down narrative: every function is followed by those at the next level down, so you descend one abstraction at a time. Read it as a set of "TO paragraphs":

To include the setups and teardowns, we include setups, then the test page content, then the teardowns.
To include the setups, we include the suite setup if this is a suite, then the regular setup.
To include the suite setup, we search the parent hierarchy for the "SuiteSetUp" page…

3.4Switch Statements

A switch inherently does N things and is hard to keep small or single-purpose. The fix isn't to ban it but to bury it once in a low-level factory, hidden behind polymorphism.

Listing 3-4 — Payroll.java (the problem)

public Money calculatePay(Employee e)
throws InvalidEmployeeType {
  switch (e.type) {
    case COMMISSIONED:
      return calculateCommissionedPay(e);
    case HOURLY:
      return calculateHourlyPay(e);
    case SALARIED:
      return calculateSalariedPay(e);
    default:
      throw new InvalidEmployeeType(e.type);
  }
}
Four problems with this switch

It's large and grows with each new type; it does more than one thing; it violates SRP (more than one reason to change); it violates OCP (must change when types are added); and worst, the same structure repeats in isPayday(e, date), deliverPay(e, pay), and countless others.

Listing 3-5 — Employee and Factory (the fix)

public abstract class Employee {
  public abstract boolean isPayday();
  public abstract Money calculatePay();
  public abstract void deliverPay(Money pay);
}
-----------------
public interface EmployeeFactory {
  public Employee makeEmployee(EmployeeRecord r) throws InvalidEmployeeType;
}
-----------------
public class EmployeeFactoryImpl implements EmployeeFactory {
  public Employee makeEmployee(EmployeeRecord r) throws InvalidEmployeeType {
    switch (r.type) {
      case COMMISSIONED:
        return new CommissionedEmployee(r) ;
      case HOURLY:
        return new HourlyEmployee(r);
      case SALARIED:
        return new SalariedEmploye(r);
      default:
        throw new InvalidEmployeeType(r.type);
    }
  }
}
Switch Rule

A switch is tolerable if it appears only once, is used to create polymorphic objects, and is hidden behind an inheritance relationship so the rest of the system can't see it.

3.5Use Descriptive Names

Renaming testableHtml to SetupTeardownIncluder.render — and the private methods to things like isTestPage and includeSetupAndTeardownPages — makes the code self-explanatory. The smaller and more focused a function, the easier it is to name well.

Don't fear long names

A long descriptive name beats a short enigmatic one, and beats a long descriptive comment. Try several names and read the code with each; hunting for a good name often leads to a favorable restructuring. Be consistent: includeSetupPages, includeSuiteSetupPage, includeSetupPage — the shared phrasing lets the sequence tell a story.

3.6Function Arguments

The ideal argument count, in order: zero (niladic) > one (monadic) > two (dyadic) > three (triadic, avoid) > more (polyadic, needs special justification — don't). Arguments take conceptual power, and they're hard to test — every combination multiplies the test cases.

FormArgsVerdict
Niladic0Best — trivial to understand and test
Monadic1Next best (question, transform, or event)
Dyadic2Harder; OK when args are naturally ordered components
Triadic3Significantly harder; think very carefully
Polyadic4+Needs special justification — then don't

Common Monadic Forms

Two natural reasons for one argument: asking a question — boolean fileExists("MyFile") — or transforming the argument and returning it — InputStream fileOpen("MyFile"). A less common form is an event, like void passwordAttemptFailedNtimes(int attempts), which alters system state; use it with care and make its event nature obvious.

If a function transforms its input, the transformation should appear in the return value, not an output argument — StringBuffer transform(StringBuffer in) is better than void transform(StringBuffer out).

Dyads & Triads

writeField(name) reads more easily than writeField(outputStream, name). Dyads are appropriate when the two arguments are ordered components of a single value — new Point(0, 0) is fine because Cartesian points naturally take two. But even assertEquals(expected, actual) trips people up because the order is just a convention. Triads multiply the ordering/pausing/ignoring problems: assertEquals(message, expected, actual) invites mistaking the message for the expected.

3.7Flag Arguments

Flag arguments are ugly

Passing a boolean into a function loudly proclaims it does more than one thing — one thing if true, another if false. render(true) is confusing; the function should have been split into renderForSuite() and renderForSingleTest().

3.8Argument Objects & Argument Lists

When a function seems to need more than two or three arguments, some likely belong wrapped in their own class:

❌ Before 
Circle makeCircle(double x, double y, double radius);
✅ After 
Circle makeCircle(Point center, double radius);

When variables travel together (like x and y), they're usually part of a concept that deserves its own name.

Argument lists. Variable args treated identically are equivalent to a single List argument — so String.format(String format, Object... args) is really dyadic. Variadic functions can be monads, dyads, or triads, but no more:

void monad(Integer... args);
void dyad(String name, Integer... args);
void triad(String name, int count, Integer... args);

Verbs and keywords. A monad should form a verb/noun pair — writeField(name). The keyword form encodes argument names into the function name to fix ordering confusion: assertExpectedEqualsActual(expected, actual).

3.9Have No Side Effects

Side effects are lies. Your function promises to do one thing, but it also does other hidden things.

Can you spot the side effect below?

Listing 3-6 — UserValidator.java

public class UserValidator {
  private Cryptographer cryptographer;
  public boolean checkPassword(String userName, String password) {
    User user = UserGateway.findByName(userName);
    if (user != User.NULL) {
      String codedPhrase = user.getPhraseEncodedByPassword();
      String phrase = cryptographer.decrypt(codedPhrase, password);
      if ("Valid Password".equals(phrase)) {
        Session.initialize();
        return true;
      }
    }
    return false;
  }
}
The hidden side effect

Session.initialize() — nothing in the name checkPassword implies it wipes session state. This creates a temporal coupling: the function can only be called when it's safe to initialize the session. If you must have such coupling, name it for it (checkPasswordAndInitializeSession) — though that violates "do one thing."

Output Arguments

Arguments are naturally read as inputs. appendFooter(s) forces a double-take — does it append s as a footer, or append a footer to s? Prefer making it a method on the owning object: report.appendFooter(). In general, if a function must change state, it should change the state of its own object.

3.10Command Query Separation

A function should either do something or answer something — not both. Consider:

public boolean set(String attribute, String value);

This sets a value and returns success, producing ambiguous reads like:

❌ Before 
if (set("username", "unclebob"))...
✅ After 
if (attributeExists("username")) {
  setAttribute("username", "unclebob");
  ...
}

Is the if asking whether the attribute was set, or commanding it to be set? Separating the command from the query removes the ambiguity entirely.

3.11Prefer Exceptions to Returning Error Codes

Returning error codes is a subtle violation of command/query separation — it tempts you to use commands as if predicates and forces the caller to handle errors immediately, producing deep nesting:

❌ Before — error codes 
if (deletePage(page) == E_OK) {
  if (registry.deleteReference(page.name) == E_OK) {
    if (configKeys.deleteKey(page.name.makeKey()) == E_OK){
      logger.log("page deleted");
    } else {
      logger.log("configKey not deleted");
    }
  } else {
    logger.log("deleteReference from registry failed");
  }
} else {
  logger.log("delete failed");
  return E_ERROR;
}
✅ After — exceptions 
try {
  deletePage(page);
  registry.deleteReference(page.name);
  configKeys.deleteKey(page.name.makeKey());
}
catch (Exception e) {
  logger.log(e.getMessage());
}

Extract Try/Catch Blocks & Error Handling Is One Thing

Try/catch blocks confuse structure by mixing error processing with normal processing, so extract their bodies into their own functions:

public void delete(Page page) {
  try {
    deletePageAndAllReferences(page);
  }
  catch (Exception e) {
    logError(e);
  }
}
private void deletePageAndAllReferences(Page page) throws Exception {
  deletePage(page);
  registry.deleteReference(page.name);
  configKeys.deleteKey(page.name.makeKey());
}
private void logError(Exception e) {
  logger.log(e.getMessage());
}
Error Handling Is One Thing

A function that handles errors should do nothing else. If try exists in a function, it should be the very first word, and there should be nothing after the catch/finally blocks.

The Error enum dependency magnet

An Error enum of codes is a dependency magnet — every change forces recompiling and redeploying its many users, so programmers reuse old codes rather than add new ones. With exceptions, new error types are simply derivatives that add no recompilation pressure.

3.12Don't Repeat Yourself (DRY)

Listing 3-1 repeated the same include algorithm four times (SetUp, SuiteSetUp, TearDown, SuiteTearDown), bloating the code and creating a four-fold modification and error risk. Extracting an include method removed it.

Duplication may be the root of all evil

So much of software innovation — database normal forms, OO base classes, structured/aspect/component-oriented programming — exists to control or eliminate duplication. Since the invention of the subroutine, the field has been one long attempt to remove it.

3.13Structured Programming

Dijkstra's rule is one entry, one exit: a single return, no break/continue in loops, and never goto. But these rules give significant benefit only in large functions. When functions are small, an occasional multiple return, break, or continue does no harm and can be more expressive. goto only makes sense in large functions, so avoid it.

3.14How Do You Write Functions Like This?

It's a process, not a first draft

Writing code is like writing prose: you get a clumsy first draft down, then refine it. Martin's functions come out long, deeply nested, with arbitrary names and duplication — but covered by unit tests. Then he massages and refines: splitting functions, renaming, eliminating duplication, even breaking out whole classes, all while keeping the tests passing. Nobody writes them clean from the start.

Master programmers think of systems as stories to be told rather than programs to be written. Functions are the verbs of that language, and classes are the nouns.

The payoff is the fully refactored SetupTeardownIncluder (Listing 3-7), where each function introduces the next and stays at a consistent level of abstraction — every method just two to four lines.

3.15Principles & Rules

Small & Do One Thing

Tiny functions, one responsibility, indent depth of one or two.

One Level of Abstraction (Stepdown Rule)

All statements at the same level; code reads top-down as "TO paragraphs."

Fewest Arguments

0 > 1 > 2 > 3. No flag arguments, no output arguments.

No Side Effects

Do exactly what the name says; avoid hidden temporal couplings.

Command Query Separation

Do something or answer something — never both.

Exceptions over Error Codes

Separate happy-path from error handling; error handling is one thing.

DRY

Duplication is the root of much evil — remove it relentlessly.

3.16Common Mistakes

Mixing abstraction levels

High-level calls beside low-level .append("\n") blurs essential vs. detail.

Repeated switch statements

The same type-switch reappears across many functions — bury it once behind polymorphism.

Boolean & output arguments

Flags signal "more than one thing"; output args force a double-take.

Hidden side effects

A "check" that also initializes state lies to its caller and couples timing.

Error codes as predicates

Leads to deep nesting and a dependency-magnet error enum.
