TL;DR

Classes should be small — measured by responsibilities, not lines. The Single Responsibility Principle says a class should have one, and only one, reason to change; if you can't name it concisely or describe it in ~25 words without "and/or," it does too much. Prefer many small, cohesive classes over a few "God classes." Organize for change so new features arrive by extension, not modification (OCP), and depend on abstractions, not concrete details (DIP) so your code is testable and isolated from change.

10.1Class Organization

Following Java convention, a class begins with its variables: public static constants first, then private static variables, then private instance variables. There's seldom a good reason for a public variable. Public functions follow the variables, with the private utilities a public function calls placed right after it — honoring the stepdown rule so the class reads like a newspaper article.

10.2Encapsulation

Tests rule — but privacy first

Keep variables and utilities private, but don't be fanatic. If a test in the same package needs access, loosening to protected or package scope is acceptable — but only as a last resort, after first looking for a way to keep things private.

10.3Classes Should Be Small!

The first rule of classes is that they should be small; the second is that they should be smaller than that. With functions we counted lines; with classes we count responsibilities. A SuperDashboard exposing ~70 public methods is a "God class":

Listing 10-1 — Too Many Responsibilities (excerpt) 
public class SuperDashboard extends JFrame implements MetaDataUser
  public String getCustomizerLanguagePath()
  public void setSystemConfigPath(String systemConfigPath)
  public String getSystemConfigDocument()
  public boolean getGuruState()
  public void showObject(MetaObject object)
  public Component getLastFocusedComponent()
  public void setLastFocused(Component lastFocused)
  public LanguageManager getLanguageManager()
  public Project getProject()
  public int getMajorVersionNumber()
  public int getMinorVersionNumber()
  public int getBuildNumber()
  // ... about 70 public methods in all ...
}

But even a five-method version is too big if it has too many responsibilities:

public class SuperDashboard extends JFrame implements MetaDataUser
  public Component getLastFocusedComponent()
  public void setLastFocused(Component lastFocused)
  public int getMajorVersionNumber()
  public int getMinorVersionNumber()
  public int getBuildNumber()
}
Naming & the 25-word test

A class name should describe its responsibilities — if you can't derive a concise name, it's too large. Weasel words like Processor, Manager, or Super hint at aggregated responsibilities. You should be able to describe the class in about 25 words without using "if," "and," "or," or "but." The first "and" in "tracks the last focused component and the version numbers" reveals two responsibilities.

10.4The Single Responsibility Principle

SRP

A class or module should have one, and only one, reason to change. The "small" SuperDashboard has two: it tracks version info (changes on each ship) and manages Swing components (changes with GUI code). Extract the version methods into their own reusable class:

public class Version {
  public int getMajorVersionNumber()
  public int getMinorVersionNumber()
  public int getBuildNumber()
}
Why SRP is abused

Getting code to work and making it clean are different activities. Most of us stop once it works and move on, never breaking the overstuffed class into single-responsibility units. Others fear that many small classes make the big picture harder to see — but a system of many small classes has no more moving parts than one of few large classes.

Do you want your tools organized into toolboxes with many small, well-labeled drawers? Or a few drawers that you just toss everything into?

10.5Cohesion

Classes should have few instance variables, and each method should manipulate one or more of them. The more variables a method uses, the more cohesive it is to its class; a class where every variable is used by every method is maximally cohesive. Aim for high cohesion — methods and variables that hang together as a logical whole.

public class Stack {
  private int topOfStack = 0;
  List<Integer> elements = new LinkedList<Integer>();
  public int size() {
    return topOfStack;
  }
  public void push(int element) {
    topOfStack++;
    elements.add(element);
  }
  public int pop() throws PoppedWhenEmpty {
    if (topOfStack == 0)
      throw new PoppedWhenEmpty();
    int element = elements.get(--topOfStack);
    elements.remove(topOfStack);
    return element;
  }
}

This Stack is very cohesive — only size() fails to use both variables.

10.6Maintaining Cohesion → Many Small Classes

When cohesion drops, split

Keeping functions small and argument lists short can push shared state into instance variables used by only a subset of methods. That falling cohesion is a signal: those few functions and variables are a class trying to get out. When classes lose cohesion, split them.

Knuth's PrintPrimes as one monolithic function vs. its refactoring into three single-responsibility classes:

❌ Listing 10-5 — PrintPrimes.java (monolith) 
package literatePrimes;
public class PrintPrimes {
  public static void main(String[] args) {
    final int M = 1000;
    final int RR = 50;
    final int CC = 4;
    final int WW = 10;
    final int ORDMAX = 30;
    int P[] = new int[M + 1];
    int PAGENUMBER;
    int PAGEOFFSET;
    int ROWOFFSET;
    int C;
    int J;
    int K;
    boolean JPRIME;
    int ORD;
    int SQUARE;
    int N;
    int MULT[] = new int[ORDMAX + 1];
    J = 1;
    K = 1;
    P[1] = 2;
    ORD = 2;
    SQUARE = 9;
    while (K < M) {
      do {
        J = J + 2;
        if (J == SQUARE) {
          ORD = ORD + 1;
          SQUARE = P[ORD] * P[ORD];
          MULT[ORD - 1] = J;
        }
        N = 2;
        JPRIME = true;
        while (N < ORD && JPRIME) {
          while (MULT[N] < J)
            MULT[N] = MULT[N] + P[N] + P[N];
          if (MULT[N] == J)
            JPRIME = false;
          N = N + 1;
        }
      } while (!JPRIME);
      K = K + 1;
      P[K] = J;
    }
    {
      PAGENUMBER = 1;
      PAGEOFFSET = 1;
      while (PAGEOFFSET <= M) {
        System.out.println("The First " + M +
          " Prime Numbers --- Page " + PAGENUMBER);
        System.out.println("");
        for (ROWOFFSET = PAGEOFFSET; ROWOFFSET < PAGEOFFSET + RR; ROWOFFSET++){
          for (C = 0; C < CC;C++)
            if (ROWOFFSET + C * RR <= M)
              System.out.format("%10d", P[ROWOFFSET + C * RR]);
          System.out.println("");
        }
        System.out.println("\f");
        PAGENUMBER = PAGENUMBER + 1;
        PAGEOFFSET = PAGEOFFSET + RR * CC;
      }
    }
  }
}

The refactor is longer (descriptive names, declarations as commentary, whitespace) but splits into three responsibilities: PrimePrinter (execution), RowColumnPagePrinter (formatting), PrimeGenerator (algorithm). This was not a rewrite — the same algorithm was transformed by many tiny changes, each verified by a test suite.

10.7Organizing for Change (OCP)

Change is continual, and every change risks breaking the system. A Sql class that must be "opened" to add an update statement risks breaking its other code. Refactoring each statement type into its own Sql subclass fixes this:

❌ Listing 10-9 — opened for change 
public class Sql {
  public Sql(String table, Column[] columns)
  public String create()
  public String insert(Object[] fields)
  public String selectAll()
  public String findByKey(String keyColumn, String keyValue)
  public String select(Column column, String pattern)
  public String select(Criteria criteria)
  public String preparedInsert()
  private String columnList(Column[] columns)
  private String valuesList(Object[] fields, final Column[] columns)
  private String selectWithCriteria(String criteria)
  private String placeholderList(Column[] columns)
}
✅ Listing 10-10 — closed classes 
abstract public class Sql {
  public Sql(String table, Column[] columns)
  abstract public String generate();
}
public class CreateSql extends Sql {
  public CreateSql(String table, Column[] columns)
  @Override public String generate()
}
public class SelectSql extends Sql {
  public SelectSql(String table, Column[] columns)
  @Override public String generate()
}
public class InsertSql extends Sql {
  public InsertSql(String table, Column[] columns, Object[] fields)

Open-Closed Principle (OCP)

Classes should be open for extension but closed for modification. Adding an update statement means dropping in a new UpdateSql subclass — no existing class changes. Each class becomes excruciatingly simple, isolated, and easy to test. Incorporate new features by extending the system, not modifying existing code.

10.8Isolating from Change (DIP)

A client depending on concrete details is at risk when those details change — and hard to test. A Portfolio that directly used a live TokyoStockExchange would give a different answer every five minutes. Introduce an interface and inject it:

public interface StockExchange {
  Money currentPrice(String symbol);
}

public Portfolio {
  private StockExchange exchange;
  public Portfolio(StockExchange exchange) {
    this.exchange = exchange;
  }
  // ...
}

Now the test injects a fixed stub that always returns a known price:

public class PortfolioTest {
  private FixedStockExchangeStub exchange;
  private Portfolio portfolio;
  @Before
  protected void setUp() throws Exception {
    exchange = new FixedStockExchangeStub();
    exchange.fix("MSFT", 100);
    portfolio = new Portfolio(exchange);
  }
  @Test
  public void GivenFiveMSFTTotalShouldBe500() throws Exception {
    portfolio.add(5, "MSFT");
    Assert.assertEquals(500, portfolio.value());
  }
}
Dependency Inversion Principle (DIP)

Classes should depend upon abstractions, not concrete details. Portfolio now depends on the StockExchange interface (the abstract concept of "current price of a symbol"), not on TokyoStockExchange. Decoupling like this makes the system testable, more flexible, and more reusable — each element is isolated from change and easier to understand.

10.9Principles & Rules

Small Classes

Measure size by responsibilities; a concise name and a 25-word description are litmus tests.

SRP

One, and only one, reason to change per class.

High Cohesion → Many Small Classes

When cohesion drops, a new class is trying to get out — split it.

OCP

Open for extension, closed for modification; add features by extending.

DIP

Depend on abstractions, not concrete details, to isolate from change.

10.10Common Mistakes

God classes

Dozens of methods and many responsibilities crammed into one class.

Stopping at "it works"

Never refactoring the overstuffed class into single-responsibility units.

Weasel-word names

Processor, Manager, Super — signs of aggregated responsibilities.

Opening classes to change them

Modifying existing code instead of extending via subclasses (OCP).

Depending on concrete details

Coupling to a concrete API makes code fragile and hard to test.
