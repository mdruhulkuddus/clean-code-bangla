TL;DR

Kent Beck's four rules of Simple Design, in priority order, make good design emerge: a design is simple if it runs all the tests, contains no duplication, expresses the programmer's intent, and minimizes classes and methods. Being testable pushes you toward small, single-purpose, loosely-coupled classes. Then refactoring — done safely under the protection of tests — lets you eliminate duplication, sharpen names, and apply patterns. These simple practices don't replace experience, but they encode decades of it.

12.1Getting Clean via Emergent Design

According to Kent Beck, a design is "simple" if it follows these rules, in order of importance:

Kent Beck's Four Rules of Simple Design

1. Runs all the tests  •  2. Contains no duplication  •  3. Expresses the intent of the programmer  •  4. Minimizes the number of classes and methods.

Following these rules gives you insights into structure and design, making it easier to apply principles like SRP and DIP — facilitating the emergence of good design.

12.2Simple Design Rule 1: Runs All the Tests

A design must produce a system that works as intended. A system that can't be easily verified should arguably never be deployed. Crucially, the act of making a system testable improves its design:

Tests drive better design

Testable code pushes toward small, single-purpose classes (SRP is easier to test). Tight coupling makes tests hard to write, so writing more tests pushes you toward DIP, dependency injection, interfaces, and abstraction — minimizing coupling. A simple, obvious rule ("have tests and run them continuously") drives the primary OO goals of low coupling and high cohesion. Writing tests leads to better designs.

12.3Simple Design Rules 2–4: Refactoring

Once you have tests, you can keep code clean fearlessly. After every few lines, pause and reflect: did I just degrade the design? If so, clean it and run the tests. The tests eliminate the fear that cleanup will break something.

This refactoring step is where you apply the whole body of design knowledge — increase cohesion, decrease coupling, separate concerns, shrink functions and classes, choose better names — and apply the final three rules: eliminate duplication, ensure expressiveness, and minimize classes and methods.

12.4No Duplication

Duplication is the primary enemy of a well-designed system.

It represents extra work, extra risk, and unnecessary complexity. Duplication appears as identical lines, similar lines (massage them to look alike, then refactor), and duplication of implementation:

❌ Two separate implementations 
int size() {}
boolean isEmpty() {}
// isEmpty tracks its own boolean,
// size tracks its own counter
✅ Tie one to the other 
boolean isEmpty() {
  return 0 == size();
}

Even tiny duplication is worth eliminating — extracting a small replaceImage method shared by two image operations:

❌ Duplicated dispose/gc/assign 
public void scaleToOneDimension(
    float desiredDimension, float imageDimension) {
  if (Math.abs(desiredDimension - imageDimension) < errorThreshold)
    return;
  float scalingFactor = desiredDimension / imageDimension;
  scalingFactor = (float)(Math.floor(scalingFactor * 100) * 0.01f);
  RenderedOp newImage = ImageUtilities.getScaledImage(
    image, scalingFactor, scalingFactor);
  image.dispose();
  System.gc();
  image = newImage;
}
public synchronized void rotate(int degrees) {
  RenderedOp newImage = ImageUtilities.getRotatedImage(
    image, degrees);
  image.dispose();
  System.gc();
  image = newImage;
}
✅ Extracted replaceImage 
public void scaleToOneDimension(
    float desiredDimension, float imageDimension) {
  if (Math.abs(desiredDimension - imageDimension) < errorThreshold)
    return;
  float scalingFactor = desiredDimension / imageDimension;
  scalingFactor = (float)(Math.floor(scalingFactor * 100) * 0.01f);
  replaceImage(ImageUtilities.getScaledImage(
    image, scalingFactor, scalingFactor));
}
public synchronized void rotate(int degrees) {
  replaceImage(ImageUtilities.getRotatedImage(image, degrees));
}
private void replaceImage(RenderedOp newImage) {
  image.dispose();
  System.gc();
  image = newImage;
}

Extracting commonality at this tiny level surfaces SRP violations and enables "reuse in the small" — which is essential to achieving reuse in the large.

Template Method for higher-level duplication

❌ Duplicated algorithm 
public class VacationPolicy {
  public void accrueUSDivisionVacation() {
    // calculate vacation from hours worked
    // ensure vacation meets US minimums
    // apply vacation to payroll record
  }
  public void accrueEUDivisionVacation() {
    // calculate vacation from hours worked
    // ensure vacation meets EU minimums
    // apply vacation to payroll record
  }
}
✅ TEMPLATE METHOD pattern 
abstract public class VacationPolicy {
  public void accrueVacation() {
    calculateBaseVacationHours();
    alterForLegalMinimums();
    applyToPayroll();
  }
  private void calculateBaseVacationHours() { /* ... */ };
  abstract protected void alterForLegalMinimums();
  private void applyToPayroll() { /* ... */ };
}
public class USVacationPolicy extends VacationPolicy {
  @Override protected void alterForLegalMinimums() {
    // US specific logic
  }
}
public class EUVacationPolicy extends VacationPolicy {
  @Override protected void alterForLegalMinimums() {
    // EU specific logic
  }
}

The subclasses fill in the one "hole" in the algorithm — the only part that isn't duplicated.

12.5Expressive

The majority of a project's cost is long-term maintenance, and most defects come from misunderstanding. Code should clearly express the intent of its author — the clearer it is, the less time others spend understanding it. Ways to be expressive:

How to express intent

Choose good names (hear a name and not be surprised by its responsibilities); keep functions and classes small (easy to name, write, understand); use standard nomenclature — pattern names like COMMAND or VISITOR in class names succinctly convey design; and write well-written unit tests as documentation by example.

The most important way: try

Too often we get code working and move on without making it readable for the next person — who is most likely to be you. Take pride in your workmanship: spend a little time with each function and class, choose better names, split large functions. Care is a precious resource.

12.6Minimal Classes and Methods

Even good ideas — eliminating duplication, expressiveness, SRP — can be taken too far, producing too many tiny classes and methods. Keep function and class counts low too.

Pointless dogmatism

High counts often come from dogma: insisting on an interface for every class, or always separating fields and behavior into data classes and behavior classes. Resist such dogma; adopt a pragmatic approach. But remember this rule is the lowest priority of the four — having tests, eliminating duplication, and expressing yourself matter more.

12.7Principles & Rules

Runs All Tests (highest priority)

A verifiable system; testability forces low coupling and high cohesion.

No Duplication

The primary enemy of good design; eliminate it even in a few lines, via extraction and Template Method.

Expressive

Good names, small units, standard pattern names, expressive tests — and above all, try.

Minimal Classes & Methods (lowest priority)

Keep counts low, but never at the expense of the higher three rules.

12.8Common Mistakes

Skipping tests

An unverifiable design — and a missed driver of low coupling / high cohesion.

Tolerating "just a little" duplication

Small duplications fester; eliminating them surfaces deeper design improvements.

Stopping at "it works"

Leaving code unreadable for the next person — who is probably you.

Dogmatic over-decomposition

An interface per class, or rigid data/behavior splits, inflating class and method counts.
