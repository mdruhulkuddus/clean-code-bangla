How to use this list

Martin compiled this by refactoring several programs and, with each change, writing down why he made it. The result distills the entire book into a checklist. These are heuristics, not hard rules — a description of the value system that drives clean code. Read it top to bottom once, then keep it as a reference and a code-review aid.

CComments C1–C5

CodeHeuristicWhat it means
C1Inappropriate InformationComments should hold info the code/system can't — not change history, authors, or metadata that belongs in source control or other systems.
C2Obsolete CommentA comment that has grown old, irrelevant, or wrong. Update or delete it before it misleads — better yet, don't write ones that can go stale.
C3Redundant CommentA comment that says nothing the code doesn't already say (e.g. i++; // increment i). It just takes time to read and can drift out of sync.
C4Poorly Written CommentIf you write one, make it the best you can: brief, correct, grammatical — don't ramble or state the obvious.
C5Commented-Out CodeDelete it. It rots, confuses readers who fear removing it, and source control remembers it anyway.

EEnvironment E1–E2

CodeHeuristicWhat it means
E1Build Requires More Than One StepYou should check out and build the whole system with one trivial command — not hunt for files or type a long sequence.
E2Tests Require More Than One StepYou should run all unit tests with one button or one command. Anything harder discourages running them.

FFunctions F1–F4

CodeHeuristicWhat it means
F1Too Many ArgumentsPrefer zero, then one, then two. Three is questionable; more should be avoided.
F2Output ArgumentsCounterintuitive — readers expect arguments as inputs. If a function must change state, change its own object's state.
F3Flag ArgumentsA boolean argument announces the function does more than one thing. Eliminate it; split the function.
F4Dead FunctionMethods that are never called should be deleted. Source control keeps the history.

GGeneral G1–G36

CodeHeuristicWhat it means
G1Multiple Languages in One Source FileMinimize the number and extent of languages in a file (Java + HTML + XML + …). Ideally one.
G2Obvious Behavior Is UnimplementedFollow the Principle of Least Surprise — a function should do what a reader obviously expects (e.g. day-name parsing should be case-insensitive).
G3Incorrect Behavior at the BoundariesDon't rely on intuition; write tests for every boundary and corner case. Bugs hide at the edges.
G4Overridden SafetiesDon't turn off compiler warnings, skip failing tests, or override safeguards — it's risking debts that come due.
G5Duplication"DRY" / "Once and only once." Every duplication is a missed abstraction — fold it into a method, base class, or pattern (Template Method, polymorphism, etc.).
G6Code at Wrong Level of AbstractionSeparate higher-level general concepts from lower-level detailed ones, and put them in different (base vs. derivative) places.
G7Base Classes Depending on DerivativesBase classes should know nothing of their derivatives. Such dependence usually signals a deployment/partitioning problem.
G8Too Much InformationKeep interfaces small and tight — few methods, few variables. Well-defined modules hide almost everything; less coupling = less to know.
G9Dead CodeCode that never executes (unreachable branches, unused utilities). Find it and delete it.
G10Vertical SeparationDeclare variables and define private functions close to where they're used; minimize vertical distance.
G11InconsistencyDo similar things the same way. Consistency lets readers trust their assumptions (the Principle of Least Surprise again).
G12ClutterDefault constructors with no use, unused variables, meaningless comments — remove everything that isn't pulling its weight.
G13Artificial CouplingDon't couple things that have no real dependency by placing them together for convenience (e.g. a general enum nested in a specific class).
G14Feature EnvyA method that fiddles with another object's data via its accessors "envies" that class — move the behavior to where the data lives (Fowler's smell).
G15Selector ArgumentsFlags and other selector args force the reader to remember what each value means. Prefer many small functions over one with a selector.
G16Obscured IntentDon't write so densely that intent is hidden (run-on expressions, magic numbers, Hungarian notation). Make it expressive.
G17Misplaced ResponsibilityPut code where a reader would naturally expect it — based on the Principle of Least Surprise, not on what's convenient to you.
G18Inappropriate StaticPrefer nonstatic methods. Make a function static only when there's no chance you'll want polymorphic behavior on it.
G19Use Explanatory VariablesBreak calculations into intermediate values with meaningful names — one of the most powerful ways to make a program readable.
G20Function Names Should Say What They DoIf you must look at the implementation (or docs) to know what a call does, the name has failed — rename it.
G21Understand the AlgorithmDon't just hack until tests pass. Know why a function works; refactor it until it obviously reflects your understanding.
G22Make Logical Dependencies PhysicalIf one module depends on another, make that dependency explicit — don't make assumptions about the other module's behavior (e.g. ask it for the value rather than hard-coding it).
G23Prefer Polymorphism to If/Else or Switch/CaseConsider polymorphism before reaching for selection. "One switch" rule: there may be at most one switch for a given type of selection, hidden behind a factory.
G24Follow Standard ConventionsThe team follows one standard (formatting, naming, organization) based on industry norms — and everyone abides by it.
G25Replace Magic Numbers with Named ConstantsHide raw literals behind well-named constants. ("Magic number" includes any unexplained token, not just numbers.)
G26Be PreciseDon't be lazy about decisions — check for nulls, handle concurrency, lock when needed, use the right type. Ambiguity in code is laziness.
G27Structure over ConventionEnforce design decisions with structure (abstract methods, polymorphism) rather than relying on a convention people must remember.
G28Encapsulate ConditionalsExtract boolean logic into well-named functions: if (shouldBeDeleted(timer)) beats a tangled inline expression.
G29Avoid Negative ConditionalsPositives are easier to read than negatives — prefer if (buffer.shouldCompact()) over if (!buffer.shouldNotCompact()).
G30Functions Should Do One ThingA function with many sections doing several things should be split into smaller single-purpose functions.
G31Hidden Temporal CouplingsWhen calls must happen in a certain order, make it visible — have each call produce a result the next one needs as an argument.
G32Don't Be ArbitraryHave a reason for the way you structure code, and make that reason consistent and communicated, so others won't "fix" it.
G33Encapsulate Boundary ConditionsDon't scatter +1/-1 edge logic; capture it in one well-named variable (e.g. nextLevel = level + 1).
G34Functions Should Descend Only One Level of AbstractionStatements in a function should all be one level below the function's name — don't mix high- and low-level operations.
G35Keep Configurable Data at High LevelsConstants and config values known at a high level should live there and be passed down, not buried in low-level functions.
G36Avoid Transitive NavigationThe Law of Demeter / "writing shy code." A module should know only its direct collaborators, not navigate a.getB().getC() chains.

JJava J1–J3

CodeHeuristicWhat it means
J1Avoid Long Import Lists by Using WildcardsIf you use two or more classes from a package, import the whole package with * to reduce clutter and coupling to specific names.
J2Don't Inherit ConstantsDon't hide constants in an inherited interface/class to avoid qualifying them. Use a static import instead.
J3Constants versus EnumsUse enums, not public static final int constants. Enums are type-safe, carry behavior, and read better.

NNames N1–N7

CodeHeuristicWhat it means
N1Choose Descriptive NamesNames are 90% of readability. Choose them carefully and keep them current; a good name reveals intent and abstraction.
N2Names at the Appropriate Level of AbstractionDon't name things for their implementation; name them for their concept/intent (so the name survives implementation changes).
N3Use Standard Nomenclature Where PossibleLean on names rooted in conventions and patterns (...Visitor, ...Factory, toString) so readers recognize them instantly.
N4Unambiguous NamesPick a name that leaves no doubt about what a function or variable does — even if it's longer.
N5Use Long Names for Long ScopesShort names (i, j) are fine in tiny scopes; the larger the scope, the longer and clearer the name should be.
N6Avoid EncodingsNo Hungarian notation, no type/scope prefixes, no m_. Modern tools make them needless noise.
N7Names Should Describe Side-EffectsA name should reveal everything a function does — getOos() that also creates the stream should be createOrReturnOos().

TTests T1–T9

CodeHeuristicWhat it means
T1Insufficient TestsA test suite should test everything that could plausibly break — not just the few cases you happened to think of.
T2Use a Coverage Tool!Coverage tools reveal the gaps in your testing strategy and find untested branches and statements.
T3Don't Skip Trivial TestsThey're easy to write and their documentary value outweighs the cost.
T4An Ignored Test Is a Question about an AmbiguityExpress an open question about requirements as a commented-out or @Ignore'd test, depending on whether it compiles.
T5Test Boundary ConditionsTake special care to test the edges — the middle of an algorithm is often right while the boundaries are wrong.
T6Exhaustively Test Near BugsBugs cluster. When you find one, test thoroughly around it — there are probably more nearby.
T7Patterns of Failure Are RevealingThe pattern of which tests pass and fail can diagnose the problem; complete test cases ordered reasonably expose patterns.
T8Test Coverage Patterns Can Be RevealingLooking at what passing tests do and don't execute gives clues to why failing tests fail.
T9Tests Should Be FastA slow test is a test that won't get run. Keep them fast so they're run often.
The high-value handful

If you internalize only a few: G5 Duplication, G30 Do One Thing, G34 One Level of Abstraction, G25 Magic Numbers, G28/G29 Encapsulate & avoid negative conditionals, N1 Descriptive Names, and G36 Law of Demeter. They recur throughout every chapter of the book.

★Conclusion

This list of heuristics and smells could hardly be said to be complete. … Indeed, I'm not sure that such a list can ever be complete.

But completeness isn't the goal. The list implies a value system — and that value system is the real point of the book, and its true subject. A knowledge of these heuristics is not what makes a craftsman; you can know them all and still apply them poorly. Craftsmanship is the discipline of caring — applying the values, not just memorizing the rules.

One-liner Takeaway

These 67 heuristics aren't rules to memorize but a value system to absorb — clean code comes from caring, applied one small decision at a time.
