TL;DR

Objects hide their data behind abstractions and expose functions that operate on it; data structures expose their data and have no meaningful behavior — they are virtual opposites. This creates an anti-symmetry: OO code makes it easy to add new types but hard to add new functions; procedural code is the reverse. Pick the side that fits the change you expect. The Law of Demeter says talk to friends, not strangers — avoid "train wreck" call chains that reach through an object's innards. And don't blindly bolt getters/setters onto everything: that creates hybrids, the worst of both worlds.

6.1Data Abstraction

We keep variables private so no one depends on them and we stay free to change their type or implementation. So why do so many programmers reflexively add getters and setters, effectively making private variables public again?

❌ Listing 6-1 — Concrete Point 
public class Point {
  public double x;
  public double y;
}
✅ Listing 6-2 — Abstract Point 
public interface Point {
  double getX();
  double getY();
  void setCartesian(double x, double y);
  double getR();
  double getTheta();
  void setPolar(double r, double theta);
}

You can't tell whether Listing 6-2 is rectangular or polar — it might be neither. The interface also enforces a policy: read coordinates independently, but set them together atomically. The concrete version forces you to manipulate rectangular coordinates and exposes implementation (even with private fields and single-variable getters/setters).

❌ Listing 6-3 — Concrete Vehicle 
public interface Vehicle {
  double getFuelTankCapacityInGallons();
  double getGallonsOfGasoline();
}
✅ Listing 6-4 — Abstract Vehicle 
public interface Vehicle {
  double getPercentFuelRemaining();
}
Hiding Implementation = Abstraction

Hiding implementation isn't just putting a layer of functions over variables. A class should expose abstract interfaces that let users manipulate the essence of the data without knowing its form. The worst option is to blithely add getters and setters; serious thought belongs in how you represent the data.

6.2Data/Object Anti-Symmetry

The Two Definitions (virtual opposites)

Objects hide their data behind abstractions and expose functions that operate on that data. Data structures expose their data and have no meaningful functions. Read that again — the difference seems trivial but has far-reaching implications.

Procedural — Listing 6-5 
public class Square {
  public Point topLeft;
  public double side;
}
public class Rectangle {
  public Point topLeft;
  public double height;
  public double width;
}
public class Circle {
  public Point center;
  public double radius;
}
public class Geometry {
  public final double PI = 3.141592653589793;
  public double area(Object shape) throws NoSuchShapeException
  {
    if (shape instanceof Square) {
      Square s = (Square)shape;
      return s.side * s.side;
    }
    else if (shape instanceof Rectangle) {
      Rectangle r = (Rectangle)shape;
      return r.height * r.width;
    }
    else if (shape instanceof Circle) {
      Circle c = (Circle)shape;
      return PI * c.radius * c.radius;
    }
    throw new NoSuchShapeException();
  }
}
Object-Oriented — Listing 6-6 
public class Square implements Shape {
  private Point topLeft;
  private double side;
  public double area() {
    return side*side;
  }
}
public class Rectangle implements Shape {
  private Point topLeft;
  private double height;
  private double width;
  public double area() {
    return height * width;
  }
}
public class Circle implements Shape {
  private Point center;
  private double radius;
  public final double PI = 3.141592653589793;
  public double area() {
    return PI * radius * radius;
  }
}

Add a perimeter() function: the procedural shapes are unaffected, but you must touch every function in Geometry to add a new shape. The OO version is the mirror image — add a new shape freely, but adding a function forces a change to all shapes.

The Fundamental Dichotomy

Procedural code makes it easy to add new functions without changing existing data structures, but hard to add new data structures (every function must change). OO code makes it easy to add new classes without changing existing functions, but hard to add new functions (every class must change). What's hard for one is easy for the other — so the idea that "everything is an object" is a myth. Sometimes you really do want simple data structures with procedures operating on them.

6.3The Law of Demeter

Law of Demeter

A module should not know about the innards of the objects it manipulates. More precisely, a method f of class C should only call methods of: C itself, an object created by f, an object passed as an argument to f, or an object held in an instance variable of C. It should not call methods on objects returned by those allowed calls. In short: talk to friends, not to strangers.

6.4Train Wrecks

❌ Train wreck 
final String outputDir = ctxt.getOptions()
  .getScratchDir().getAbsolutePath();
✅ Split up 
Options opts = ctxt.getOptions();
File scratchDir = opts.getScratchDir();
final String outputDir = scratchDir.getAbsolutePath();

Chained calls look like coupled train cars. Whether this violates Demeter depends on what ctxt, Options, and ScratchDir are: if they're objects, reaching through their innards is a clear violation; if they're plain data structures (which naturally expose their fields), Demeter doesn't apply. Accessor functions muddy this — written as ctxt.options.scratchDir.absolutePath we wouldn't even ask. The confusion arises because frameworks (like "beans") demand accessors even on simple data structures.

6.5Hybrids

The worst of both worlds

A hybrid is half object, half data structure: it has functions that do significant things and public variables (or public accessors/mutators) that effectively expose its private fields. Hybrids make it hard to add new functions and hard to add new data structures. They signal a muddled design whose authors aren't sure whether they need protection from functions or from types. Avoid creating them.

6.6Hiding Structure

If ctxt, options, and scratchDir are real objects, we shouldn't navigate through them at all. Neither ctxt.getAbsolutePathOfScratchDirectoryOption() (an explosion of methods) nor ctx.getScratchDirectoryOption().getAbsolutePath() (which presumes a returned data structure) feels good.

So ask why we wanted the absolute path. The code downstream was building a scratch file:

String outFile = outputDir + "/" + className.replace('.', '/') + ".class";
FileOutputStream fout = new FileOutputStream(outFile);
BufferedOutputStream bos = new BufferedOutputStream(fout);
❌ Asking for internals 
final String outputDir =
  ctxt.options.scratchDir.absolutePath;
// ...then build the stream by hand
✅ Telling the object what to do 
BufferedOutputStream bos =
  ctxt.createScratchFileStream(classFileName);

Tell ctxt to create the scratch file. That lets it hide its internals and frees the caller from navigating objects it shouldn't know about — tell, don't ask.

6.7Data Transfer Objects

The quintessential data structure is a class with public variables and no functions — a Data Transfer Object (DTO). DTOs are very useful for talking to databases or parsing socket messages, often the first stage that converts raw data into application objects. The more common "bean" form uses private fields with getters/setters:

public class Address {
  private String street;
  private String streetExtra;
  private String city;
  private String state;
  private String zip;
  public Address(String street, String streetExtra,
                 String city, String state, String zip) {
    this.street = street;
    this.streetExtra = streetExtra;
    this.city = city;
    this.state = state;
    this.zip = zip;
  }
  public String getStreet() { return street; }
  public String getStreetExtra() { return streetExtra; }
  public String getCity() { return city; }
  public String getState() { return state; }
  public String getZip() { return zip; }
}

The bean's quasi-encapsulation soothes OO purists but usually provides no other benefit.

Active Record

An Active Record is a DTO with navigational methods like save and find, typically a direct translation of a database table. The mistake is adding business-rule methods to it, creating a hybrid. The solution: treat the Active Record as a pure data structure and put business rules in separate objects that hide their data (which may just be instances of the Active Record).

6.8Principles & Rules

Abstraction over Accessors

Expose the essence of data through abstract interfaces — don't reflexively add getters/setters.

Object/Data Anti-Symmetry

Objects ease new types; data structures ease new functions. Choose by the change you expect.

Law of Demeter

Talk to friends, not strangers; don't reach through returned objects.

Tell, Don't Ask

Tell an object to do work rather than asking for its internals to do it yourself.

No Prejudice

"Everything is an object" is a myth; sometimes a plain data structure is right.

6.9Common Mistakes

Reflexive getters/setters

Pushing every private variable out through accessors — exposing, not hiding, implementation.

Train-wreck call chains

Reaching through an object's innards: a.getB().getC().getD().

Creating hybrids

Mixing significant behavior with exposed data — hard to extend in either direction.

Business rules in Active Records

Treating a data structure as an object; keep rules in separate objects.

Dogmatic OO

Forcing objects where simple data + procedures would serve better.
