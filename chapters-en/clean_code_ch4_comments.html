TL;DR

Comments don't make up for bad code — if you're tempted to explain a mess, clean the mess instead. Comments lie: code changes but comments drift away from it, growing inaccurate and misleading over time. The only truly good comment is the one you found a way not to write by expressing yourself in code. A handful are genuinely useful — legal, intent, warnings, clarification, amplification, TODOs, public-API Javadocs — but most are redundant, mandated, noisy, or journal clutter that source control already handles. Truth lives in one place: the code.

4.1Comments Are a Necessary Evil

"Don't comment bad code — rewrite it." — Brian W. Kernighan and P. J. Plauger

The proper use of a comment is to compensate for our failure to express ourselves in code. Martin means "failure" literally: every comment is a small defeat for your expressive ability. When you find yourself reaching for one, think about whether you can turn the tables and say it in code instead.

Why comments rot

Code moves, splits, and recombines, but comments can't always follow. They become orphaned blurbs of ever-decreasing accuracy. An example: a HTTP_DATE_REGEXP constant whose explanatory comment // Example: "Tue, 02 Apr 2003 22:18:49 GMT" ended up separated by several later-added instance variables.

Key Insight

Inaccurate comments are far worse than no comments at all — they delude, mislead, and set expectations that will never be met. Truth can be found in only one place: the code.

4.2Comments Do Not Make Up for Bad Code

The wrong instinct

You write a confusing, disorganized module and think, "Ooh, I'd better comment that!" No — you'd better clean it. Clear, expressive code with few comments beats cluttered code with many. Spend the time cleaning the mess, not documenting it.

4.3Explain Yourself in Code

In many cases a comment can be replaced simply by creating a function that says the same thing:

❌ Before 
// Check to see if the employee is eligible for full benefits
if ((employee.flags & HOURLY_FLAG) &&
    (employee.age > 65))
✅ After 
if (employee.isEligibleForFullBenefits())

It takes only a few seconds of thought to capture most intent in code rather than a comment.

4.4Good Comments

Some comments earn the bits they consume — but remember, the only truly good comment is the one you didn't have to write.

Legal Comments

Copyright and license headers are reasonable. Keep them short and refer to an external license where possible rather than embedding a legal tome.

// Copyright (C) 2003,2004,2005 by Object Mentor, Inc. All rights reserved.
// Released under the terms of the GNU General Public License version 2 or later.

Informative Comments

Basic information can help, though renaming is usually better. This comment tells us the regex matches a formatted time/date:

// format matched kk:mm:ss EEE, MMM dd, yyyy
Pattern timeMatcher = Pattern.compile(
  "\d*:\d*:\d* \w*, \w* \d*, \d*");

Explanation of Intent

A comment can document the reasoning behind a decision — you may disagree with the solution, but at least you understand what the author was trying to do (e.g. sorting objects of one's own class above all others, or a deliberate attempt to provoke a race condition by spawning 25,000 threads in a test).

Clarification

Translating an obscure standard-library argument or return value can help when you can't alter the code itself — but it's risky, because a clarifying comment can easily be wrong. Verify accuracy before writing one.

assertTrue(a.compareTo(a) == 0);   // a == a
assertTrue(a.compareTo(b) != 0);   // a != b
assertTrue(a.compareTo(b) == -1);  // a < b

Warning of Consequences

Warning other programmers can be justified — e.g. why a test is disabled (// Don't run unless you have some time to kill.) or why a SimpleDateFormat instance is created fresh each time (it isn't thread-safe), preventing an over-eager optimizer from using a static initializer.

TODO Comments

//TODO notes mark work the programmer can't do right now. IDEs locate them easily, but they are not an excuse to leave bad code. Scan and prune them regularly.

//TODO-MdM these are not needed
// We expect this to go away when we do the checkout model
protected VersionInfo makeVersion() throws Exception {
  return null;
}

Amplification & Public-API Javadocs

A comment can amplify the importance of something easily overlooked (e.g. "the trim is real important — it removes the starting spaces…"). And a well-described public API deserves good Javadocs — the standard Java library is the case in point — but they can mislead just like any comment, so apply the rest of this chapter's advice to them too.

4.5Bad Comments

Most comments fall here — crutches, excuses, or the programmer talking to himself.

Mumbling

Plopping in a comment because you feel you should is a hack. An empty catch with // No properties files means all defaults are loaded raises more questions than it answers — and forces you to read other modules to decode it. A comment that sends you elsewhere has failed.

Redundant Comments

A header that takes longer to read than the code it describes (and is less precise) serves no purpose — like a used-car salesman insisting you needn't look under the hood. The Tomcat ContainerBase class is buried under dozens of these.

Misleading Comments

A comment saying a method "returns when this.closed is true" when it actually waits for a blind timeout and then throws — subtly wrong, leading a caller into a slow debugging session.

Mandated Comments

A rule that every function needs a Javadoc and every variable a comment produces clutter, lies, and confusion — like a CD's Javadoc that re-lists each obvious parameter.

Journal Comments

A running change-log at the top of a module made sense before source control. Now it's pure clutter — delete it; the VCS remembers every edit.

Noise Comments

/** Default constructor. */ or /** The day of the month. */ private int dayOfMonth; restate the obvious. We learn to ignore them — and then they start to lie as the code drifts.

Position Markers & Closing-Brace Comments

Banners like // Actions ////////////// become background noise if overused. } //while / } //catch markers signal your functions are too long — shorten them instead.

Attributions, HTML, Nonlocal & Too-Much Info

/* Added by Rick */ belongs in source control. HTML inside comments is an abomination in the editor. Don't put systemwide facts (like a default port the function can't control) in a local comment, nor irrelevant historical essays (the full RFC 2045 base64 spec).

Inobvious Connection & Nonpublic Javadocs

If a comment needs its own explanation ("what's a filter byte? does it relate to the +1 or the *3?"), it has failed. And generating Javadocs for non-public internal code adds only cruft and formality.

4.6Don't Use a Comment When a Function or Variable Will Do

❌ Before 
// does the module from the global list <mod> depend on the
// subsystem we are part of?
if (smodule.getDependSubsystems().contains(subSysMod.getSubSystem()))
✅ After 
ArrayList moduleDependees = smodule.getDependSubsystems();
String ourSubSystem = subSysMod.getSubSystem();
if (moduleDependees.contains(ourSubSystem))

Naming intermediate values makes the intent self-evident and lets the comment disappear.

4.7Commented-Out Code

Don't do this!

Few practices are as odious. Others won't dare delete commented-out lines — they assume they're important — so the dead code gathers "like dregs at the bottom of a bad bottle of wine." Source control remembers it. Just delete it. You won't lose it. Promise.

this.bytePos = writeBytes(pngIdBytes, 0);
//hdrPos = bytePos;
writeHeader();
writeResolution();
//dataPos = bytePos;
if (writeImageData()) {
  writeEnd();
  this.pngBytes = resizeByteArray(this.pngBytes, this.maxPos);
}

4.8Full Example: GeneratePrimes → PrimeGenerator

This module was written as an example of bad commenting style, then refactored. Spot how many comment problems live in the "before."

❌ Before — Listing 4-7 (GeneratePrimes.java) 
/**
 * This class Generates prime numbers up to a user specified
 * maximum. The algorithm used is the Sieve of Eratosthenes.
 * <p>
 * Eratosthenes of Cyrene, b. c. 276 BC, Cyrene, Libya --
 * d. c. 194, Alexandria. The first man to calculate the
 * circumference of the Earth. Also known for working on
 * calendars with leap years and ran the library at Alexandria.
 * <p>
 * The algorithm is quite simple. Given an array of integers
 * starting at 2. Cross out all multiples of 2. Find the next
 * uncrossed integer, and cross out all of its multiples.
 * Repeat untilyou have passed the square root of the maximum
 * value.
 *
 * @author Alphonse
 * @version 13 Feb 2002 atp
 */
import java.util.*;
public class GeneratePrimes
{
  /**
   * @param maxValue is the generation limit.
   */
  public static int[] generatePrimes(int maxValue)
  {
    if (maxValue >= 2) // the only valid case
    {
      // declarations
      int s = maxValue + 1; // size of array
      boolean[] f = new boolean[s];
      int i;
      // initialize array to true.
      for (i = 0; i < s; i++)
        f[i] = true;
      // get rid of known non-primes
      f[0] = f[1] = false;
      // sieve
      int j;
      for (i = 2; i < Math.sqrt(s) + 1; i++)
      {
        if (f[i]) // if i is uncrossed, cross its multiples.
        {
          for (j = 2 * i; j < s; j += i)
            f[j] = false; // multiple is not prime
        }
      }
      // how many primes are there?
      int count = 0;
      for (i = 0; i < s; i++)
      {
        if (f[i])
          count++; // bump count.
      }
      int[] primes = new int[count];
      // move the primes into the result
      for (i = 0, j = 0; i < s; i++)
      {
        if (f[i]) // if prime
          primes[j++] = i;
      }
      return primes; // return the primes
    }
    else // maxValue < 2
      return new int[0]; // return null array if bad input.
  }
}
✅ After — Listing 4-8 (PrimeGenerator.java) 
/**
 * This class Generates prime numbers up to a user specified
 * maximum. The algorithm used is the Sieve of Eratosthenes.
 * Given an array of integers starting at 2:
 * Find the first uncrossed integer, and cross out all its
 * multiples. Repeat until there are no more multiples
 * in the array.
 */
public class PrimeGenerator
{
  private static boolean[] crossedOut;
  private static int[] result;
  public static int[] generatePrimes(int maxValue)
  {
    if (maxValue < 2)
      return new int[0];
    else
    {
      uncrossIntegersUpTo(maxValue);
      crossOutMultiples();
      putUncrossedIntegersIntoResult();
      return result;
    }
  }
  private static void uncrossIntegersUpTo(int maxValue)
  {
    crossedOut = new boolean[maxValue + 1];
    for (int i = 2; i < crossedOut.length; i++)
      crossedOut[i] = false;
  }
  private static void crossOutMultiples()
  {
    int limit = determineIterationLimit();
    for (int i = 2; i <= limit; i++)
      if (notCrossed(i))
        crossOutMultiplesOf(i);
  }
  private static int determineIterationLimit()
  {
    // Every multiple in the array has a prime factor that
    // is less than or equal to the root of the array size,
    // so we don't have to cross out multiples of numbers
    // larger than that root.
    double iterationLimit = Math.sqrt(crossedOut.length);
    return (int) iterationLimit;
  }
  private static void crossOutMultiplesOf(int i)
  {
    for (int multiple = 2*i;
         multiple < crossedOut.length;
         multiple += i)
      crossedOut[multiple] = true;
  }
  private static boolean notCrossed(int i)
  {
    return crossedOut[i] == false;
  }
  private static void putUncrossedIntegersIntoResult()
  {
    result = new int[numberOfUncrossedIntegers()];
    for (int j = 0, i = 2; i < crossedOut.length; i++)
      if (notCrossed(i))
        result[j++] = i;
  }
  private static int numberOfUncrossedIntegers()
  {
    int count = 0;
    for (int i = 2; i < crossedOut.length; i++)
      if (notCrossed(i))
        count++;
    return count;
  }
}

The refactor keeps just two comments, both explanatory: a high-level algorithm summary, and the rationale for using the square root as the loop limit (which no variable name could capture). Everything else became a well-named function.

4.9Principles & Rules

Express in Code First

Before writing a comment, try to make the code say it — via a function or a named variable.

Comments Lie Over Time

Treat every comment as a maintenance liability that drifts from the code it describes.

Truth Is in the Code

Code is the only fully accurate source; minimize anything that competes with it.

Keep Only Earned Comments

Legal, intent, warning, clarification, amplification, TODO, public-API — and only when no better option exists.

4.10Common Mistakes

Commenting instead of cleaning

Documenting a mess rather than fixing it.

Redundant / noise / mandated comments

Restating the obvious or satisfying a "comment everything" rule.

Leaving commented-out code & journals

Source control already preserves history — delete them.

Nonlocal / misleading / inobvious comments

Describing distant parts of the system, or being subtly inaccurate.

One-liner Takeaway

Every comment is a confession of failure to express yourself in code — so write the code so well that the comment becomes unnecessary.
