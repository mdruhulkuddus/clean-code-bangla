TL;DR

Formatting is communication, not decoration. Read a file vertically like a newspaper: a clear name at top, high-level concepts first, details below. Use blank lines to separate concepts and tight grouping to show association; keep related code vertically close, with callers above callees. Favor short files (~200 lines, ≤500) and short lines (~120 chars). Use horizontal whitespace to reflect operator precedence, skip column alignment, and never break indentation. Above all, a team agrees on one style so every file reads the same way.

5.1The Purpose of Formatting

Formatting is too important to ignore and too important to treat religiously. It's about communication — the professional developer's first order of business (not "getting it working"). Today's functionality will likely change next release, but readability shapes every future change.

Key Insight

Your coding style and discipline survive even though your code does not. The precedents you set continue to affect maintainability long after the original lines are rewritten.

5.2Vertical Size & The Newspaper Metaphor

Across seven projects, big systems were built from small files: FitNesse (~50,000 lines) averaged ~65 lines per file. Aim for files around 200 lines, with an upper limit near 500 — not a hard rule, but highly desirable, since small files are easier to understand.

The Newspaper Metaphor

A source file should read like a newspaper article: a simple, explanatory name (the headline), high-level concepts and algorithms at the top (the synopsis), and increasing detail as you move down. A newspaper of one long disorganized story would go unread — and so would such a file.

5.3Vertical Openness Between Concepts

Each group of lines is a complete thought; separate thoughts with blank lines. Each blank line is a visual cue that draws the eye to the start of the next concept.

✅ Listing 5-1 (with openness) 
package fitnesse.wikitext.widgets;

import java.util.regex.*;

public class BoldWidget extends ParentWidget {
  public static final String REGEXP = "'''.+?'''";
  private static final Pattern pattern = Pattern.compile("'''(.+?)'''",
    Pattern.MULTILINE + Pattern.DOTALL
  );

  public BoldWidget(ParentWidget parent, String text) throws Exception {
    super(parent);
    Matcher match = pattern.matcher(text);
    match.find();
    addChildWidgets(match.group(1));
  }

  public String render() throws Exception {
    StringBuffer html = new StringBuffer("<b>");
    html.append(childHtml()).append("</b>");
    return html.toString();
  }
}
❌ Listing 5-2 (openness removed)

Unfocus your eyes: the first version's groupings pop out, the second is a muddle. The only difference is a little vertical openness.

5.4Vertical Density

If openness separates concepts, density implies association. Tightly related lines should sit together. Useless comments break that association:

❌ Listing 5-3 (broken by comments) 
public class ReporterConfig {
  /**
   * The class name of the reporter listener
   */
  private String m_className;
  /**
   * The properties of the reporter listener
   */
  private List<Property> m_properties = new ArrayList<Property>();
  public void addProperty(Property property) {
    m_properties.add(property);
  }
✅ Listing 5-4 (dense, an "eye-full") 
public class ReporterConfig {
  private String m_className;
  private List<Property> m_properties = new ArrayList<Property>();
  public void addProperty(Property property) {
    m_properties.add(property);
  }

The dense version is read at a glance — two variables and a method — without moving your head or eyes.

5.5Vertical Distance

Closely related concepts should be kept vertically close to avoid forcing readers to hop around files. (This is one reason to avoid protected variables — they invite separation.)

Variable Declarations

Declare variables as close to their use as possible. With short functions, locals go at the top of the function; loop control variables go inside the loop statement.

Instance Variables

Declare them in one well-known place — the top of the class in Java. The worst case is the JUnit TestSuite, which hides two instance variables halfway down the class where you'd only find them by accident.

Dependent Functions

If one function calls another, keep them close, with the caller above the callee. This gives a natural top-down flow so readers can trust definitions follow shortly after their use.

Conceptual Affinity

Code with strong affinity wants to be near related code — e.g. JUnit's assertTrue/assertFalse family shares a naming scheme and task. The stronger the affinity, the smaller the vertical distance should be, even without a direct call.

5.6Vertical Ordering

Call dependencies should point downward: a called function appears below its caller, creating a flow from high level to low level (the opposite of Pascal/C/C++'s "declare before use"). Like a newspaper, the most important concepts come first with the least polluting detail, so you can skim the first few functions and get the gist.

5.7Horizontal Width

Programmers clearly prefer short lines — most lines cluster around 20–60 characters. The old 80-column Hollerith limit is arbitrary; edging out to 100 or 120 is fine, but beyond that is careless.

Uncle Bob's limit

Modern monitors let you cram 200 characters across by shrinking the font. Don't. Martin sets his personal limit at 120 characters and never scrolls right.

5.8Horizontal Openness and Density

Use horizontal whitespace to associate strongly related things and separate weakly related ones. Surround assignment operators with spaces (left side vs. right side), but put no space between a function name and its opening paren (they're tightly bound). Whitespace can also reflect operator precedence:

public class Quadratic {
  public static double root1(double a, double b, double c) {
    double determinant = determinant(a, b, c);
    return (-b + Math.sqrt(determinant)) / (2*a);
  }
  private static double determinant(double a, double b, double c) {
    return b*b - 4*a*c;
  }
}

High-precedence factors (b*b, 4*a*c) have no spaces; lower-precedence terms are separated by spaces — though most reformatting tools are blind to precedence and will flatten these subtle spacings.

5.9Horizontal Alignment

❌ Aligned (don't) 
private Socket      socket;
private InputStream input;
private OutputStream output;
private Request     request;
private Response    response;
✅ Unaligned (prefer) 
private Socket socket;
private InputStream input;
private OutputStream output;
private Request request;
private Response response;

Alignment emphasizes the wrong things (your eye reads down the names, skipping the types) and reformatting tools wipe it out. If a list is so long that alignment seems to help, the real problem is the length of the list — the class should be split.

5.10Indentation

A source file is a hierarchy of scopes; indentation makes that hierarchy visible. Programmers rely on it to hop over irrelevant scopes. Two syntactically identical programs:

❌ Unindented (impenetrable) 
public class FitNesseServer implements SocketServer { private FitNesseContext
context; public FitNesseServer(FitNesseContext context) { this.context =
context; } public void serve(Socket s) { serve(s, 10000); } public void
serve(Socket s, long requestTimeout) { try { FitNesseExpediter sender = new
FitNesseExpediter(s, context);
sender.setRequestParsingTimeLimit(requestTimeout); sender.start(); }
catch(Exception e) { e.printStackTrace(); } } }
✅ Indented (instantly clear) 
public class FitNesseServer implements SocketServer {
  private FitNesseContext context;

  public FitNesseServer(FitNesseContext context) {
    this.context = context;
  }

  public void serve(Socket s) {
    serve(s, 10000);
  }

  public void serve(Socket s, long requestTimeout) {
    try {
      FitNesseExpediter sender = new FitNesseExpediter(s, context);
      sender.setRequestParsingTimeLimit(requestTimeout);
      sender.start();
    }
    catch (Exception e) {
      e.printStackTrace();
    }
  }
}
Breaking Indentation & Dummy Scopes

Don't collapse scopes onto one line for short ifs/loops/functions — expand and indent them instead. And when a while/for has a dummy body, make the lone semicolon visible on its own indented line, or it will fool you:

while (dis.read(buf, 0, readBufferSize) != -1)
  ;

5.11Team Rules

The team rules

Every programmer has favorite formatting rules — but on a team, the team rules. Agree on one style (braces, indent size, naming), encode it in the IDE's formatter, and all comply. The FitNesse team settled theirs in about 10 minutes. A reader must trust that a formatting gesture means the same thing in every file. The goal: software that reads like one consistent voice, not a jumble of disagreeing individuals.

Consider this an example of how code makes the best coding standard document.

5.12Principles & Rules

Newspaper Metaphor

Name → high-level → detail, top to bottom; small files (~200 lines).

Openness vs. Density

Blank lines separate concepts; tight grouping shows association.

Minimize Vertical Distance

Declare near use; callers above callees; keep affine code close.

Short Lines & Meaningful Whitespace

~120 char limit; spaces reflect precedence; skip column alignment.

Consistent Indentation & Team Style

Never break indentation; one agreed style across the whole team.

5.13Common Mistakes

Removing vertical openness

Cramming everything together so concepts blur into a muddle.

Hiding instance variables mid-class

Readers can only find them by accident — declare them in one known place.

Column-aligning declarations/assignments

Emphasizes the wrong thing and gets wiped by formatters.

Collapsing scopes & invisible dummy semicolons

One-line if/loops and hidden ; mislead the reader.

Everyone using their own style

Inconsistent formatting adds complexity to the whole codebase.
