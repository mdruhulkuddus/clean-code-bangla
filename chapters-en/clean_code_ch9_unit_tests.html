TL;DR

TDD's Three Laws lock production and test code into a ~30-second cycle, producing thousands of tests a year. Dirty tests are worse than no tests — they rot until the team abandons them and loses the ability to change code safely. Tests enable all the -ilities because they enable change without fear. A clean test's first quality is readability, achieved with the BUILD-OPERATE-CHECK structure and a domain-specific testing language. Minimize asserts and test one concept per test, and keep every test F.I.R.S.T.

9.1The Three Laws of TDD

First Law

You may not write production code until you have written a failing unit test.

Second Law

You may not write more of a unit test than is sufficient to fail — and not compiling is failing.

Third Law

You may not write more production code than is sufficient to pass the currently failing test.

These laws lock you into a cycle perhaps thirty seconds long, with tests just a few seconds ahead of production code. Work this way and you write dozens of tests a day, thousands a year — covering virtually all production code. That sheer bulk can become a management problem of its own.

9.2Keeping Tests Clean

"Quick and dirty" tests

A team that let test code skip the standards of production code — bad names, long functions, no design — found that as production code evolved, the tangled tests grew ever harder to change. Old tests failed on every change, the suite became a liability, and eventually they discarded it entirely. Without tests they feared change, stopped cleaning code, and the production code rotted.

The moral

Test code is just as important as production code. It is not a second-class citizen — it requires thought, design, and care, and must be kept as clean as production code. Having dirty tests is equivalent to, if not worse than, having no tests.

9.3Tests Enable the -ilities

It is unit tests that keep code flexible, maintainable, and reusable. The reason is simple: with tests, you don't fear making changes. The higher your coverage, the less your fear — you can improve a tangled architecture with near impunity. Lose the tests and you lose the ability to improve the code's structure; the dirtier your tests, the dirtier your code becomes.

9.4Clean Tests

What makes a clean test? Three things. Readability, readability, and readability.

Readability comes from clarity, simplicity, and density of expression — say a lot with few expressions. Compare these FitNesse tests:

❌ Listing 9-1 — drowning in detail 
public void testGetPageHieratchyAsXml() throws Exception
{
  crawler.addPage(root, PathParser.parse("PageOne"));
  crawler.addPage(root, PathParser.parse("PageOne.ChildOne"));
  crawler.addPage(root, PathParser.parse("PageTwo"));

  request.setResource("root");
  request.addInput("type", "pages");
  Responder responder = new SerializedPageResponder();
  SimpleResponse response =
    (SimpleResponse) responder.makeResponse(
      new FitNesseContext(root), request);
  String xml = response.getContent();

  assertEquals("text/xml", response.getContentType());
  assertSubString("<name>PageOne</name>", xml);
  assertSubString("<name>PageTwo</name>", xml);
  assertSubString("<name>ChildOne</name>", xml);
}
✅ Listing 9-2 — refactored 
public void testGetPageHierarchyAsXml() throws Exception {
  makePages("PageOne", "PageOne.ChildOne", "PageTwo");

  submitRequest("root", "type:pages");

  assertResponseIsXML();
  assertResponseContains(
    "<name>PageOne</name>", "<name>PageTwo</name>", "<name>ChildOne</name>"
  );
}

public void testGetDataAsXml() throws Exception {
  makePageWithContent("TestPageOne", "test page");

  submitRequest("TestPageOne", "type:data");

  assertResponseIsXML();
  assertResponseContains("test page", "<Test");
}
BUILD-OPERATE-CHECK

Each clean test splits into three obvious parts: build the test data, operate on it, and check the results. The annoying detail (PathParser calls, responder construction, casting) is gone — anyone can grasp the test quickly.

9.5Domain-Specific Testing Language

Build a testing API

Rather than calling raw system APIs, build helper functions (makePages, submitRequest, assertResponseContains) that form a specialized testing language. It isn't designed up front — it evolves from refactoring test code that got too tainted by obfuscating detail, making tests easier to write and read.

9.6A Dual Standard

Test code can hold to different engineering standards than production code — still simple, succinct, and expressive, but it need not be as efficient, because it runs in a test environment. Compare these environment-controller tests:

❌ Listing 9-3 — eye ping-pong 
@Test
public void turnOnLoTempAlarmAtThreashold() throws Exception {
  hw.setTemp(WAY_TOO_COLD);
  controller.tic();
  assertTrue(hw.heaterState());
  assertTrue(hw.blowerState());
  assertFalse(hw.coolerState());
  assertFalse(hw.hiTempAlarm());
  assertTrue(hw.loTempAlarm());
}
✅ Listing 9-4/9-5 — encoded state 
@Test
public void turnOnLoTempAlarmAtThreshold() throws Exception {
  wayTooCold();
  assertEquals("HBchL", hw.getState());
}
@Test
public void turnOnCoolerAndBlowerIfTooHot() throws Exception {
  tooHot();
  assertEquals("hBChl", hw.getState());
}

Upper case = "on," lower case = "off," in a fixed order {heater, blower, cooler, hi-temp, lo-temp}. It edges close to mental-mapping, but once learned, the eye glides across the string. The getState implementation uses string concatenation instead of a StringBuffer — fine in a test environment that isn't resource-constrained. The dual standard touches efficiency, never cleanliness.

9.7One Assert / Single Concept per Test

One school says every test should have a single assert — a quick, easy-to-understand conclusion. Splitting a multi-assert test using the given-when-then convention helps, though it can cause duplication (resolvable via TEMPLATE METHOD or @Before). Martin treats single-assert as a good guideline, not a law: minimize the asserts.

Listing 9-8 — testing many concepts at once 
public void testAddMonths() {
  SerialDate d1 = SerialDate.createInstance(31, 5, 2004);
  SerialDate d2 = SerialDate.addMonths(1, d1);
  assertEquals(30, d2.getDayOfMonth());
  assertEquals(6, d2.getMonth());
  assertEquals(2004, d2.getYYYY());
  SerialDate d3 = SerialDate.addMonths(2, d1);
  assertEquals(31, d3.getDayOfMonth());
  ...
}

This tests three independent things and should be split. The real rule: minimize asserts per concept, and test just one concept per test function.

9.8F.I.R.S.T.

Fast

Tests should run quickly, or you won't run them often, and problems hide.

Independent

No test sets up the next; run them in any order. Dependence causes failure cascades.

Repeatable

Runnable in any environment — prod, QA, your laptop on a train with no network.

Self-Validating

A boolean pass/fail — never read logs or compare files by hand.

Timely

Written just before the production code that passes them, so that code stays testable.

9.9Principles & Rules

Three Laws of TDD

Failing test first; just enough test to fail; just enough code to pass.

Tests Are First-Class Code

Keep them as clean as production code or you'll lose them.

Readability Above All

BUILD-OPERATE-CHECK plus a domain-specific testing language.

One Concept per Test

Minimize asserts; don't test miscellaneous things together.

F.I.R.S.T.

Fast, Independent, Repeatable, Self-Validating, Timely.

9.10Common Mistakes

"Quick and dirty" test code

Held to lower standards — rots and gets abandoned.

Tests drowning in detail

Raw APIs and casting obscure intent; build a testing DSL.

Multiple concepts per test

Forces the reader to decode why each section exists.

Slow / interdependent tests

Discourage frequent runs and cause failure cascades.

If you let the tests rot, your code rots too — keep your tests clean and they'll keep your code free to change.
