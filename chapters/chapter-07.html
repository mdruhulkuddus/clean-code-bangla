Error Handling
by Michael Feathers

Clean code নিয়ে একটা বইতে error handling নিয়ে আলোচনা একটু অদ্ভুত লাগতে পারে। কিন্তু বাস্তবতা হলো, প্রোগ্রামিং করতে গেলে এরর হ্যান্ডলিং করতেই হয় — ইনপুট ভুল আসতে পারে, ডিভাইস কাজ নাও করতে পারে, নেটওয়ার্ক ফেইল করতে পারে। আমাদের দায়িত্ব হলো এসব পরিস্থিতিতেও কোড যেন ঠিকমতো কাজ করে।

অনেক codebase আছে যেখানে error handling এতটাই ছড়িয়ে-ছিটিয়ে থাকে যে আসল business logic বোঝাই যায় না। Error handling গুরুত্বপূর্ণ, কিন্তু এটা যদি মূল logic কে ঢেকে ফেলে, তাহলে কোড ভালো হচ্ছে না।

Exception ব্যবহার করো, Return Code নয় Use Exceptions Rather Than Return Codes

আগেকার অনেক ভাষায় exception ছিল না। তখন error জানানোর জন্য error flag সেট করা হতো, বা একটা error code রিটার্ন করা হতো যেটা caller চেক করতো। এই পদ্ধতির সমস্যা হলো — কোড জটিল ও অপরিষ্কার হয়ে যায়। নিচের উদাহরণটা দেখো:

Listing 7-1: DeviceController.java (error code ব্যবহার করে)
✗ খারাপ 
public class DeviceController {
    ...
    public void sendShutDown() {
        DeviceHandle handle = getHandle(DEV1);
        // Check the state of the device
        if (handle != DeviceHandle.INVALID) {
            // Save the device status to the record field
            retrieveDeviceRecord(handle);
            // If not suspended, shut down
            if (record.getStatus() != DEVICE_SUSPENDED) {
                pauseDevice(handle);
                clearDeviceWorkQueue(handle);
                closeDevice(handle);
            } else {
                logger.log("Device suspended. Unable to shut down");
            }
        } else {
            logger.log("Invalid handle for: " + DEV1.toString());
        }
    }
    ...
}

দেখো কতগুলো nested if-else! এখন একই কাজ exception দিয়ে করলে কেমন হয়:

Listing 7-2: DeviceController.java (exception ব্যবহার করে)
✓ ভালো 
public class DeviceController {
    ...
    public void sendShutDown() {
        try {
            tryToShutDown();
        } catch (DeviceShutDownError e) {
            logger.log(e);
        }
    }

    private void tryToShutDown() throws DeviceShutDownError {
        DeviceHandle handle = getHandle(DEV1);
        DeviceRecord record = retrieveDeviceRecord(handle);
        pauseDevice(handle);
        clearDeviceWorkQueue(handle);
        closeDevice(handle);
    }

    private DeviceHandle getHandle(DeviceID id) {
        ...
        throw new DeviceShutDownError("Invalid handle for: " + id.toString());
        ...
    }
    ...
}

লক্ষ্য করো কতো পরিষ্কার হয়ে গেছে! দুটো আলাদা বিষয় — device shutdown এর algorithm আর error handling — এখন আলাদা আলাদা জায়গায় আছে। প্রতিটোকে আলাদাভাবে বোঝা ও পরিবর্তন করা যায়।

Try-Catch-Finally আগে লেখো Write Your Try-Catch-Finally Statement First

Exception (ব্যতিক্রম) এর একটা মজার ব্যাপার হলো এটা তোমার প্রোগ্রামে একটা scope তৈরি করে। try ব্লকের কোড যেকোনো সময় abort হতে পারে এবং catch ব্লকে গিয়ে resume হতে পারে। এটাকে অনেকটা transaction (লেনদেন) এর মতো ভাবা যায় — try তে যা-ই হোক, catch কে প্রোগ্রামকে একটা consistent অবস্থায় রাখতে হবে।

তাই exception throw হতে পারে এমন কোড লেখার সময় আগে try-catch-finally structure তৈরি করো। এটা TDD (Test Driven Development) এর সাথেও ভালো মেলে — আগে একটা test লেখো যেটা exception আশা করে, তারপর কোড লেখো:

@Test(expected = StorageException.class)
public void retrieveSectionShouldThrowOnInvalidFileName() {
    sectionStore.retrieveSection("invalid - file");
}

এই test পাস করাতে আমরা ধাপে ধাপে implementation তৈরি করি। প্রথমে exception catch করি, তারপর narrow করি FileNotFoundException এ:

public List<RecordedGrip> retrieveSection(String sectionName) {
    try {
        FileInputStream stream = new FileInputStream(sectionName);
        stream.close();
    } catch (FileNotFoundException e) {
        throw new StorageException("retrieval error", e);
    }
    return new ArrayList<RecordedGrip>();
}

এখন try-catch structure তৈরি হয়ে গেছে। এর ভেতরে বাকি logic যোগ করা যাবে — এবং সেই logic লেখার সময় ধরে নেওয়া যায় কিছু ভুল হবে না, কারণ ভুল হলে catch ব্লক সামলে নেবে।

Unchecked Exception ব্যবহার করো Use Unchecked Exceptions

Java-তে checked exception মানে হলো যেসব exception method signature-এ declare করতে হয়। এটা প্রথমে ভালো আইডিয়া মনে হয়েছিল, কিন্তু বাস্তবে এটা Open/Closed Principle ভঙ্গ করে।

Open/Closed Principle

একটা class পরিবর্তনের জন্য বন্ধ কিন্তু extension এর জন্য খোলা থাকা উচিত। Checked exception এই নীতি ভাঙে কারণ একটা নিচু লেভেলের function-এ নতুন exception যোগ করলে তার উপরের সব function-এর signature পরিবর্তন করতে হয়!

ধরো, তোমার কোডে একটা function অনেক নিচের স্তরে আছে, আর catch block আছে তিন স্তর উপরে। মাঝের প্রতিটা function-এর signature-এ throws clause যোগ করতে হবে। একটা ছোট পরিবর্তনের জন্য পুরো call chain পরিবর্তন — এটা encapsulation ভাঙে।

C#, Python, Ruby — এসব ভাষায় checked exception নেই, তবুও এসব ভাষায় শক্তিশালী সফটওয়্যার তৈরি হচ্ছে। তাই সাধারণ application development-এ unchecked exception ব্যবহার করো।

Exception এর সাথে যথেষ্ট Context দাও Provide Context with Exceptions

প্রতিটা exception throw করার সময় যথেষ্ট তথ্য দাও যাতে error-এর source ও কারণ বোঝা যায়। Java-তে stack trace পাওয়া যায় ঠিকই, কিন্তু stack trace বলে না কেন অপারেশনটা ব্যর্থ হয়েছে। তাই informative error message দাও — কোন অপারেশন ব্যর্থ হয়েছে এবং কী ধরনের failure হয়েছে সেটা উল্লেখ করো।

Caller এর প্রয়োজন অনুযায়ী Exception Class তৈরি করো Define Exception Classes in Terms of a Caller's Needs

Exception classify করার অনেক উপায় আছে — source অনুযায়ী, type অনুযায়ী। কিন্তু সবচেয়ে গুরুত্বপূর্ণ হলো কীভাবে catch করো হবে সেটা মাথায় রেখে exception design করা।

নিচের কোডটা দেখো — একটা third-party library ব্যবহার করছে এবং প্রতিটা exception আলাদাভাবে handle করছে, অথচ সব ক্ষেত্রে একই কাজ করছে:

✗ খারাপ 
ACMEPort port = new ACMEPort(12);
try {
    port.open();
} catch (DeviceResponseException e) {
    reportPortError(e);
    logger.log("Device response exception", e);
} catch (ATM1212UnlockedException e) {
    reportPortError(e);
    logger.log("Unlock exception", e);
} catch (GMXError e) {
    reportPortError(e);
    logger.log("Device response exception");
} finally {
    …
}

এখানে অনেক duplication (পুনরাবৃত্তি) আছে। সমাধান হলো — API টাকে wrap করো এবং একটাই common exception type ব্যবহার করো:

✓ ভালো 
LocalPort port = new LocalPort(12);
try {
    port.open();
} catch (PortDeviceFailure e) {
    reportError(e);
    logger.log(e.getMessage(), e);
} finally {
    …
}

LocalPort class টা ACMEPort এর wrapper — সব exception ধরে একটাই PortDeviceFailure exception-এ রূপান্তর করে:

public class LocalPort {
    private ACMEPort innerPort;

    public LocalPort(int portNumber) {
        innerPort = new ACMEPort(portNumber);
    }

    public void open() {
        try {
            innerPort.open();
        } catch (DeviceResponseException e) {
            throw new PortDeviceFailure(e);
        } catch (ATM1212UnlockedException e) {
            throw new PortDeviceFailure(e);
        } catch (GMXError e) {
            throw new PortDeviceFailure(e);
        }
    }
    …
}
Third-party API Wrapping — সেরা অভ্যাস

Third-party API Wrapping (তৃতীয়-পক্ষের API মোড়ানো) একটা best practice। এর তিনটা সুবিধা: ১) তুমি ভবিষ্যতে সহজেই অন্য library-তে যেতে পারবে, ২) testing এর সময় mock করা সহজ হবে, ৩) তুমি নিজের ইচ্ছামতো API design করতে পারবে।

Normal Flow সংজ্ঞায়িত করো Define the Normal Flow

উপরের পদ্ধতিগুলো অনুসরণ করলে business logic আর error handling আলাদা হয়ে যায়। কিন্তু কখনো কখনো exception ব্যবহার করলে কোড অযথা জটিল হয়। দেখো এই উদাহরণ:

✗ অপ্রয়োজনীয় exception 
try {
    MealExpenses expenses = expenseReportDAO.getMeals(employee.getID());
    m_total += expenses.getTotal();
} catch(MealExpensesNotFound e) {
    m_total += getMealPerDiem();
}

এখানে logic হলো — খাবারের খরচ থাকলে সেটা যোগ করো, না থাকলে per diem (দৈনিক ভাতা) যোগ করো। Exception ব্যবহার না করে এটা অনেক সহজে লেখা যায়:

✓ ভালো 
MealExpenses expenses = expenseReportDAO.getMeals(employee.getID());
m_total += expenses.getTotal();

এটা সম্ভব হয় যদি expenseReportDAO সবসময় একটা MealExpense object রিটার্ন করে। খাবার খরচ না থাকলে per diem রিটার্ন করা একটা special object পাঠায়:

public class PerDiemMealExpenses implements MealExpenses {
    public int getTotal() {
        // return the per diem default
    }
}
Special Case Pattern

Special Case Pattern (বিশেষ ক্ষেত্র প্যাটার্ন) — Martin Fowler এই pattern এর নাম দিয়েছেন। এটা হলো এমন একটা class বা object তৈরি করা যেটা বিশেষ পরিস্থিতি নিজেই handle করে, ফলে client code-কে exceptional behavior নিয়ে ভাবতে হয় না।

Null রিটার্ন করো না Don't Return Null

Error handling এর আলোচনায় null রিটার্ন করা একটা বড় সমস্যা। অনেক codebase-এ প্রায় প্রতিটা লাইনে null check দেখা যায়:

✗ খারাপ 
public void registerItem(Item item) {
    if (item != null) {
        ItemRegistry registry = peristentStore.getItemRegistry();
        if (registry != null) {
            Item existing = registry.getItem(item.getID());
            if (existing.getBillingPeriod().hasRetailOwner()) {
                existing.register(item);
            }
        }
    }
}

এই কোডে persistentStore null হলে NullPointerException হবে! Null রিটার্ন করলে আমরা নিজেরাই নিজেদের জন্য সমস্যা তৈরি করছি। এর বদলে exception throw করো অথবা Special Case object রিটার্ন করো।

আরেকটা সহজ উদাহরণ দেখো:

✗ খারাপ — null চেক করতে হচ্ছে 
List<Employee> employees = getEmployees();
if (employees != null) {
    for(Employee e : employees) {
        totalPay += e.getPay();
    }
}
✓ ভালো — empty list রিটার্ন করো 
List<Employee> employees = getEmployees();
for(Employee e : employees) {
    totalPay += e.getPay();
}

Java-তে Collections.emptyList() ব্যবহার করে সহজেই empty list রিটার্ন করা যায়:

public List<Employee> getEmployees() {
    if( .. there are no employees .. )
        return Collections.emptyList();
}

Null পাস করো না Don't Pass Null

Null রিটার্ন করা খারাপ, কিন্তু method এ null আর্গুমেন্ট হিসেবে পাঠানো আরও খারাপ। এই method দেখো:

public class MetricsCalculator {
    public double xProjection(Point p1, Point p2) {
        return (p2.x – p1.x) * 1.5;
    }
}

কেউ যদি calculator.xProjection(null, new Point(12, 13)) কল করে? NullPointerException পাবে। তুমি null check যোগ করতে পারো, assert ব্যবহার করতে পারো — কিন্তু কোনোটাই ভালো সমাধান নয়। সবচেয়ে ভালো নীতি হলো: null পাস করাই নিষিদ্ধ করো। তাহলে argument list-এ null দেখলেই বুঝবে এটা bug।

উপসংহার Conclusion

Clean code পড়তে সহজ, কিন্তু সেটা robust (শক্তিশালী)ও হতে হবে। এই দুটো পরস্পরবিরোধী নয়। Error handling কে মূল logic থেকে আলাদা concern হিসেবে দেখলে, দুটোকেই আলাদাভাবে বোঝা ও উন্নত করা যায়।

★ মূল ধারণা সারসংক্ষেপ Key Concepts

★ Exception ব্যবহার করো, Return Code নয়
Error code রিটার্ন করলে কোড জটিল হয়ে যায়। Exception throw করলে মূল logic পরিষ্কার থাকে।
★ Try-Catch-Finally আগে লেখো
Exception হতে পারে এমন কোড লেখার সময় আগে try-catch structure তৈরি করো।
★ Unchecked Exception ব্যবহার করো
Checked exception কোডে অপ্রয়োজনীয় dependency তৈরি করে।
★ Null রিটার্ন করো না, Null পাস করো না
Null এর বদলে Special Case object বা empty collection ব্যবহার করো।
★ Third-party API Wrap করো
বাইরের library-র exception গুলো নিজের exception এ রূপান্তর করো। এতে dependency কমে, testing সহজ হয়, আর নিজের ইচ্ছামতো API design করা যায়।
★ Special Case Pattern
বিশেষ পরিস্থিতির জন্য আলাদা class/object তৈরি করো যা নিজেই সেই কেস handle করে, ফলে client code-কে exception নিয়ে ভাবতে হয় না।
★ Context সমৃদ্ধ Error Message
Exception throw করার সময় যথেষ্ট তথ্য দাও — কোন অপারেশন ব্যর্থ হয়েছে এবং কেন হয়েছে।
