Concurrency
Clean Code — Robert C. Martin

পরিষ্কার concurrent program লেখা অত্যন্ত কঠিন — সত্যিই অনেক কঠিন। একটি single thread-এ চলা কোড লেখা অনেক সহজ। এমনকি multithreaded কোডও উপর থেকে দেখতে ঠিকঠাক লাগতে পারে, কিন্তু গভীরে গেলে দেখা যায় তা ভেঙে পড়ে। সিস্টেমে চাপ পড়লে এই ধরনের কোড সমস্যা তৈরি করে।

এই অধ্যায়ে আমরা আলোচনা করবো কেন concurrent programming দরকার, এতে কী কী সমস্যা হয়, এবং কিভাবে পরিষ্কার concurrent কোড লেখা যায়।

কনকারেন্সি কেন দরকার? Why Concurrency?

Concurrency মূলত একটি decoupling কৌশল। এটি "কী করা হবে" (what) এবং "কখন করা হবে" (when) — এই দুটো জিনিসকে আলাদা করতে সাহায্য করে।

Single-threaded application-এ "কী" আর "কখন" এতটাই জোড়া লাগানো থাকে যে stack backtrace দেখেই পুরো application-এর অবস্থা বোঝা যায়। কিন্তু এই দুটোকে আলাদা করতে পারলে application-এর throughput এবং structure — দুটোই উন্নত করা যায়।

দাহরণ হিসেবে ভাবুন একটি Web application-এর কথা যেটা Servlet model ব্যবহার করে। প্রতিটি servlet asynchronously চলে এবং নীতিগতভাবে প্রতিটি servlet execution নিজের ছোট জগতে থাকে।

আরেকটি দাহরণ: একটি information aggregator যেটি বিভিন্ন ওয়েবসাইট থেকে তথ্য সংগ্রহ করে। Single-threaded হলে একটা শেষ না হওয়া পর্যন্ত পরেরটা শুরু হয় না। ওয়েবসাইটের সংখ্যা বাড়লে সময়ও বাড়তে থাকে। Multithreaded algorithm ব্যবহার করলে একই সময়ে একাধিক সাইট থেকে ডাটা আনা যায়।

ভুল ধারণা ও বাস্তবতা Myths and Misconceptions

Concurrency নিয়ে কিছু প্রচলিত ভুল ধারণা আছে:

ভুল ধারণা ১: "Concurrency সবসময় performance বাড়ায়।"
বাস্তবতা: শুধুমাত্র যখন যথেষ্ট wait time থাকে যা thread-এ ভাগ করা যায়, তখনই performance বাড়ে।
ভুল ধারণা ২: "Concurrent program লেখার সময় design পাল্টায় না।"
বাস্তবতা: Concurrent algorithm-এর design single-threaded design থেকে সম্পূর্ণ আলাদা হতে পারে।
ভুল ধারণা ৩: "Web container ব্যবহার করলে concurrency বোঝার দরকার নেই।"
বাস্তবতা: Container কী করছে তা বুঝতে হবে এবং concurrent update ও deadlock থেকে সাবধান থাকতে হবে।

কিছু বাস্তবসম্মত কথা:

  • • Concurrency-তে অতিরিক্ত overhead থাকে — performance-এও এবং extra কোড লেখাতেও।
  • • সঠিক concurrency জটিল, এমনকি সহজ সমস্যার ক্ষেত্রেও।
  • • Concurrency bug সাধারণত পুনরাবৃত্তিযোগ্য হয় না, তাই এগুলো প্রায়ই উপেক্ষা করা হয়।
  • • Concurrency-তে প্রায়ই design strategy-তে মৌলিক পরিবর্তন দরকার হয়।

চ্যালেঞ্জ Challenges

Concurrent programming কেন এত কঠিন? এই সাধারণ class-টি দেখুন:

সমস্যাযুক্ত কোড:
public class X {
    private int lastIdUsed;
    public int getNextId() {
        return ++lastIdUsed;
    }
}

ধরুন আমরা X-এর একটি instance তৈরি করলাম, lastIdUsed সেট করলাম 42, এবং দুটি thread-এ শেয়ার করলাম। দুটো thread-ই getNextId() call করলে তিনটি সম্ভাব্য ফলাফল হতে পারে:

  • • Thread একে পায় 43, thread দুই পায় 44, lastIdUsed হয় 44।
  • • Thread একে পায় 44, thread দুই পায় 43, lastIdUsed হয় 44।
  • • Thread একে পায় 43, thread দুই পায় 43, lastIdUsed হয় 43।

তৃতীয় ফলাফলটি চমকে দেওয়ার মতো! এটি ঘটে কারণ দুটি thread একই সময়ে একটি instruction-এ কাজ করে ফেলে। Java byte-code-এ এই একটি method-এর জন্য 12,870 টি ভিন্ন execution path সম্ভব! বেশিরভাগ path সঠিক ফলাফল দেয়, কিন্তু কিছু path দেয় না।

কনকারেন্সি রক্ষার নীতিমালা Concurrency Defense Principles

Single Responsibility Principle (SRP)

SRP বলে যে একটি method/class/component-এর পরিবর্তনের একটিমাত্র কারণ থাকা উচিত। Concurrency design এতটাই জটিল যে এটি নিজেই একটি পরিবর্তনের কারণ, তাই একে বাকি কোড থেকে আলাদা রাখা উচিত।

পরামর্শ:
আপনার concurrency-সংক্রান্ত কোড অন্য কোড থেকে আলাদা রাখুন।

Corollary: Data-র Scope সীমিত রাখুন

দুটি thread যদি একই shared object-এর একই field পরিবর্তন করে তাহলে তারা একে অপরের সাথে সংঘর্ষ করতে পারে। সমাধান হলো synchronized keyword ব্যবহার করে critical section রক্ষা করা। কিন্তু যত বেশি জায়গায় shared data update হয়:

  • • কোনো একটি জায়গা protect করতে ভুলে যাওয়ার সম্ভাবনা বাড়ে।
  • • DRY principle ভঙ্গ হয়।
  • • সমস্যার উৎস খুঁজে পাওয়া কঠিন হয়।
পরামর্শ:
Data encapsulation কে গুরুত্ব দিন; shared data-র access যথাসম্ভব সীমিত রাখুন।

Corollary: Data-র Copy ব্যবহার করুন

Shared data এড়ানোর সবচেয়ে ভালো উপায় হলো আদৌ share না করা। কিছু ক্ষেত্রে object copy করে read-only হিসেবে ব্যবহার করা যায়। Object copy করে বিভিন্ন thread-এ কাজ করিয়ে পরে একটি thread-এ merge করা যেতে পারে। Synchronization এড়ানো গেলে যে সময় বাঁচে তা সাধারণত extra object creation-এর খরচের চেয়ে বেশি।

Corollary: Thread যতটা সম্ভব স্বাধীন রাখুন

প্রতিটি thread যেন নিজের জগতে থাকে, অন্য কোনো thread-এর সাথে data share না করে — এভাবে কোড লেখার চেষ্টা করুন। যেমন HttpServlet-এর subclass-গুলো তাদের সব তথ্য doGet ও doPost method-এর parameter হিসেবে পায়, যতক্ষণ শুধু local variable ব্যবহার করা হয় ততক্ষণ synchronization সমস্যা হয় না।

পরামর্শ:
Data কে স্বাধীন subset-এ ভাগ করার চেষ্টা করুন যা স্বাধীন thread-এ চলতে পারে।

আপনার লাইব্রেরি জানুন Know Your Library

Java 5 concurrent development-এ অনেক উন্নতি এনেছিলো। Thread-safe collection ব্যবহার করুন, executor framework ব্যবহার করুন, এবং যেখানে সম্ভব nonblocking solution ব্যবহার করুন।

ConcurrentHashMap প্রায় সব পরিস্থিতিতে HashMap-এর চেয়ে ভালো perform করে। এটি একই সাথে concurrent read ও write সমর্থন করে।

আরো কিছু গুরুত্বপূর্ণ class:

  • • ReentrantLock — এমন একটি lock যা এক method-এ নেওয়া যায় এবং অন্য method-এ ছাড়া যায়।
  • • Semaphore — ক্লাসিক semaphore-এর implementation, একটি count সহ lock।
  • • CountDownLatch — নির্দিষ্ট সংখ্যক event ঘটার আগ পর্যন্ত সব thread-কে আটকে রাখে।
পরামর্শ:
java.util.concurrent, java.util.concurrent.atomic, java.util.concurrent.locks-র class-গুলোর সাথে পরিচিত হন।

Execution Model জানুন Know Your Execution Models

Concurrent application-এ আচরণ ভাগ করার বিভিন্ন উপায় আছে। কিছু মৌলিক সংজ্ঞা:

  • • Bound Resources — নির্দিষ্ট আকারের resource, যেমন database connection বা buffer।
  • • Mutual Exclusion — একই সময়ে শুধু একটি thread shared data access করতে পারবে।
  • • Starvation — একটি thread অতিরিক্ত সময় বা চিরকালের জন্য অপেক্ষায় থাকে।
  • • Deadlock — দুই বা ততোধিক thread একে অপরের জন্য অপেক্ষা করে।
  • • Livelock — Thread-গুলো কাজ করার চেষ্টা করে কিন্তু একে অপরকে "পথে" পায়।

Producer-Consumer

এক বা একাধিক producer thread কাজ তৈরি করে একটি queue-তে রাখে। এক বা একাধিক consumer thread সেই queue থেকে কাজ নিয়ে সম্পন্ন করে। Queue হলো একটি bound resource। Producer-কে queue-তে জায়গা খালি হওয়ার জন্য অপেক্ষা করতে হয় এবং consumer-কে queue-তে কিছু থাকার জন্য অপেক্ষা করতে হয়।

Readers-Writers

যখন একটি shared resource মূলত reader-দের জন্য তথ্যের উৎস হিসেবে কাজ করে, কিন্তু মাঝেমধ্যে writer দ্বারা update হয়, তখন throughput একটি সমস্যা। Reader এবং writer ভয়ের কাহিনী মেটানো এবং starvation এড়ানোর ভারসাম্য রাখাটাই চ্যালেঞ্জ।

Dining Philosophers

কল্পনা করুন কিছু দার্শনিক একটি গোল টেবিলে বসে আছেন। প্রতিটির বাঁদিকে একটি কাঁটাচামচ। মাঝখানে স্প্যাগেটির বাটি। খেতে হলে দুটি কাঁটাচামচ দরকার। পাশের জন তার কাঁটাচামচ ব্যবহার করলে অপেক্ষা করতে হবে।

দার্শনিকদের জায়গায় thread বসান এবং কাঁটাচামচের জায়গায় resource — এই সমস্যাটি অনেক enterprise application-এ দেখা যায় যেখানে process-গুলো resource-এর জন্য প্রতিযোগিতা করে।

পরামর্শ:
এই মৌলিক algorithm-গুলো শিখুন এবং এদের সমাধান বুঝুন।

Synchronized Method-এর মধ্যে Dependency থেকে সাবধান

একই shared class-এ একাধিক synchronized method থাকলে সূক্ষ্ম bug তৈরি হতে পারে।

পরামর্শ:
একটি shared object-এ একাধিক method ব্যবহার করা এড়িয়ে চলুন।

যখন একাধিক method ব্যবহার করতেই হয়, তখন তিনটি উপায় আছে:

  • • Client-Based Locking — Client প্রথম method call করার আগে server lock করবে।
  • • Server-Based Locking — Server-এর মধ্যে একটি method তৈরি করুন যা lock করে সব method call করে।
  • • Adapted Server — একটি intermediary তৈরি করুন যা locking করবে।

Synchronized সেকশন ছোট রাখুন

synchronized keyword একটি lock তৈরি করে। Lock-এ delay হয় এবং overhead যোগ হয়। তাই synchronized statement দিয়ে কোড ভরিয়ে ফেলা উচিত নয়। আবার critical section রক্ষা করাও জরুরি। কিছু programmer critical section অনেক বড় করে ফেলে, কিন্তু এতে contention বাড়ে এবং performance কমে।

পরামর্শ:
Synchronized সেকশন যতটা সম্ভব ছোট রাখুন।

সঠিক Shut-Down কোনো সহজ কাজ নয়

চিরকাল চলবে এমন system লেখা আর কিছুক্ষণ চলে gracefully shut down করবে এমন system লেখা — দুটো আলাদা ব্যাপার। সাধারণ সমস্যা হলো deadlock, যেখানে thread-গুলো এমন signal-এর জন্য অপেক্ষা করে যা কখনো আসে না।

দাহরণ: একটি parent thread কিছু child thread তৈরি করে এবং সবার শেষ হওয়ার জন্য অপেক্ষা করে। যদি কোনো child deadlocked হয়? Parent চিরকাল অপেক্ষা করবে। অথবা ধরুন দুটি child producer/consumer pair হিসেবে কাজ করছে — producer shutdown signal পেয়ে বন্ধ হয়ে গেলো কিন্তু consumer producer-এর message-এর জন্য অপেক্ষায় আটকে গেলো।

পরামর্শ:
Shut-down নিয়ে আগে ভাবুন এবং আগে কাজ করুন। এটা আপনার ধারণার চেয়ে বেশি সময় নেবে।

Threaded কোড টেস্ট করা Testing Threaded Code

কোড যে সঠিক তা প্রমাণ করা কঠিন। Testing সঠিকতার guarantee দেয় না, কিন্তু ভালো testing ঝুঁকি কমায়। Threaded কোডে জিনিসটা আরো জটিল হয়ে যায়।

পরামর্শ:
যথেষ্ট test লিখুন যা সমস্যা প্রকাশ করতে পারে এবং বিভিন্ন configuration-এ অনেকবার চালান। কোনো test fail করলে তা খুঁজে বের করুন। পরের run-এ pass করলেও ব্যর্থতাকে উপেক্ষা করবেন না।

প্রত্যাশিত ব্যর্থতাকে Threading সমস্যা হিসেবে দেখুন

Threaded কোডে এমন জিনিস fail হয় যা "fail হওয়া সম্ভব নয়।" Bug-গুলো হাজারবার বা লক্ষবার execution-এ একবার দেখা দিতে পারে। এদেরকে "one-off" বলে এড়িয়ে দেওয়া উচিত নয়।

Non-threaded কোড আগে সঠিক করুন

আগে নিশ্চিত করুন কোড thread ছাড়া কাজ করছে। POJO তৈরি করুন যা thread-aware নয় এবং threaded environment-এর বাইরে test করা যায়।

Threaded কোড Pluggable করুন

এমনভাবে লিখুন যা বিভিন্ন configuration-এ চালানো যায় — একটি thread, একাধিক thread, বিভিন্ন test double সহ।

Threaded কোড Tunable করুন

Thread-এর সংখ্যা সহজে পরিবর্তনযোগ্য রাখুন। System চলার সময়ও পরিবর্তন করা যেতে পারে — এমন ব্যবস্থা রাখুন।

Processor-এর চেয়ে বেশি Thread চালান

Task swap যত বেশি হবে, ততই critical section miss বা deadlock ধরা পড়ার সম্ভাবনা বাড়বে।

বিভিন্ন Platform-এ চালান

ভিন্ন ভিন্ন operating system-এ ভিন্ন ভিন্ন threading policy থাকে। একটি OS-এ pass করা কোড অন্যটিতে fail করতে পারে।

কোড Instrument করুন — কোডকে ব্যর্থতা খুঁজে দিন

Concurrent কোডের ত্রুটি লুকিয়ে থাকে। Object.wait(), Object.sleep(), Object.yield() এবং Object.priority()-তে call যোগ করে execution-এর ক্রম পরিবর্তন করা যায়।

হাতে করা দাহরণ:
public synchronized String nextUrlOrNull() {
    if(hasNext()) {
        String url = urlGenerator.next();
        Thread.yield(); // testing-এর জন্য যোগ করা
        updateHasNext();
        return url;
    }
    return null;
}

এর একটি automated পদ্ধতি হলো ThreadJigglePoint class ব্যবহার করা:

ThreadJigglePoint:
public class ThreadJigglePoint {
    public static void jiggle() { }
}

public synchronized String nextUrlOrNull() {
    if(hasNext()) {
        ThreadJigglePoint.jiggle();
        String url = urlGenerator.next();
        ThreadJigglePoint.jiggle();
        updateHasNext();
        ThreadJigglePoint.jiggle();
        return url;
    }
    return null;
}

ThreadJigglePoint-এর দুটি implementation রাখা যায় — production-এ কিছু করবে না, testing-এ randomly sleep, yield, বা কিছুই না করবে। এভাবে বিভিন্ন execution order তৈরি হয়ে লুকানো bug ধরা পড়তে পারে।

পরামর্শ:
Jiggling কৌশল ব্যবহার করে error খুঁজে বের করুন।

উপসংহার Conclusion

Concurrent কোড সঠিকভাবে লেখা কঠিন। প্রথমত, Single Responsibility Principle অনুসরণ করুন। System-কে POJO-তে ভেঙে ফেলুন যা thread-aware কোড থেকে আলাদা। Concurrency সমস্যার সম্ভাব্য উৎসগুলো জানুন — shared data-তে multiple thread কাজ করা, common resource pool ব্যবহার করা।

আপনার library শিখুন এবং মৌলিক algorithm বুঝুন। কোন কোড lock করা দরকার তা খুঁজে বের করুন এবং শুধু সেগুলোই lock করুন। Shared object-এর সংখ্যা এবং sharing-এর scope যতটা সম্ভব কমান।

Thread-সক্রান্ত কোড অনেক configuration-এ, অনেক platform-এ, বারবার এবং ক্রমাগত চালানো দরকার। কোড instrument করার জন্য সময় বিনিয়োগ করুন। Clean approach নিলে সফল হওয়ার সম্ভাবনা অনেক বেড়ে যায়।

ConcurrentHashMap এর মতো thread-safe collection ব্যবহার করুন।
