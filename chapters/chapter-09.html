ইউনিট টেস্ট
Unit Tests
by Robert C. Martin

গত এক দশকে আমাদের পেশা অনেক এগিয়েছে। ১৯৯৭ সালে Test Driven Development (TDD) কেউ শোনেনি। তখন unit test মানে ছিল "কোড কাজ করে কিনা দেখার জন্য লেখা ছোট্ট throwaway code।" class আর method লিখে, কিছু ad hoc কোড লিখে পরীক্ষা করা হতো — সাধারণত একটা simple driver program যেটা দিয়ে manually interact করা যেতো।

লেখক একটা ব্যক্তিগত গল্প বলেন — ১৯৯০-এর দশকে একটা embedded real-time system-এ C++ timer program লিখেছিলেন। Testing করতে keyboard-এ একটা rhythm type করে ৫ সেকেন্ড পর সেই rhythm replay হচ্ছে কিনা দেখতেন! Test শেষে সেই test code ফেলে দিতেন।

আজকের দিনে সেই কাজটাই করা হতো automated test suite দিয়ে — timing function mock করে, boolean flag ব্যবহার করে, সব test source code-এর সাথে check in করে। আমরা অনেক এগিয়েছি, কিন্তু ভালো test লেখার সূক্ষ্ম বিষয়গুলো অনেকে এখনো মিস করেন।

TDD-র তিনটি নিয়ম The Three Laws of TDD

TDD বলে production code লেখার আগে unit test লেখো। কিন্তু এটা শুধু শুরু। তিনটি সুনির্দিষ্ট নিয়ম আছে:

প্রথম নিয়ম: একটা failing unit test না লেখা পর্যন্ত production code লেখা যাবে না।First Law of TDD
দ্বিতীয় নিয়ম: Unit test এর বেশি লেখা যাবে না যতটুকু fail করার জন্য যথেষ্ট (compile না হওয়াও failing)।Second Law of TDD
তৃতীয় নিয়ম: বর্তমান failing test পাস করানোর জন্য যতটুকু production code দরকার তার বেশি লেখা যাবে না।Third Law of TDD

এই তিনটি নিয়ম তোমাকে প্রায় ৩০ সেকেন্ডের একটা cycle-এ আটকে রাখে। Test আর production code একসাথে লেখা হয়, test সবসময় কয়েক সেকেন্ড এগিয়ে থাকে। এভাবে কাজ করলে প্রতিদিন ডজন ডজন test লেখা হবে, যেগুলো প্রায় সব production code cover করবে।

Test পরিষ্কার রাখো Keeping Tests Clean

লেখক একটা টিমের কথা বলেন যেখানে সবাই ঠিক করেছিল test code production code-এর মানের হতে হবে না। "Quick and dirty" ছিল তাদের মন্ত্র — variable-র নাম ভালো না হলেও চলবে, test function ছোট না হলেও চলবে।

ফলাফল? Test code এত জটিল হয়ে গেল যে নতুন test যোগ করতে production code লেখার চেয়ে বেশি সময় লাগতো। Production code পরিবর্তন করলে পুরোনো test fail করতো, আর test code-এর mess এর কারণে সেগুলো ঠিক করা কঠিন ছিল।

শেষ পর্যন্ত পুরো test suite বাদ দিতে হলো। Test suite ছাড়া তারা কোনো পরিবর্তন করতে ভয় পেতেন — কারণ জানার উপায় ছিল না পরিবর্তন অন্য কিছু ভেঙেছে কিনা। Defect rate বাড়তে থাকলো, production code পচতে শুরু করলো।

শিক্ষা

Test code production code-এর সমান গুরুত্বপূর্ণ। এটা "দ্বিতীয় শ্রেণীর নাগরিক" নয়। এটাতেও চিন্তা, design, আর যত্ন দরকার। Test code production code-এর মতোই পরিষ্কার রাখতে হবে।

Test দেয় -ilities Tests Enable the -ilities

Test পরিষ্কার না রাখলে এক সময় test হারাবে। আর test ছাড়া production code flexible, maintainable, আর reusable রাখা অসম্ভব।

কারণ সহজ: test থাকলে কোড পরিবর্তন করতে ভয় লাগে না। Test coverage যত বেশি, ভয় তত কম। Architecture যত খারাপই হোক, test থাকলে সেটা improve করার সাহস পাওয়া যায়।

তাই automated unit test suite যেটা production code cover করে — সেটাই design ও architecture পরিষ্কার রাখার চাবি। Test পরিবর্তন সম্ভব করে, আর পরিবর্তনই সবকিছু সম্ভব করে।

Clean Tests Clean Tests

পরিষ্কার test কী? তিনটি জিনিস: Readability (পাঠযোগ্যতা), readability, আর readability! Test-এ কম expression-এ বেশি কথা বলতে হবে।

নিচের test গুলো দেখো — অনেক duplicate code, অপ্রয়োজনীয় detail, বুঝতে কষ্ট হয়:

Listing 9-1: SerializedPageResponderTest.java (refactor এর আগে)
✗ খারাপ 
public void testGetPageHieratchyAsXml() throws Exception {
    crawler.addPage(root, PathParser.parse("PageOne"));
    crawler.addPage(root, PathParser.parse("PageOne.ChildOne"));
    crawler.addPage(root, PathParser.parse("PageTwo"));

    request.setResource("root");
    request.addInput("type", "pages");
    Responder responder = new SerializedPageResponder();
    SimpleResponse response =
        (SimpleResponse) responder.makeResponse(
            new FitNesseContext(root), request);
    String xml = response.getContent();

    assertEquals("text/xml", response.getContentType());
    assertSubString("<n>PageOne</n>", xml);
    assertSubString("<n>PageTwo</n>", xml);
    assertSubString("<n>ChildOne</n>", xml);
}

PathParser call গুলো, responder তৈরির বিস্তারিত, response cast করা — এসব noise। এগুলো test-এর মূল কথা বুঝতে বাধা দেয়। এখন refactored version দেখো:

✓ ভালো

BUILD-OPERATE-CHECK Pattern

প্রতিটা test তিন ভাগে বিভক্ত: ১) Build — test data তৈরি করো, ২) Operate — সেই data-র উপর operation চালাও, ৩) Check — যাচাই করো প্রত্যাশিত ফলাফল এসেছে কিনা।

Domain-Specific Testing Language Domain-Specific Testing Language

Listing 9-2 এর test গুলো একটা গুরুত্বপূর্ণ technique দেখায় — test-এর জন্য নিজস্ব domain-specific language তৈরি করা। System manipulate করার API সরাসরি ব্যবহার না করে, helper function ও utility তৈরি করো যেগুলো test সহজে লেখা ও পড়ার উপযোগী করে।

এই testing API আগে থেকে design করা হয় না — test code refactor করতে করতে ধীরে ধীরে evolve হয়।

দ্বৈত মান Dual Standard

Test code-র engineering standard production code থেকে একটু আলাদা হতে পারে। এটা simple, succinct, আর expressive হতে হবে — কিন্তু production code-এর মতো efficient হতে হবে না। কারণ test environment আর production environment এর চাহিদা আলাদা।

এই test দেখো — temperature control system-এর জন্য:

getState() function টা দেখো:

Listing 9-6: MockControlHardware.java
public String getState() {
    String state = "";
    state += heater ? "H" : "h";
    state += blower ? "B" : "b";
    state += cooler ? "C" : "c";
    state += hiTempAlarm ? "H" : "h";
    state += loTempAlarm ? "L" : "l";
    return state;
}

এই কোড efficient নয় — StringBuffer ব্যবহার করলে ভালো হতো। কিন্তু test environment-এ এটা ঠিক আছে। Dual standard মানে: test environment-এ memory বা CPU efficiency নিয়ে ছাড় দেওয়া যায়, কিন্তু cleanliness (পরিচ্ছন্নতা) নিয়ে কখনো নয়।

প্রতি Test-এ একটি Assert One Assert per Test

একটা ধারণা আছে যে প্রতিটা test function-এ একটাই assert থাকা উচিত। Listing 9-5 এর test গুলো এর ভালো উদাহরণ — প্রতিটা test একটাই conclusion-এ আসে, দ্রুত বোঝা যায়।

কিন্তু সবসময় একটা assert-এ সীমাবদ্ধ রাখা বাস্তবসম্মত নয়। Listing 9-2 তে XML output ও specific substring দুটোই check করতে হচ্ছে। test আলাদা করা যায়, কিন্তু তাতে duplicate code বাড়ে:

Listing 9-7: SerializedPageResponderTest.java (Single Assert)
public void testGetPageHierarchyAsXml() throws Exception {
    givenPages("PageOne", "PageOne.ChildOne", "PageTwo");
    whenRequestIsIssued("root", "type:pages");
    thenResponseShouldBeXML();
}

public void testGetPageHierarchyHasRightTags() throws Exception {
    givenPages("PageOne", "PageOne.ChildOne", "PageTwo");
    whenRequestIsIssued("root", "type:pages");
    thenResponseShouldContain(
        "<n>PageOne</n>", "<n>PageTwo</n>", "<n>ChildOne</n>"
    );
}

এখানে given-when-then convention ব্যবহার করা হয়েছে। Template Method pattern বা @Before function ব্যবহার করে duplication কমানো যায়, কিন্তু এত mechanism এত ছোট বিষয়ের জন্য বাড়াবাড়ি।

সবচেয়ে ভালো নিয়ম: প্রতি concept-এ assert সংখ্যা minimize করো, এবং প্রতিটা test function একটাই concept test করো।

Single Concept per Test Single Concept per Test

একটা test function-এ একের বেশি concept test করলে পাঠক বুঝতে পারে না কোন section কেন আছে। নিচের test তিনটা আলাদা জিনিস test করছে — এটাকে তিনটা আলাদা test-এ ভাগ করা উচিত:

Listing 9-8: একাধিক concept একসাথে
✗ একাধিক concept 
public void testAddMonths() {
    SerialDate d1 = SerialDate.createInstance(31, 5, 2004);

    SerialDate d2 = SerialDate.addMonths(1, d1);
    assertEquals(30, d2.getDayOfMonth());
    assertEquals(6, d2.getMonth());
    assertEquals(2004, d2.getYYYY());

    SerialDate d3 = SerialDate.addMonths(2, d1);
    assertEquals(31, d3.getDayOfMonth());
    assertEquals(7, d3.getMonth());
    assertEquals(2004, d3.getYYYY());

    SerialDate d4 = SerialDate.addMonths(1,
        SerialDate.addMonths(1, d1));
    assertEquals(30, d4.getDayOfMonth());
    assertEquals(7, d4.getMonth());
    assertEquals(2004, d4.getYYYY());
}

এই test গুলোকে আলাদা করলে একটা সাধারণ নিয়ম বেরিয়ে আসে: মাস বাড়ালে তারিখ সেই মাসের শেষ দিনের বেশি হতে পারে না। এই নিয়ম থেকে আরও test লেখা যায় — যেমন February 28 এ এক মাস যোগ করলে March 28 হওয়া উচিত।

F.I.R.S.T. F.I.R.S.T.

Clean test পাঁচটি নিয়ম মেনে চলে যেগুলো F.I.R.S.T. নামে পরিচিত:

সংক্ষেপইংরেজিবাংলায় ব্যাখ্যা
FFastদ্রুত — Test দ্রুত চলতে হবে। ধীর হলে ঘন ঘন চালানো হবে না, সমস্যা দেরিতে ধরা পড়বে, কোড পচতে শুরু করবে।
IIndependentস্বাধীন — এক test অন্য test-এর উপর নির্ভরশীল হবে না। যেকোনো ক্রমে চালানো যাবে। একটা fail করলে বাকিগুলো cascade fail করবে না।
RRepeatableপুনরাবৃত্তিযোগ্য — যেকোনো environment-এ চলবে — production, QA, laptop, এমনকি নেটওয়ার্ক ছাড়াও।
SSelf-Validatingস্ব-যাচাইকারী — Test-এর output হবে boolean — pass অথবা fail। Log file পড়ে বা দুটো file compare করে ফলাফল বের করা যাবে না।
TTimelyসময়োপযোগী — Test production code-এর ঠিক আগে লিখতে হবে। পরে লিখলে production code test করা কঠিন হতে পারে, এবং testable ভাবে design নাও হতে পারে।

উপসংহার Conclusion

এই অধ্যায়ে test-এর শুধু উপরিভাগ স্পর্শ করা হয়েছে। Test project-এর স্বাস্থ্যের জন্য production code-এর সমান, বা তার চেয়েও বেশি গুরুত্বপূর্ণ — কারণ test production code-এর flexibility, maintainability, আর reusability রক্ষা ও বৃদ্ধি করে।

তাই test সবসময় পরিষ্কার রাখো। Expressive ও succinct করো। Testing API তৈরি করো যেটা domain-specific language হিসেবে কাজ করে।

Test পচলে কোডও পচবে। Test পরিষ্কার রাখো।

Test-এর সবচেয়ে গুরুত্বপূর্ণ গুণ হলো readability (পাঠযোগ্যতা)।
★ BUILD-OPERATE-CHECK Pattern
প্রতিটা test তিন ভাগে বিভক্ত: test data তৈরি করো (Build), operation চালাও (Operate), ফলাফল যাচাই করো (Check)।
★ Domain-Specific Testing Language তৈরি করো
Test সহজে লেখা ও পড়ার জন্য helper function ও utility তৈরি করো।
★ Dual Standard
Test code-এ efficiency-তে ছাড় দেওয়া যায়, কিন্তু cleanliness-এ কখনো নয়।
★ F.I.R.S.T. নিয়ম মানো
Fast, Independent, Repeatable, Self-Validating, Timely — এই পাঁচটি নিয়ম clean test-এর ভিত্তি।
