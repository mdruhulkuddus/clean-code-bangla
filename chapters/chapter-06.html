অবজেক্ট ও ডেটা স্ট্রাকচার
Objects and Data Structures
by Robert C. Martin

আমরা variable-কে private রাখি কারণ চাই কেউ যেন তাদের উপর নির্ভর না করে। যেকোনো সময় type বা implementation বদলানোর স্বাধীনতা রাখতে চাই। তাহলে কেন এত programmer স্বয়ংক্রিয়ভাবে getter ও setter যোগ করেন, private variable-কে কার্যত public করে ফেলেন?

Data Abstraction ডেটা বিমূর্তকরণ

নিচের দুটি উদাহরণের পার্থক্য দেখুন — দুটোই Cartesian plane-এ একটি point প্রকাশ করে:

Concrete Point — implementation উন্মুক্ত
public class Point {
    public double x;
    public double y;
}
Abstract Point — implementation লুকানো
public interface Point {
    double getX();
    double getY();
    void setCartesian(double x, double y);
    double getR();
    double getTheta();
    void setPolar(double r, double theta);
}

দ্বিতীয়টির সৌন্দর্য হলো, আপনি বুঝতে পারবেন না implementation rectangular নাকি polar coordinate-এ। হয়তো দুটোর কোনোটাই নয়! তবু interface স্পষ্টভাবে data structure প্রকাশ করে। তবে method গুলো একটি access policy enforce করে — coordinate পৃথকভাবে পড়া যায়, কিন্তু set করতে হয় একসাথে।

Implementation লুকানো মানে শুধু function-এর স্তর বসানো নয়। এটাই abstraction (বিমূর্তকরণ)! একটি class তার variable-এ getter/setter দিয়ে বাইরে ছেড়ে দেওয়া নয়, বরং abstract interface দেওয়া যা ব্যবহারকারীকে data-এর সারমর্ম নিয়ে কাজ করতে দেয়, implementation না জেনেই।

আরেকটি উদাহরণ:

Concrete — implementation প্রকাশিত
public interface Vehicle {
    double getFuelTankCapacityInGallons();
    double getGallonsOfGasoline();
}
Abstract — implementation লুকানো
public interface Vehicle {
    double getPercentFuelRemaining();
}

দ্বিতীয়টি উত্তম। Data-এর বিস্তারিত প্রকাশ না করে abstract term-এ প্রকাশ করতে হবে। শুধু interface বা getter/setter দিলেই abstraction হয় না, ভেতরে ভাবতে হবে data-কে সবচেয়ে ভালোভাবে কীভাবে represent করা যায়।

Data/Object Anti-Symmetry ডেটা/অবজেক্ট বিপরীত-প্রতিসাম্য

Object ও Data Structure-এর মধ্যে মৌলিক পার্থক্য:

Object: data লুকায় abstraction-এর পেছনে, function প্রকাশ করে যা data-এর উপর কাজ করে।

Data Structure: data প্রকাশ করে, কোনো অর্থবহ function রাখে না।

দুটো সম্পূর্ণ বিপরীত, এবং তাদের সুবিধা-অসুবিধাও প্রতিসাম্য।

Procedural approach-এ shape-এর উদাহরণ:

Procedural Approach — Data Structures
public class Square {
    public Point topLeft;
    public double side;
}
public class Rectangle {
    public Point topLeft;
    public double height;
    public double width;
}
public class Circle {
    public Point center;
    public double radius;
}
public class Geometry {
    public final double PI = 3.141592653589793;
    public double area(Object shape) throws NoSuchShapeException {
        if (shape instanceof Square) {
            Square s = (Square)shape;
            return s.side * s.side;
        } else if (shape instanceof Rectangle) {
            Rectangle r = (Rectangle)shape;
            return r.height * r.width;
        } else if (shape instanceof Circle) {
            Circle c = (Circle)shape;
            return PI * c.radius * c.radius;
        }
        throw new NoSuchShapeException();
    }
}

OO programmer-রা এটা দেখে বিরক্ত হতে পারেন। কিন্তু ভাবুন — যদি Geometry-তে perimeter() function যোগ করি, shape class গুলো কিন্তু বদলাবে না! তবে নতুন shape যোগ করলে Geometry-এর সব function বদলাতে হবে।

এবার OO approach:

OO Approach — Polymorphic
public class Square implements Shape {
    private Point topLeft;
    private double side;
    public double area() { return side * side; }
}
public class Rectangle implements Shape {
    private Point topLeft;
    private double height;
    private double width;
    public double area() { return height * width; }
}
public class Circle implements Shape {
    private Point center;
    private double radius;
    public final double PI = 3.141592653589793;
    public double area() { return PI * radius * radius; }
}

এখানে area() polymorphic। নতুন shape যোগ করলে বিদ্যমান কোনো function বদলায় না। কিন্তু নতুন function যোগ করলে সব shape class বদলাতে হবে!

মূল সত্য

Procedural code-এ নতুন function যোগ করা সহজ, বিদ্যমান data structure বদলাতে হয় না। কিন্তু নতুন data structure যোগ করা কঠিন — সব function বদলাতে হয়।
OO code-এ নতুন class যোগ করা সহজ, বিদ্যমান function বদলাতে হয় না। কিন্তু নতুন function যোগ করা কঠিন — সব class বদলাতে হয়।

অর্থাৎ, OO-তে যা কঠিন তা procedural-এ সহজ, ও procedural-এ যা কঠিন তা OO-তে সহজ! পরিণত programmer জানেন যে "সব কিছু object" ধারণাটি একটি মিথ। অনেক সময় data structure ও procedure-ই সবচেয়ে উপযুক্ত।

The Law of Demeter ডিমিটারের নিয়ম

Law of Demeter একটি সুপরিচিত নীতি যা বলে — একটি module তার সাথীদের অভ্যন্তরীণ কাজকর্ম সম্পর্কে জানবে না। Object তার internal structure accessor-এর মাধ্যমে প্রকাশ করবে না।

"বন্ধুদের সাথে কথা বলো, অপরিচিতদের সাথে নয়।"Talk to friends, not to strangers.

আরেকটু স্পষ্টভাবে: class C-এর method f শুধু এদের method call করতে পারবে:

• C নিজে
• f যে object তৈরি করে
• f-এর argument হিসেবে আসা object
• C-এর instance variable-এ থাকা object

Allowed function-এর return value-এর উপর method call করা যাবে না।

Train Wrecks

নিচের মতো chain call-কে train wreck বলে, দেখতে একের পর ওয়াগনের মতো:

Train Wreck
final String outputDir = ctxt.getOptions().getScratchDir().getAbsolutePath();

এটাকে ভাঙা ভালো:

ভাঙা হলে
Options opts = ctxt.getOptions();
File scratchDir = opts.getScratchDir();
final String outputDir = scratchDir.getAbsolutePath();

কিন্তু এটা Demeter-এর লঙ্ঘন কিনা নির্ভর করে ctxt, Options, ScratchDir object নাকি data structure তার উপর। Object হলে internal structure লুকানো উচিত — তাই এটা লঙ্ঘন। Data structure হলে তার স্বাভাবিকভাবেই internal structure প্রকাশ করে — তাই Demeter প্রযোজ্য নয়।

Hybrids (সংকর)

অনেক সময় এমন structure তৈরি হয় যা অর্ধেক object, অর্ধেক data structure — যেখানে অর্থবহ function-ও আছে, আবার public variable বা accessor/mutator-ও আছে যা private variable-কে কার্যত public করে দেয়।

এই hybrid গুলোতে নতুন function যোগ করাও কঠিন, নতুন data structure যোগ করাও কঠিন — দুই জগতের সবচেয়ে খারাপ। এড়িয়ে চলুন।

Hiding Structure (কাঠামো লুকানো)

ctxt যদি সত্যিকারের object হয়, তাহলে তার internal structure দিয়ে navigate করা উচিত হবে না। তাহলে scratch directory-এর absolute path কীভাবে পাবো? দেখা যাক, path দিয়ে আসলে কী করতে চাইছিলাম:

Path দিয়ে navigate করা
String outFile = outputDir + "/" + className.replace('.', '/') + ".class";
FileOutputStream fout = new FileOutputStream(outFile);
BufferedOutputStream bos = new BufferedOutputStream(fout);

উদ্দেশ্য হলো একটি scratch file তৈরি করা। তাহলে ctxt object-কেই এটা করতে বলি:

Object-কে কাজ বলা
BufferedOutputStream bos = ctxt.createScratchFileStream(classFileName);

এটা object-এর জন্য যুক্তিসঙ্গত আচরণ! ভেতরে ctxt তার internal তথ্য ব্যবহার করতে পারে কিন্তু বাইরে থেকে কাউকে navigate করতে হচ্ছে না, Law of Demeter লঙ্ঘনও হলো না।

Data Transfer Objects — DTO ডেটা ট্রান্সফার অবজেক্ট

Data structure-এর সবচেয়ে সাধারণ রূপ হলো একটি class যার public variable আছে কিন্তু কোনো function নেই। একে Data Transfer Object বা DTO বলে। Database-এর সাথে যোগাযোগ বা socket message parse করতে DTO অত্যন্ত কার্যকর।

এর একটি সাধারণ রূপ হলো "bean" — যেখানে private variable থাকে getter ও setter সহ:

Bean / DTO
public class Address {
    private String street;
    private String streetExtra;
    private String city;
    private String state;
    private String zip;

    public Address(String street, String streetExtra,
                   String city, String state, String zip) {
        this.street = street;
        this.streetExtra = streetExtra;
        this.city = city;
        this.state = state;
        this.zip = zip;
    }

    public String getStreet()      { return street; }
    public String getStreetExtra()  { return streetExtra; }
    public String getCity()         { return city; }
    public String getState()        { return state; }
    public String getZip()          { return zip; }
}

Bean-এর quasi-encapsulation কিছু OO purist-কে সন্তুষ্ট করে, তবে সাধারণত কোনো বাড়তি সুবিধা দেয় না।

Active Record

Active Record হলো DTO-এর বিশেষ রূপ — data structure যার public (বা bean-accessed) variable আছে, সাথে save ও find-এর মতো navigational method। সাধারণত database table-এর সরাসরি অনুবাদ।

অনেক developer এই data structure-কে object হিসেবে treat করে business rule method যোগ করেন, যা একটি hybrid তৈরি করে। সমাধান হলো Active Record-কে data structure হিসেবেই রাখুন এবং business rule-এর জন্য আলাদা object তৈরি করুন।

উপসংহার Conclusion

Object আচরণ প্রকাশ করে, data লুকায় — নতুন ধরনের object যোগ করা সহজ হয়, বিদ্যমান আচরণ বদলায় না। কিন্তু বিদ্যমান object-এ নতুন আচরণ যোগ করা কঠিন। Data structure data প্রকাশ করে, কোনো অর্থবহ আচরণ রাখে না — নতুন আচরণ যোগ করা সহজ, কিন্তু বিদ্যমান function-এ নতুন data structure যোগ করা কঠিন।

যেকোনো system-এ কখনো নতুন data type যোগ করার flexibility দরকার — সেখানে object ও OO উপযুক্ত। কখনো নতুন function যোগ করার flexibility দরকার — সেখানে procedural code ও data structure উপযুক্ত। ভালো software developer এই বিষয়টি পক্ষপাতহীনভাবে বোঝেন এবং সঠিক approach বেছে নেন।

★ মূল ধারণা সারসংক্ষেপ Key Concepts

★ Object vs Data Structure
Object আচরণ (behavior) প্রকাশ করে ও data লুকায়; Data Structure data প্রকাশ করে ও অর্থবহ আচরণ রাখে না।
★ Data Abstraction
শুধু getter/setter দেওয়া নয় — abstract interface দেওয়া যাতে ব্যবহারকারী implementation না জানলেও কাজ করতে পারে।
★ Anti-Symmetry
Procedural code-এ নতুন function সহজ, নতুন data type কঠিন; OO code-এ উল্টো। দুটোই প্রয়োজন — পরিস্থিতি বুঝে বেছে নাও।
★ Law of Demeter
"বন্ধুদের সাথে কথা বলো, অপরিচিতদের সাথে নয়" — object-এর internal structure দিয়ে navigate করো না।
★ Train Wreck এড়াও
Chain method call (a.getB().getC().getD()) এড়িয়ে চলো — object-কে কাজ বলো, তার ভেতর ঘুরে বেড়িও না।
★ Hybrid এড়াও
অর্ধেক object, অর্ধেক data structure — এটা উভয় জগতের সবচেয়ে খারাপ। DTO-কে DTO রাখো, object-কে object।
