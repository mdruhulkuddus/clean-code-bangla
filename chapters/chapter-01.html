ক্লিন কোড
Clean Code
by Robert C. Martin

আপনি এই বই পড়ছেন দুটি কারণে। প্রথমত, আপনি নিজে প্রোগ্রামার। দ্বিতীয়ত, আপনি আরো ভালো প্রোগ্রামার হতে চান। ভালো। আমাদের ভালো প্রোগ্রামার দরকার।

এই বইটি ভালো প্রোগ্রামিং সম্পর্কে। এটা আপনার code নেয়। এমনরা code লেখে পরে, নিজে পড়ে, ভেতরে ঢোকে — সব কিছু দেখে দেখেবাই। এই বই পড়লে প্রথমত আমরা ভালো code আর খারাপ code র পার্থক্য বুঝতে পারবো, ভালো code লিখতে পারবো, আর খারাপ code কে ভালো code এ রূপান্তর করতে পারবো।

কোড থাকবেই There Will Be Code

কেউ কেউ বলেন code নিজে বলে যথেষ্ট নয় সেটাই — আমাদের model আর requirement নিজে তৈরি করা উচিত। কেউ কেউ বলেন সুদূর ভবিষ্যতে সব code স্বয়ংক্রিয়ভাবে তৈরি হবে, প্রোগ্রামারদের আর দরকার হবে না।

বাজে কথা! Code যাওয়ার নয়, কারণ code হলো requirement র বিস্তারিত রূপ। যত উচ্চ-পর্যায়ের ভাষায় তৈরি হোক, সেগুলো শেষ পর্যন্ত code-ই। Requirement কে যথা সুনির্দিষ্টভাবে বলতে হবে যে মেশিন সেটা বোঝানো যায়। আর সেটাই programming, সেটাই code।

যারা মনে করেন code দিন দিন বিলুপ্ত হবে, তারা সেই কবিতাবিদদের মতো যারা আশা করেন দিন formal কবিতা লুপ্ত হবে। কোনো মেশিন তৈরি হওয়া সম্ভব নয় যা আমাদের অস্পষ্ট চাহিদা থেকে নিখুঁত প্রোগ্রাম তৈরি করবে। মানুষ তো পারে না — স্পষ্ট চাহিদা থেকে সফল সিস্টেম তৈরি করতেই!

মনে রাখুন — code হলো সেই ভাষা যেখানে আমরা শেষ পর্যন্ত requirement প্রকাশ করি। আমরা requirement র কাছাকাছি ভাষা তৈরি করতে পারি, tool তৈরি করতে পারি, কিন্তু precision যেটা বাদ দিতে পারি না। তাই code সবসময় থাকবে।

খারাপ কোড Bad Code

ভালো code যে গুরুত্বপূর্ণ, আমরা সবাই জানি। কারণ আমরা দুর্দিনের কথা সহ্য করেছি।

একটি কোম্পানির কথা ভাবুন। তারা একটি দুর্দান্ত app তৈরি করেছিল। খুব জনপ্রিয় হয়েছিল। কিন্তু তারপর release cycle দীর্ঘ হতে লাগলো, bug ঠিক হচ্ছিল না, load time বাড়তে লাগলো, crash বাড়তে লাগলো। শেষে কোম্পানি বন্ধ হয়ে গেল। কারণঃ তারা তাড়াহুড়ো করে product বাজারে নামিয়ে দিল আর code এত ভয়ঙ্কর আর্কিটেকচার তৈরি করেছিল। নতুন feature যোগ করতে গিয়ে code আরো খারাপ হতে লাগলো, যতক্ষণ না তারা সেটা আর manage করতে পারলো না। খারাপ code-ই কোম্পানিকে ধ্বংস করেছিল।

আপনি কি কখনো খারাপ code নিয়ে কাজ করেননি? জানো আমরা বলি wading — খারাপ code র মধ্য দিয়ে কষ্ট করে পথ খোঁজা, পাকানো কোপাট আর লুকানো ফাঁদের মধ্য দিয়ে গিয়ে যাওয়া।

তাহলে আপনি কেন খারাপ code লিখেছিলেন? তাড়াহুড়ো? ক্লান্ত? পরে ঠিক করবেন বলে ফেলে রেখেছিলেন? আমরা সবাই করেছি। আমরা সবাই দেখেছি আমাদের রাখা লোকমোকে program কাজ করছে বলে ভেবেছি "জানো করবে তো, পরে ঠিক করবো।" মনে রাখবেন LeBlanc র নিয়মঃ

"পরে ঠিক করবো" আসলে মানে "কোনোদিন ঠিক হবে না।"Later equals never

লোকমোকের মোট খরচ The Total Cost of Owning a Mess

আপনি যদি দুই-তিন বছরের বেশি programming করে থাকেন, তাহলে নিশ্চয়ই কারো রাখা লোকমোকে code আপনাকে ধীর করে দিয়েছে। প্রতিটি পরিবর্তন নতুন দুই-তিনটি অন্য জায়গা ভেঙে দেয়। কোনো পরিবর্তন একটু সহজ নয়। সময়ের সাথে সাথে এই আর্কিটেকচার এত বড় হয়ে যায় যে পরিষ্কার করা সম্ভব হয় না।

আর্কিটেকচার বাড়ার সাথে সাথে team র productivity (উৎপাদনশীলতা) কমতে থাকে, শূন্যের দিকে যেতে থাকে। Management তখন আরো লোক নিয়োগ করে, কিন্তু নতুন লোকেরা system র design বোঝে না। তারা design intent মোটাবে পরিবর্তন আর design ভঙ্গুরই পরিবর্তনের পথে বোঝে না। তারা আরো আর্কিটেকচার তৈরি করে, productivity আরো কমে।

আকাশে পুনর্নির্মাণ The Grand Redesign in the Sky

এই সময় team বিদ্রোহ করে — তারা management কে বলে এই code নিয়ে আর কাজ করা সম্ভব নয়, সব নতুন করে লিখতে হবে। একটি "tiger team" তৈরি হয়। তারা নতুন system তৈরি শুরু করে। কিন্তু নতুন system কে পুরোনো system র সব ফিচার রাখতে হবে, সাথে পুরোনো system এ হওয়া সব পরিবর্তনের সাথে তাল মেলাতে হবে।

এই দৌড় ১০ বছর লাগতে পারে। শেষ পর্যন্ত tiger team র আসল সদস্যরা চলে যায়, নতুন সদস্যরা দাবি করে যে নতুন system ও এখন লোকমোকে, আবার নতুন করে লিখতে হবে!

মূল কথা

Code পরিষ্কার রাখতে সময় ব্যয় করা শুধু cost-effective নয়, এটা professional survival র প্রশ্ন।

মনোভাব/দৃষ্টিভঙ্গি Attitude

কোড কেন খারাপ হয়? আমরা requirement পরিবর্তনের দোষ দিই, schedule র দোষ দিই, manager র দোষ দিই। কিন্তু আসল দোষ আমাদের — আমরা unprofessional।

Manager আর marketer রা আমাদের কাছে তথ্য চায় সিদ্ধান্ত নেওয়ার জন্যে। তারা schedule আর requirement নিয়ে চাপ দিতে পারে — সেটা তাদের কাজ। কিন্তু code রক্ষা করা আমাদের।

একটু ভাবুন — আপনি যদি doctor হতেন আর রোগী বলতো surgery র আগে হাত ধোয়া বন্ধ করতে কারণ সময় লাগছে, আপনি কি মানতেন? অবশ্যই না! কারণ doctor রোগের চেয়ে রোগ ও সংক্রমণের ঝুঁকি ভালো বোঝেন।

ঠিক তেমনি, programmer দের দিক নয় সেই manager দের কথায় লোকমোকে code করা যারা ঝুঁকি ভালো বোঝেন না।

মৌলিক ধাঁধা The Primal Conundrum

সব developer জানে পুরোনো আর্কিটেকচার তাদের ধীর করে দেয়। তবুও সবাই deadline মেটাতে গিয়ে আর্কিটেকচার তৈরি করে। কিন্তু সত্যি কথা হলো — আর্কিটেকচার তৈরি করে আপনি deadline মেটাতে পারবেন না। আর্কিটেকচার আপনাকে তাৎক্ষণিকভাবে ধীর করে দেবে।

সত্যি কথা

দ্রুত যাওয়ার একমাত্র উপায় হলো সবসময় code পরিষ্কার রাখা।

ক্লিন কোডের শিল্প The Art of Clean Code

Clean code লেখা কোনো বিদ্যা আর মতো। আমরা বেশিরভাগ মানুষই ভালো আর খারাপ চিনতে পারি, কিন্তু তাই বলে আমরা আঁকতে পারি না। Clean code চিনতে পারা আর লিখতে পারা এক নয়।

Clean code লিখতে সর্ব কোণ কোণ কৌশলের শৃঙ্খলাবদ্ধ ব্যবহার দরকার, যা একটি "পরিচ্ছন্নতার বোধ" (code-sense) থেকে আসে। কারো কারো জন্মগত, কারো কারো চেষ্টা করে অর্জন করতে হয়। এই code-sense শুধু ভালো-খারাপ চিনতেই সাহায্য করে না, বরং খারাপ code কে ভালো করার কৌশল দেখায়।

ক্লিন কোড কী? What Is Clean Code?

Clean code কী — এটা জানতে গেলে কিছু বিখ্যাত ও অভিজ্ঞ programmer দের মতামত জানতে হয়:

Bjarne Stroustrup
C++ এর স্রষ্টা
আমি চাই আমার code elegant ও efficient হোক। Logic straightforward হবে যাতে bug লুকাতে না পারে। Dependencies কম হবে। Error handling সম্পূর্ণ হবে। Performance optimal হবে। Clean code একটি কাজ ভালোভাবে করে।

Bjarne "elegant" শব্দটি ব্যবহার করেন — মানে সুন্দর, মার্জিত, ও সহজ। Clean code পড়তে আনন্দ লাগে। তিনি আরো বলেন খারাপ code আরো বেশি আর্কিটেকচার আকর্ষণ করে — ঠিক যেমন ভাঙা জানালার বাড়িতে আরো জানালা ভাঙা হয়। এটাকে বলে Broken Window Theory।

Bjarne বলেন error handling সম্পূর্ণ হতে হবে — বিস্তারিতভাবে মনোযোগ দেওয়ার শৃঙ্খলা হিসেবে। Memory leak, race condition, অসামঞ্জস্যপূর্ণ naming — সবই বিস্তারিতভাবে মনোযোগের লক্ষ্য। Clean code বিস্তারিত যত্ন নেয়। আর clean code একটি কাজ ভালোভাবে করে — খারাপ code যখন কিছু করতে চায়, তার উদ্দেশ্য অস্পষ্ট।

Grady Booch
Object Oriented Analysis এর লেখক
Clean code সরল ও সরাসরি। Clean code সুন্দরভাবে লেখা গদ্যের মতো পড়া যায়। Clean code কোনো designer এর উদ্দেশ্য ঢাকে না বরং স্পষ্ট abstraction ও সোজা control flow দিয়ে ভরা থাকে।

Grady readability র কথা বলেছেন। ভালো code পড়া ভালো পত্রিকায় পড়ার মতো — সমস্যার tensions স্পষ্ট দেখা যায়, আর সমাধান দেখে "আরে হ্যাঁ! এটা তো!" মনে হয়।

Legacy Code বিশেষজ্ঞ
Clean code দেখলে মনে হয় যে কেউ এটা লেখার সময় যত্ন নিয়েছে (cares)। উন্নতি করার জন্য চেষ্টা করলে দেখবেন লেখক আপনাকে সব ভেবে রেখেছেন — আপনি অবশেষে নিজের কাজে ফিরে আসবেন কারণ কিছু করার নতুন জায়গা নেই। প্রতিটা সিদ্ধান্ত ভেবেচিন্তে নেওয়া হয়েছে।

একটি শব্দে: care (যত্ন)। Clean code হলো সেই code যেটায় কেউ সময় নিয়ে যত্ন করেছে — সরল আর কোনোকিছু রেখেছে, বিস্তারিতভাবে মনোযোগ দিয়েছে।

Wiki ও Extreme Programming এর স্রষ্টা
যখন প্রতিটি routine পড়ে মনে হয় ঠিকই তো আমি এটাই আশা করেছিলাম, তখন বুঝবেন clean code। যখন code দেখে মনে হয় ভাষাটা এই সমস্যার জন্যই তৈরি — সেটা সুন্দর code।

Ward র কথা ভীষণ — clean code পড়লে আপনি বাক হবেন না। সব কিছু সুস্পষ্ট, সহজ, আর মনোমুগ্ধকর মনে হবে। প্রতিটি module পরেরটির জন্যে মঞ্চ প্রস্তুত করবে। প্রোগ্রামটি তাই ভালোভাবে লেখা যে আপনি সেটা লক্ষ্য করবেন না — ঠিক যেমন সত্যিকারের সুন্দর design দেখতে সহজ লাগে।

আর সুন্দর code সম্পর্কে Ward বলেন — দোষ ভাষার নয়, programmer র। সুন্দর code ভাষাকে সমস্যার জন্যে তৈরি মনে করায় — সেটা করা programmer র দায়িত্ব!

বয়স্কাউট নিয়ম The Boy Scout Rule

শুধু ভালো code লেখাই যথেষ্ট নয় — সময়ের সাথে code কে পরিষ্কার রাখতে হয়। আমরা সবাই দেখেছি সময়ের সাথে code নষ্ট হয়। তাই আমাদের সক্রিয়ভাবে এটা ঠেকাতে হবে। Boy Scouts of America র একটি সহজ নিয়ম আছে:

ক্যাম্পগ্রাউন্ড যেমন পেয়েছিলে, তার চেয়ে পরিষ্কার করে যেয়ো।

আমরা চেষ্টা করতে পারি — প্রতিবার code check-in করার আগে একটু পরিষ্কার করি। একটি variable র নাম ভালো করি, একটু বড় function ভেঙে ছোট করি, একটু duplication সরাই, একটি composite if statement পরিষ্কার করি।

কল্পনা করুন একটি project এ কাজ করতে গিয়ে দেখছেন code সময়ের সাথে উন্নতি হচ্ছে! এটা কি professional না? ক্রমাগত উন্নতি কি professionalism র একটি পরিচায়ক নয়?

★ মূল ধারণা সারসংক্ষেপ Key Concepts

★ Clean Code
এমন code যা পড়তে সহজ, বুঝতে সহজ, পরিবর্তন করতে সহজ, আর যেখানে কেউ যত্ন নিয়ে কাজ করেছে বোঝা যায়।
★ Wading
খারাপ code র মধ্য দিয়ে কষ্ট করে পথ খোঁজা।
★ LeBlanc's Law
"পরে ঠিক করবো" আসলে মানে "কোনোদিন ঠিক হবে না।"
★ Broken Window Theory
একটু খারাপ code আরো খারাপ code কে আমন্ত্রণ জানায়।
★ Boy Scout Rule
Code যেমন পেয়েছো, তার চেয়ে একটু ভালো করে রেখে যাও।
★ Productivity Trap
লোকমোকে code কমতে থাকলে productivity শূন্যের দিকে যায়, নতুন লোক নিয়োগ করে সমাধান হয় না।
★ Code-Sense
পরিচ্ছন্নতার সেই বোধ যা ভালো-খারাপ code চিনতে আর খারাপ code ঠিক করার কৌশল দেখাতে সাহায্য করে।
