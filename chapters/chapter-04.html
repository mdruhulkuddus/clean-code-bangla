অধ্যায় ৪
মন্তব্য
Comments
by Robert C. Martin
Brian W. Kernighan ও P. J. Plaugher
"খারাপ কোডে মন্তব্য লেখার বদলে কোডটাই নতুন করে লেখো।"

ভালো জায়গায় বসানো একটি comment যতটা সাহায্যকারী হতে পারে, অপ্রয়োজনীয় comment ততটাই বিশৃঙ্খলা তৈরি করে। আর পুরোনো, ভুল তথ্য বহনকারী comment? সেটা সবচেয়ে ক্ষতিকর।

Comment কোনো পবিত্র জিনিস নয়। বরং এগুলো হলো — সর্বোচ্চ — একটি "প্রয়োজনীয় মন্দ"। যদি আমাদের programming language এতটা শক্তিশালী হতো, বা আমরা ভাষাকে এতটা দক্ষতার সাথে ব্যবহার করতে পারতাম যে আমাদের উদ্দেশ্য স্পষ্টভাবে প্রকাশ পায়, তাহলে comment-এর দরকারই হতো না।

Comment-এর সঠিক ব্যবহার হলো — কোডে নিজেকে প্রকাশ করতে না পারার ক্ষতিপূরণ। লক্ষ্য করুন, আমি "ব্যর্থতা" শব্দটি ব্যবহার করেছি, এবং ইচ্ছাকৃতভাবেই করেছি। প্রতিবার যখন আপনি কোডের মাধ্যমে নিজেকে প্রকাশ করতে পারেন, সেটা উদযাপন করুন। প্রতিবার যখন comment লিখতে হয়, সেটাকে নিজের প্রকাশক্ষমতার ব্যর্থতা হিসেবে দেখুন।

Comment কেন সমস্যাজনক? কারণ এগুলো মিথ্যা বলে। সবসময় নয়, ইচ্ছাকৃতভাবেও নয়, তবে অনেক সময়ই। একটি comment যত পুরোনো হয়, আর যে কোড বর্ণনা করছে তার থেকে যত দূরে সরে যায়, সেটি ভুল হওয়ার সম্ভাবনা ততই বাড়ে। কারণটা সহজ — programmer-রা বাস্তবিকভাবে comment গুলো maintain করতে পারে না।

কোড বদলায়, বিবর্তিত হয়। কোডের অংশ এদিক সেদিক সরে। টুকরো টুকরো হয়ে সরে যায়। কিন্তু comment সবসময় তাদের সাথে চলে না, চলতেও পারে না। অনেক সময়ই comment কোড থেকে বিচ্ছিন্ন হয়ে যায়, এবং ক্রমশ ভুল হতে থাকে। কারণটা সহজ — programmer-রা বাস্তবিকভাবে comment গুলো maintain করতে পারে না।

Comment খারাপ কোডের ক্ষতিপূরণ করে না Comments Do Not Make Up for Bad Code

Comment লেখার সবচেয়ে সাধারণ কারণ হলো খারাপ কোড। কেউ কোনো module লিখলো, বুঝতে পারলো সেটা অগোছালো। তখন সে ভাবলো, "হ্যাঁ, ভালো হবে যদি comment দিয়ে দিই।" না! বরং কোডটাকে পরিষ্কার করো!

পরিষ্কার আর প্রকাশক্ষম কোড, যেখানে অল্প comment আছে, অনেক বেশি ভালো — সেই জটিল আর অগোছালো কোডের চেয়ে যেখানে প্রচুর comment দিয়ে আরও ঘোলাটে করা হয়েছে।

কোড দিয়ে নিজেকে ব্যাখ্যা করো Explain Yourself in Code

অনেকে মনে করেন কোড ব্যাখ্যা করার ভালো মাধ্যম নয়, যা ভুল। কিন্তু অনেক programmer-ই মনে করেন কোড দিয়ে সব বোঝানো যায় না, যা সম্পূর্ণ ভুল। কোনটা ভালো দেখুন:

Comment দিয়ে ব্যাখ্যা
// Check to see if the employee
// is eligible for full benefits
if ((employee.flags & HOURLY_FLAG) &&
    (employee.age > 65))
কোড দিয়ে ব্যাখ্যা
if (employee.isEligibleForFullBenefits())

বেশিরভাগ ক্ষেত্রেই শুধু একটু ভেবে দেখলেই কোডের মাধ্যমেই উদ্দেশ্য ব্যাখ্যা করা যায়। অনেক সময়ই শুধু একটি function তৈরি করলেই হয় যা সেই comment-এর কাজ করে।

ভালো মন্তব্য Good Comments

কিছু comment অপ্রয়োজনীয় নয়। তবে মনে রাখতে হবে, সত্যিকার ভালো comment হলো সেটা যা আপনি লেখার উপায় খুঁজে পাননি — অর্থাৎ যেটা কোড দিয়ে বলা সম্ভব নয়।

Legal Comments (আইনগত মন্তব্য)

অনেক সময় corporate coding standard অনুযায়ী আইনগত কারণে comment দিতে হয়। যেমন copyright ও authorship statement, প্রতিটি source file-এর শুরুতে দেওয়া যুক্তিসঙ্গত:

Legal Comment
// Copyright (C) 2003,2004,2005 by Object Mentor, Inc. All rights reserved.
// Released under the terms of the GNU General Public License version 2 or later.

তবে এই ধরনের comment-এ সম্পূর্ণ terms ও conditions না দিয়ে শুধু standard license বা external document-এর reference দেওয়া ভালো।

Informative Comments (তথ্যমূলক মন্তব্য)

অনেক সময় কোনো comment দিয়ে basic information জানানো যেতে পারে। যেমন কোনো abstract method-এর return value ব্যাখ্যা করা:

Informative Comment
// Returns an instance of the Responder being tested.
protected abstract Responder responderInstance();

তবে অনেক সময় function-এর নাম দিয়েই তথ্য জানানো সম্ভব। যেমন function-এর নাম responderBeingTested রাখলে comment-এর দরকার হতো না।

Explanation of Intent (উদ্দেশ্যের ব্যাখ্যা)

অনেক সময় comment শুধু implementation-এর তথ্য জানায় না, বরং সিদ্ধান্তের পেছনে intent (উদ্দেশ্য) ব্যাখ্যা করে। নিচের ক্ষেত্রে author সিদ্ধান্ত নিয়েছেন তাঁর class-এর object অন্য কোনো object-এর চেয়ে "বড়" হিসেবে sort হবে:

Intent Comment
public int compareTo(Object o)
{
    if(o instanceof WikiPagePath)
    {
        WikiPagePath p = (WikiPagePath) o;
        String compressedName = StringUtil.join(names, "");
        String compressedArgumentName = StringUtil.join(p.names, "");
        return compressedName.compareTo(compressedArgumentName);
    }
    return 1; // we are greater because we are the right type.
}

Clarification (স্পষ্টীকরণ)

যখন কোনো obscure argument বা return value-এর অর্থ সাধারণভাবে বোঝানো কঠিন, তখন clarifying comment সাহায্যকারী হতে পারে, বিশেষত যখন সেই কোড পরিবর্তন করার অধিকার আপনার নেই (যেমন standard library):

Clarifying Comments
assertTrue(a.compareTo(a) == 0);  // a == a
assertTrue(a.compareTo(b) != 0);  // a != b
assertTrue(a.compareTo(b) == -1); // a < b
assertTrue(b.compareTo(a) == 1);  // b > a

তবে মনে রাখবেন, clarifying comment সঠিক হওয়ার ঝুঁকি আছে।

Warning of Consequences (পরিণামের সতর্কতা)

অন্য programmer-দের কোনো পরিণামের বিষয়ে সতর্ক করতে comment কাজে আসে:

Warning Comment
//SimpleDateFormat is not thread safe,
//so we need to create each instance independently.
SimpleDateFormat df = new SimpleDateFormat("EEE, dd MMM yyyy HH:mm:ss z");
df.setTimeZone(TimeZone.getTimeZone("GMT"));
return df;

TODO Comments

TODO comment রাখা হলো "এখনই করতে পারছি না কিন্তু ভবিষ্যতে করা দরকার" এই মনোভাবের প্রকাশ। এগুলো যুক্তিসঙ্গত হতে পারে, যেমন কোনো deprecated feature সরানোর reminder, বা ভবিষ্যতে কিছু করতে হবে তার স্মৃতিচিহ্ন। তবে TODO কোনো খারাপ কোড রেখে দেওয়ার অজুহাত নয়। নিয়মিত scan করে অপ্রয়োজনীয় TODO সরিয়ে ফেলুন।

Amplification (গুরুত্ব বৃদ্ধি)

কোনো বিষয় যা দেখতে গুরুত্বহীন মনে হতে পারে, তার গুরুত্ব তুলে ধরতে comment ব্যবহার করা যায়:

Amplification Comment
String listItemContent = match.group(3).trim();
// the trim is real important. It removes the starting
// spaces that could cause the item to be recognized
// as another list.
new ListItemWidget(this, listItemContent, this.level + 1);
return buildList(text.substring(match.end()));

Javadocs in Public APIs

আপনি যদি public API লিখেন, তাহলে ভালো javadoc লেখা অত্যন্ত গুরুত্বপূর্ণ। Standard Java library-এর javadoc এর দারুণ উদাহরণ। তবে মনে রাখতে হবে, javadoc-ও অন্য comment-এর মতোই misleading ও dishonest হতে পারে।

খারাপ মন্তব্য Bad Comments

বেশিরভাগ comment এই category-তে পড়ে। সাধারণত এগুলো খারাপ কোডের ঢাল, অজুহাত, বা programmer-এর নিজের মনের সাথে আলাপ ছাড়া কিছু নয়।

Mumbling (বিড়বিড়ানো)

শুধু "দিতে হবে বলে" comment দেওয়া একটি hack। যদি comment লিখতেই হয়, সেখানে যথেষ্ট সময় দেওয়া উচিত। নিচের উদাহরণ দেখুন:

Mumbling Comment
public void loadProperties()
{
    try
    {
        String propertiesPath = propertiesLocation + "/" + PROPERTIES_FILE;
        FileInputStream propertiesStream = new FileInputStream(propertiesPath);
        loadedProperties.load(propertiesStream);
    }
    catch(IOException e)
    {
        // No properties files means all defaults are loaded
    }
}

catch block-এর comment-টি কী বোঝায়? properties file না পেলে default load হয়? কিন্তু কে load করে? কখন করে? comment পড়ে আরও বিভ্রান্তি তৈরি হয়। যে comment বুঝতে অন্য module-ও দেখতে হয়, সেই comment কোনো কাজে আসে না।

Redundant Comments (অপ্রয়োজনীয় পুনরাবৃত্তি)

এমন comment যা কোডের চেয়ে বেশি তথ্যপূর্ণ নয়, যা পড়তে কোডের চেয়ে বেশি সময় লাগে, সেটা redundant:

Redundant Comment
// Utility method that returns when this.closed is true. Throws an exception
// if the timeout is reached.
public synchronized void waitForClose(final long timeoutMillis) throws Exception
{
    if(!closed)
    {
        wait(timeoutMillis);
        if(!closed)
            throw new Exception("MockResponseSender could not be closed");
    }
}

এই comment কোডের চেয়ে precise না। এটা যেন used-car salesman-এর প্রতিশ্রুতি — যেমন hood-এর নিচে দেখার দরকার নেই!

Misleading Comments (বিভ্রান্তিকর মন্তব্য)

উপরের ক্ষেত্রেই দেখুন একটি সূক্ষ্ম ভুল আছে। Comment বলছে method "return করে যখন this.closed true হয়"। কিন্তু আসলে method return করে না — যদি this.closed সঠিক সময়ের মধ্যে true না হলে timeout পর্যন্ত wait করে exception throw করে।

এই সূক্ষ্ম ভুল তথ্য অন্য programmer-কে debugging-এ অনেক সময় নষ্ট করাতে পারে।

Mandated Comments (বাধ্যতামূলক মন্তব্য)

"প্রতিটি function-এ javadoc থাকতেই হবে" বা "প্রতিটি variable-এ comment থাকতেই হবে" — এই ধরনের নিয়ম অযৌক্তিক। এগুলো কোডকে শুধু বিশৃঙ্খল করে:

Journal Comments (দিনলিপি মন্তব্য)

কিছু programmer module-এর শুরুতে প্রতিটি পরিবর্তনের log রাখতেন। একসময় এটা যুক্তিসঙ্গত ছিল, কিন্তু এখন source code control system আছে। এগুলো শুধু module-কে অপরিষ্কার করে। সম্পূর্ণ সরিয়ে ফেলুন।

Noise Comments (শব্দদূষণ মন্তব্য)

এমন comment যা শুধু সুস্পষ্ট বিষয় পুনরায় বলে, কোনো নতুন তথ্য দেয় না:

Noise Comments
/** Default constructor. */
protected AnnualDateRule() {
}

/** The day of the month. */
private int dayOfMonth;

এই ধরনের comment এত "noisy" যে এক সময় আমরা এগুলো ignore করতে শিখে যাই। ফলে যদি তাদের মধ্যে কখনো সত্যিকার ভালো তথ্য থাকে, সেটাও চোখে পড়ে না।

Comment-এর বদলে Function বা Variable ব্যবহার করো

Position Markers (অবস্থান চিহ্নিতকারী)

// Actions ////////////////////////////////// — এই ধরনের banner খুবই কম ব্যবহার করুন। অতিরিক্ত ব্যবহারে এগুলো background noise হয়ে যায় এবং ignore করা হয়।

Closing Brace Comments (বন্ধনী বন্ধ করার মন্তব্য)

দীর্ঘ function-এ closing brace-এ } //while বা } //try লেখা — এটা করার বদলে function ছোট করুন।

Commented-Out Code (মন্তব্য করা কোড)

⚠️ গুরুত্বপূর্ণ: কোড comment-out করে রাখা অত্যন্ত খারাপ অভ্যাস। এটা করবেন না!

অন্যরা commented-out code দেখে মুছতে সাহস পায় না — ভাবে "নিশ্চয়ই কোনো কারণে রাখা হয়েছে"। ফলে এগুলো বোতলের তলানির মতো জমতে থাকে। আমাদের source code control system আছে — কোড মুছে ফেলুন। হারাবে না, প্রতিশ্রুতি!

HTML Comments

Source code comment-এ HTML ব্যবহার করা জঘন্য। Editor/IDE-তে যেখানে comment সহজে পড়ার কথা, সেখানে HTML tag comment-কে দুর্বোধ্য করে তোলে। HTML যোগ করা tool-এর দায়িত্ব, programmer-এর নয়।

Nonlocal Information (অ-স্থানীয় তথ্য)

Comment যদি লিখতেই হয়, সেটা যেন কাছের কোড সম্পর্কে হয়। দূরবর্তী কোনো system-এর তথ্য local comment-এ দেওয়া ঠিক নয় — কারণ সেই দূরবর্তী কোড বদলালে এই comment কেউ আপডেট করবে না।

Too Much Information (অতিরিক্ত তথ্য)

Comment-এ ইতিহাস, প্রাসঙ্গিক বিস্তারিত আলোচনা বা বিবরণ দেবেন না। পড়তে যতটুকু দরকার, ততটুকু রাখুন।

Inobvious Connection (অস্পষ্ট সম্পর্ক)

Comment ও কোডের মধ্যে সম্পর্ক সুস্পষ্ট হওয়া উচিত। যদি comment নিজেই ব্যাখ্যা দরকার করে, তাহলে সেটা ব্যর্থ:

Inobvious Connection
/*
 * start with an array that is big enough to hold all the pixels
 * (plus filter bytes), and an extra 200 bytes for header info
 */
this.pngBytes = new byte[((this.width + 1) * this.height * 3) + 200];

"filter bytes" কী? +1-এর সাথে সম্পর্ক কী? 200 কেন? Comment নিজেই ব্যাখ্যা করতে পারছে না!

Function Headers

ছোট function-এর জন্য বেশি বর্ণনা লাগে না। একটি ভালো নামের ছোট function, যেটা শুধু একটি কাজই করে, সেটা comment header-এর চেয়ে অনেক ভালো।

Nonpublic Code-এ Javadocs

Public API-তে javadoc দরকারী। কিন্তু internal code-এ javadoc page তৈরি করা সাধারণত অপ্রয়োজনীয়, শুধু অতিরিক্ত formality বা cruft তৈরি করে যা distraction সৃষ্টি করে।

★ মূল ধারণা সারসংক্ষেপ Key Concepts

★ Comment = ব্যর্থতার স্বীকৃতি
Comment হলো কোডে আমাদের ব্যর্থতার স্বীকৃতি — কোড নিজেই যথেষ্ট পরিষ্কার হলে comment লাগে না।
★ পুরোনো Comment সবচেয়ে ক্ষতিকর
পুরোনো ও ভুল comment কোনো comment না থাকার চেয়ে বেশি ক্ষতিকর — কারণ এগুলো মিথ্যা তথ্য ছড়ায়।
★ ভালো Comment-এর ধরন
Legal, TODO, intent ব্যাখ্যা, warning, clarification — কিন্তু বেশিরভাগ comment-ই অপ্রয়োজনীয়।
★ কোড দিয়ে বলো
Comment লেখার আগে ভাবো — কোড দিয়েই কি একই কথা বলা যায়? Function বা variable-এর নাম দিয়ে comment-এর প্রয়োজন দূর করো।
★ Commented-out Code রাখো না
Source control সব মনে রাখে — কোড comment-out করে রাখা অত্যন্ত খারাপ অভ্যাস। মুছে ফেলো।
★ Redundant ও Misleading
কোডের চেয়ে কম তথ্য দেয় বা ভুল তথ্য দেয় — এমন comment সবচেয়ে বিপজ্জনক।
