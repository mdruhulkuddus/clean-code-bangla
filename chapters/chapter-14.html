Successive Refinement
Clean Code — Robert C. Martin

এই অধ্যায়টি একটি case study — command-line argument parser-এর। এখানে দেখানো হয়েছে কিভাবে একটি module প্রথমে ভালো শুরু হলো কিন্তু বড় হতে গিয়ে সমস্যায় পড়লো, এবং তারপর কিভাবে সেটিকে refactor ও পরিষ্কার করা হলো।

লেখক নিজের তৈরি একটি argument parser-এর কথা বলছেন যার নাম Args। এটি খুব সহজে ব্যবহার করা যায়:

✓ Args-এর ব্যবহার:
public static void main(String[] args) {
    try {
        Args arg = new Args("l,p#,d*", args);
        boolean logging = arg.getBoolean('l');
        int port = arg.getInt('p');
        String directory = arg.getString('d');
        executeApplication(logging, port, directory);
    } catch (ArgsException e) {
        System.out.printf("Argument error: %s\n", e.errorMessage());
    }
}

এখানে "l,p#,d*" হলো schema string। l হলো boolean argument, p# হলো integer argument, এবং d* হলো string argument। Constructor-এ কোনো ArgsException না আসলে মানে command-line সফলভাবে parse হয়েছে।

Args-এর Implementation Args Implementation

চূড়ান্ত পরিষ্কার version-এ Args class এভাবে সাজানো হয়েছে:

✓ পরিষ্কার Args class:
public class Args {
    private Map<Character, ArgumentMarshaler> marshalers;
    private Set<Character> argsFound;
    private ListIterator<String> currentArgument;

    public Args(String schema, String[] args) throws ArgsException {
        marshalers = new HashMap<Character, ArgumentMarshaler>();
        argsFound = new HashSet<Character>();
        parseSchema(schema);
        parseArgumentStrings(Arrays.asList(args));
    }

    private void parseSchema(String schema) throws ArgsException {
        for (String element : schema.split(","))
            if (element.length() > 0)
                parseSchemaElement(element.trim());
    }

    private void parseSchemaElement(String element) throws ArgsException {
        char elementId = element.charAt(0);
        String elementTail = element.substring(1);
        validateSchemaElementId(elementId);
        if (elementTail.length() == 0)
            marshalers.put(elementId, new BooleanArgumentMarshaler());
        else if (elementTail.equals("*"))
            marshalers.put(elementId, new StringArgumentMarshaler());
        else if (elementTail.equals("#"))
            marshalers.put(elementId, new IntegerArgumentMarshaler());
        else if (elementTail.equals("##"))
            marshalers.put(elementId, new DoubleArgumentMarshaler());
        else if (elementTail.equals("[*]"))
            marshalers.put(elementId, new StringArrayArgumentMarshaler());
        else
            throw new ArgsException(INVALID_ARGUMENT_FORMAT,
                elementId, elementTail);
    }
    // ... বাকি method-গুলো
}

লক্ষ্য করুন — এই কোড ওপর থেকে নিচে পড়া যায়, কোথাও বেশি লাফ দিতে হয় না।

ArgumentMarshaler হলো একটি interface:

ArgumentMarshaler interface:
public interface ArgumentMarshaler {
    void set(Iterator<String> currentArgument) throws ArgsException;
}

প্রতিটি argument type-এর জন্য আলাদা implementation আছে:

Boolean ও String Marshaler:
public class BooleanArgumentMarshaler implements ArgumentMarshaler {
    private boolean booleanValue = false;
    public void set(Iterator<String> currentArgument) throws ArgsException {
        booleanValue = true;
    }
    public static boolean getValue(ArgumentMarshaler am) {
        if (am != null && am instanceof BooleanArgumentMarshaler)
            return ((BooleanArgumentMarshaler) am).booleanValue;
        else return false;
    }
}

public class StringArgumentMarshaler implements ArgumentMarshaler {
    private String stringValue = "";
    public void set(Iterator<String> currentArgument) throws ArgsException {
        try {
            stringValue = currentArgument.next();
        } catch (NoSuchElementException e) {
            throw new ArgsException(MISSING_STRING);
        }
    }
    public static String getValue(ArgumentMarshaler am) {
        if (am != null && am instanceof StringArgumentMarshaler)
            return ((StringArgumentMarshaler) am).stringValue;
        else return "";
    }
}

এটা কিভাবে করলাম? How Did I Do This?

লেখক বলেন — তিনি এই program শুরু থেকে শেষ পর্যন্ত এই পরিষ্কার রূপে লেখেননি। তিনি আমাদের কাউকে এটা আশা করেন না। কয়েক দশকে আমরা যা শিখেছি তা হলো — programming বিজ্ঞানের চেয়ে বেশিটাই শিল্প (craft)।

পরিষ্কার কোড লিখতে হলে আগে "dirty" কোড লিখতে হবে, তারপর সেটা পরিষ্কার করতে হবে। এটা ঠিক যেমন প্রবন্ধ লেখার সময় হয় — প্রথমে rough draft, তারপর দ্বিতীয় draft, তারপর আরো কয়েকটি draft, এবং সবশেষে চূড়ান্ত version। পরিষ্কার কোড লেখার ব্যাপারটা হলো ধাপে ধাপে উন্নতি (successive refinement) এর ব্যাপার।

বেশিরভাগ নতুন programmer (এবং প্রবন্ধ লেখার ছাত্রদের মতো) এই পরামর্শ মানে না। তারা মনে করে প্রাথমিক লক্ষ্য হলো program কাজ করানো। একবার "কাজ করলে" তারা পরের কাজে চলে যায়, "কাজ করা" program-কে যে অবস্থায় আছে সেই অবস্থায় রেখে দেয়। অভিজ্ঞ programmer জানেন এটা পেশাদার আত্মহত্যা।

Args: প্রাথমিক সংস্করণ The Rough Draft

প্রথম version-টি কাজ করতো — কিন্তু ছিলো এলোমেলো। সব argument type-এর জন্য আলাদা HashMap ছিলো, parsing logic ছিলো জটিল এবং এক জায়গায় জড়ো করা:

✗ প্রাথমিক এলোমেলো version:
public class Args {
    private String schema;
    private String[] args;
    private boolean valid = true;
    private Set<Character> unexpectedArguments = new TreeSet<Character>();
    private Map<Character, Boolean> booleanArgs =
        new HashMap<Character, Boolean>();
    private Map<Character, String> stringArgs =
        new HashMap<Character, String>();
    private Map<Character, Integer> intArgs =
        new HashMap<Character, Integer>();
    private Set<Character> argsFound = new HashSet<Character>();
    private int currentArgument;
    private char errorArgumentId = '\0';
    private String errorParameter = "TILT";
    private ErrorCode errorCode = ErrorCode.OK;
    private enum ErrorCode {

        INVALID_INTEGER, UNEXPECTED_ARGUMENT}
    // ... বিশাল জটিল কোড
}

Boolean এবং String argument যোগ করার পর ঠিকাকই ছিলো। কিন্তু Integer argument যোগ করতে গিয়ে অনেক জায়গায় কোড duplicate হতে শুরু করলো। প্রতিটি নতুন argument type-এর জন্য তিনটি জায়গায় কোড যোগ করতে হতো: schema parsing, command-line parsing, এবং getXXX method।

তাই আমি থামলাম So I Stopped

আরো দুটি argument type যোগ করা বাকি ছিলো, এবং লেখক বুঝতে পারলেন সেগুলো জিনিসটাকে আরো খারাপ করবে। জোর করে এগিয়ে গেলে হয়তো কাজ করানো যেতো, কিন্তু পেছনে রেখে যেতো এমন একটি গোলমাল যা ঠিক করা সম্ভব নয়।

তাই তিনি feature যোগ করা বন্ধ করে refactoring শুরু করলেন। অনেক ধরনের type, সবার একই রকম method — এটা শুনতে একটি class-এর মতো লাগে। এভাবেই ArgumentMarshaler-এর ধারণা জন্ম নিলো।

ধাপে ধাপে এগিয়ে যাওয়া On Incrementalism

Program নষ্ট করার সবচেয়ে ভালো উপায় হলো "উন্নতির" নামে এর structure-এ বিশাল পরিবর্তন করা। কিছু program এই "উন্নতি" থেকে আর সুস্থ হয় না। সমস্যা হলো "উন্নতি"-র পর program-কে আগের মতো কাজ করানো অনেক কঠিন।

এটা এড়াতে লেখক Test-Driven Development (TDD)-এর শৃঙ্খলা ব্যবহার করেন। TDD-এর একটি মূল নীতি হলো — system-কে সবসময় চালু রাখা। প্রতিটি পরিবর্তন এমন হতে হবে যা system ভাঙে না। এর জন্য দরকার automated test suite যা যেকোনো সময় চালানো যায়। Args class-এর জন্য unit test (JUnit-এ) এবং acceptance test (FitNesse-এ) তৈরি করা ছিলো।

তারপর তিনি অনেক অনেক ছোট ছোট পরিবর্তন করেন। প্রতিটি পরিবর্তন system-কে ArgumentMarshaler ধারণার দিকে নিয়ে যায়, এবং প্রতিটি পরিবর্তনের পরও system কাজ করতে থাকে।

প্রথম পরিবর্তন — ArgumentMarshaler-এর কঙ্কাল যোগ করা:

প্রাথমিক কঙ্কাল:
private class ArgumentMarshaler {
    private boolean booleanValue = false;
    public void setBoolean(boolean value) { booleanValue = value; }
    public boolean getBoolean() { return booleanValue; }
}

private class BooleanArgumentMarshaler extends ArgumentMarshaler { }
private class StringArgumentMarshaler extends ArgumentMarshaler { }
private class IntegerArgumentMarshaler extends ArgumentMarshaler { }

এটা কিছু ভাঙে না। তারপর Boolean argument-এর HashMap পরিবর্তন করা হলো ArgumentMarshaler নিতে। এতে কিছু statement ভেঙেছিলো, যা দ্রুত ঠিক করা হলো।

ছোট পরিবর্তনে test fail করলে সাথে সাথে ঠিক করা হতো। এভাবে ধীরে ধীরে — একটি type-এর parse, set, get আলাদা Marshaler-এ সরানো হলো। Boolean-এর পর String, তারপর Integer — প্রতিটি ধাপে test pass করাতে করাতে।

এই পুরো প্রক্রিয়ায় HashMap-গুলো একটি একটি করে সরানো হলো, error handling উন্নত করা হলো, এবং সবশেষে সব ArgumentMarshaler তাদের নিজস্ব file-এ চলে গেলো। ArgsException class-ও আলাদা করা হলো error message formatting সহ।

ভালো software design-এর অনেকটাই হলো partitioning — বিভিন্ন ধরনের কোডের জন্য যথার্থ জায়গা তৈরি করা। এই separation of concerns কোডকে বুঝতে ও রক্ষণাবেক্ষণ করতে অনেক সহজ করে তোলে।

উপসংহার Conclusion

কোড শুধু কাজ করলেই যথেষ্ট নয়। যে কোড কাজ করে সেটাও প্রায়ই ভয়করভাবে ভাঙা। যে programmer "শুধু কাজ করে" — এটা নিয়ে সন্তুষ্ট, তিনি unprofessionally আচরণ করেন।

খারাপ কোড পচে এবং কাঁজিয়ে ওঠে, একটি নিবাড় ভার হয়ে team-কে টেনে ধরে। খারাপ schedule আবার করা যায়, খারাপ requirement পুনঃসংজ্ঞায়িত করা যায়, খারাপ team dynamics মেরামত করা যায়। কিন্তু খারাপ কোড পচায় আর team-র ভার বিশ্বের কিছুই নিরাময় করে না।

খারাপ কোড পরিষ্কার করা যায়, কিন্তু এটা অনেক ব্যয়বহুল। সকালে কোনো module-এ গোলমাল করলে বিকেলে পরিষ্কার করা সহজ। পাঁচ মিনিট আগে গোলমাল করলে এখনই পরিষ্কার করা আরো সহজ।

সমাধান হলো — ক্রমাগত আপনার কোড যতটা সম্ভব পরিষ্কার ও সহজ রাখুন। কখনো শুরু হতে দেবেন না।

★ মূল ধারণা সারসংক্ষেপ Key Concepts

★ Successive Refinement
প্রথমে একটি কাজ করা version লেখো, তারপর ধাপে ধাপে সেটোকে পরিষ্কার করো।
★ Dirty First, Then Clean
পরিষ্কার কোড প্রথম চেষ্টায় হয় না — প্রথমে "dirty" কোড লিখতে হয়, তারপর পরিষ্কার করতে হয়।
★ Incrementalism
বড় পরিবর্তন একবারে না করে, অনেক ছোট ছোট পরিবর্তনের মাধ্যমে এগিয়ে যাওয়া।
★ TDD
Test-Driven Development ব্যবহার করে প্রতিটি ছোট পরিবর্তনের পর system কাজ করছে কিনা যাচাই করা।
★ ArgumentMarshaler Pattern
একই ধরনের কাজ বারবার করতে হলে সেটা একটি class-এ পরিণত করার কথা ভাবুন।
★ কোড শুধু "কাজ করলেই" যথেষ্ট নয়
Structure ও design-ও গুরুত্বপূর্ণ। খারাপ কোড team-কে ধ্বংস করে।
