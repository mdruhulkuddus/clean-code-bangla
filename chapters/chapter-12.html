Emergence
by Robert C. Martin

Kent Beck-এর Simple Design-এর চারটি নিয়ম মেনে চললে ভালো design আপনাআপনি তৈরি হয় (emerge করে)। নিয়মগুলো গুরুত্বের ক্রমে: (১) সব টেস্ট চালাও, (২) Duplication দূর করো, (৩) Programmer-এর উদ্দেশ্য প্রকাশ করো, (৪) ক্লাস ও মেথডের সংখ্যা কমাও।

Emergent Design-এ পরিচ্ছন্নতা অর্জন Getting Clean via Emergent Design

কল্পনা করুন — চারটি সহজ নিয়ম মেনে চললেই ভালো design তৈরি হয়। এই নিয়মগুলো মানলে SRP, DIP ইত্যাদি principle-ও স্বাভাবিকভাবে প্রয়োগ হয়ে যায়। Kent Beck-এর Simple Design-এর চারটি নিয়ম:

Simple Design-এর চারটি নিয়ম (গুরুত্বের ক্রমে)
১. সব টেস্ট সফলভাবে চলে (Runs all the tests)
২. কোনো duplication নেই (Contains no duplication)
৩. Programmer-এর উদ্দেশ্য প্রকাশ করে (Expresses the intent of the programmer)
৪. ক্লাস ও মেথডের সংখ্যা কম রাখে (Minimizes the number of classes and methods)

নিয়ম ১: সব টেস্ট চলে Runs All the Tests

প্রথম এবং সবচেয়ে গুরুত্বপূর্ণ — সিস্টেম যেভাবে কাজ করার কথা, সেভাবেই কাজ করে কিনা সেটা verify করা যায়। যে সিস্টেম টেস্ট করা যায় না, তাকে verify করা যায় না — আর verify করা যায় না এমন সিস্টেম deploy করা উচিত নয়।

টেস্ট লেখার চাপেই আমরা ক্লাস ছোট ও single-purpose রাখতে বাধ্য হই। SRP-মেনে চলা ক্লাস টেস্ট করা সহজ। আর যত বেশি টেস্ট লিখি, তত বেশি DIP, interface, abstraction ব্যবহার করি coupling কমাতে। ফলে design আরও ভালো হয়।

একটি সহজ নিয়ম

"টেস্ট লেখো এবং ক্রমাগত চালাও" — এই নিয়মটিই আমাদের সিস্টেমকে OO-র মূল লক্ষ্য, অর্থাৎ low coupling এবং high cohesion-এর দিকে ঠেলে দেয়।

নিয়ম ২-৪: Refactoring Refactoring

টেস্ট থাকলে কোড পরিষ্কার করার সাহস পাওয়া যায়। প্রতি কয়েক লাইন কোড যোগ করার পর থামুন, দেখুন design খারাপ হয়েছে কিনা। হয়ে থাকলে পরিষ্কার করুন, তারপর টেস্ট চালান — নিশ্চিত হন কিছু ভাঙেনি।

Refactoring-এর সময় আমরা cohesion বাড়াই, coupling কমাই, concern আলাদা করি, function ও class ছোট করি, ভালো নাম বাছাই করি। এবং বাকি তিনটি নিয়ম প্রয়োগ করি: duplication দূর করো, expressiveness নিশ্চিত করো, ক্লাস-মেথড সংখ্যা কমাও।

Duplication দূর করো No Duplication

Duplication হলো ভালো design-এর প্রধান শত্রু। এটা অতিরিক্ত কাজ, অতিরিক্ত ঝুঁকি, এবং অতিরিক্ত জটিলতা আনে।

Duplication অনেক রূপে আসে। হুবহু একই কোড তো আছেই, কিন্তু implementation-এর duplication-ও থাকতে পারে। যেমন:

int size() {}
boolean isEmpty() {}

এদের আলাদা implementation দেওয়ার বদলে isEmpty-কে size-এর সাথে বেঁধে দেওয়া যায়:

boolean isEmpty() {
    return 0 == size();
}

আরেকটি উদাহরণ — দুটো method-এ একই ধরনের কাজ হচ্ছে:

✗ শেষের তিন লাইন duplicate 
public void scaleToOneDimension(
        float desiredDimension, float imageDimension) {
    if (Math.abs(desiredDimension - imageDimension) < errorThreshold)
        return;
    float scalingFactor = desiredDimension / imageDimension;
    scalingFactor = (float)(Math.floor(scalingFactor * 100) * 0.01f);

    RenderedOp newImage = ImageUtilities.getScaledImage(
        image, scalingFactor, scalingFactor);
    image.dispose();
    System.gc();
    image = newImage;
}

public synchronized void rotate(int degrees) {
    RenderedOp newImage = ImageUtilities.getRotatedImage(
        image, degrees);
    image.dispose();
    System.gc();
    image = newImage;
}

শেষের তিন লাইন একই! এটা একটি আলাদা method-এ বের করে আনা যায়:

✓ ভালো — common code আলাদা 
public void scaleToOneDimension(
        float desiredDimension, float imageDimension) {
    if (Math.abs(desiredDimension - imageDimension) < errorThreshold)
        return;
    float scalingFactor = desiredDimension / imageDimension;
    scalingFactor = (float)(Math.floor(scalingFactor * 100) * 0.01f);
    replaceImage(ImageUtilities.getScaledImage(
        image, scalingFactor, scalingFactor));
}

public synchronized void rotate(int degrees) {
    replaceImage(ImageUtilities.getRotatedImage(image, degrees));
}

private void replaceImage(RenderedOp newImage) {
    image.dispose();
    System.gc();
    image = newImage;
}

এভাবে ছোট ছোট commonality বের করতে গেলে SRP violation ধরা পড়ে এবং নতুন method-কে অন্য ক্লাসে স্থানান্তরের সুযোগ পাওয়া যায়। "ছোট পরিসরে reuse" বড় পরিসরে reuse-এর ভিত্তি তৈরি করে।

Template Method Pattern Template Method Pattern

Higher-level duplication দূর করতে Template Method pattern কাজে আসে:

✗ দুটো method-এ একই structure 
public class VacationPolicy {
    public void accrueUSDivisionVacation() {
        // ঘণ্টার হিসাবে ছুটি গণনা
        // ...
        // US minimum নিশ্চিত করো
        // ...
        // payroll-এ প্রয়োগ
        // ...
    }

    public void accrueEUDivisionVacation() {
        // ঘণ্টার হিসাবে ছুটি গণনা (একই!)
        // ...
        // EU minimum নিশ্চিত করো (ভিন্ন!)
        // ...
        // payroll-এ প্রয়োগ (একই!)
        // ...
    }
}

Template Method প্রয়োগ করলে:

✓ ভালো — Template Method 
abstract public class VacationPolicy {
    public void accrueVacation() {
        calculateBaseVacationHours();
        alterForLegalMinimums();
        applyToPayroll();
    }

    private void calculateBaseVacationHours() { /* ... */ };
    abstract protected void alterForLegalMinimums();
    private void applyToPayroll() { /* ... */ };
}

public class USVacationPolicy extends VacationPolicy {
    @Override protected void alterForLegalMinimums() {
        // US-specific logic
    }
}

public class EUVacationPolicy extends VacationPolicy {
    @Override protected void alterForLegalMinimums() {
        // EU-specific logic
    }
}

Subclass শুধু algorithm-এর সেই অংশটুকু পূরণ করে যেটা ভিন্ন — বাকি সব common code base class-এ থাকে।

Expressive কোড Expressive

কোড লেখার সময় আমরা সমস্যার গভীরে থাকি বলে কোড বুঝতে পারি। কিন্তু পরবর্তীতে যিনি maintain করবেন, তাঁর এত গভীর বোঝাপড়া নাও থাকতে পারে। সফটওয়্যারের সবচেয়ে বড় খরচ হলো দীর্ঘমেয়াদী maintenance। তাই কোড পরিষ্কারভাবে লিখে উদ্দেশ্য প্রকাশ করা উচিত।

Expressive কোড লেখার উপায়:

ভালো নাম বাছাই করুন: ক্লাস বা function-এর নাম শুনেই যেন তার দায়িত্ব সম্পর্কে আন্দাজ পাওয়া যায়।

Function ও class ছোট রাখুন: ছোট ক্লাস ও function সহজে নামকরণ, লেখা, ও বোঝা যায়।

Standard nomenclature ব্যবহার করুন: Design pattern-এর নাম (যেমন COMMAND, VISITOR) ক্লাসের নামে ব্যবহার করলে অন্য developer দ্রুত বুঝতে পারে।

ভালো unit test লিখুন: টেস্ট কোডের "documentation by example" হিসেবে কাজ করে।

চেষ্টা করুন: কোড কাজ করলেই পরবর্তী সমস্যায় চলে যাবেন না। একটু সময় নিন কোডকে পরবর্তী পাঠকের জন্য সহজ করতে। মনে রাখুন — পরবর্তী পাঠক সম্ভবত আপনি নিজেই!

ক্লাস ও মেথড সংখ্যা কমাও Minimal Classes and Methods

Duplication দূর করা, expressiveness — এসব নিয়ম অতিরিক্ত মানতে গেলে খুব বেশি ছোট ক্লাস ও method তৈরি হতে পারে। এই চতুর্থ নিয়ম বলে — ক্লাস ও method-এর মোট সংখ্যাও কম রাখো।

যেমন, প্রতিটি ক্লাসের জন্য আলাদা interface তৈরি করার জেদ, বা data class ও behavior class আলাদা করার গোঁড়ামি — এগুলো অনর্থক complexity বাড়ায়। Pragmatic (বাস্তববাদী) হতে হবে।

তবে মনে রাখতে হবে — এটা চারটি নিয়মের মধ্যে সবচেয়ে কম গুরুত্বপূর্ণ। টেস্ট থাকা, duplication দূর করা, ও expressiveness — এগুলো সবসময় আগে।

উপসংহার Conclusion

এই চারটি নিয়ম কি অভিজ্ঞতার বিকল্প? নিশ্চয়ই না। তবে এগুলো দশকের পর দশক অভিজ্ঞতার সংকলিত রূপ। Simple design-এর চর্চা developer-দের ভালো principle ও pattern অনুসরণ করতে উৎসাহিত করে — যেগুলো অন্যথায় শিখতে বছরের পর বছর লাগে।

★ মূল ধারণা সারসংক্ষেপ Key Concepts

★ Simple Design-এর চারটি নিয়ম
১) সব টেস্ট চলে, ২) Duplication নেই, ৩) Programmer-এর উদ্দেশ্য প্রকাশ করে, ৪) ক্লাস ও মেথড সংখ্যা কম — গুরুত্বের এই ক্রমে।
★ টেস্ট সবকিছুর ভিত্তি
টেস্ট লেখার চাপেই ক্লাস ছোট, single-purpose, এবং loosely coupled হয়। টেস্ট থাকলে refactoring-এর সাহস পাওয়া যায়।
★ Duplication হলো প্রধান শত্রু
হুবহু duplicate code থেকে শুরু করে implementation duplication — সব ধরনের duplication দূর করতে হবে।
★ Expressive কোড লেখো
ভালো নাম দাও, ছোট function-class রাখো, standard pattern নাম ব্যবহার করো, ভালো টেস্ট লেখো।
★ Template Method Pattern
Higher-level duplication দূর করতে Template Method ব্যবহার করো — common algorithm base class-এ রাখো, ভিন্ন অংশ subclass-এ।
★ Pragmatic হও
নিয়ম অতিরিক্ত মানতে গিয়ে অনর্থক complexity তৈরি করো না। ক্লাস-মেথড সংখ্যা কম রাখো, কিন্তু এটা সবচেয়ে কম priority।
