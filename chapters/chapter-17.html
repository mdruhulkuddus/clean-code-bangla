অধ্যায় ১৭
কোডের গন্ধ ও হিউরিস্টিকস
Smells and Heuristics
by Robert C. Martin

Code Smell মানে হলো কোডে এমন কিছু যা দেখলেই বুঝবেন কিছু একটা ঠিক নেই — সরাসরি Bug না হলেও ভবিষ্যতে সমস্যা তৈরি করবে। Heuristic মানে হলো অভিজ্ঞতালব্ধ নিয়ম যা কোড লেখার সময় মেনে চলা উচিত। এই অধ্যায়টি একটি সম্পূর্ণ Reference Guide — প্রতিটি Smell ও Heuristic-এর একটি সংক্ষিপ্ত বিবরণ এখানে দেওয়া হলো।

কমেন্ট সম্পর্কিত সমস্যা Comments (C1–C5)

C1
অনুচিত তথ্য (Inappropriate Information)
কমেন্টে change history, author নাম, SPR নম্বর ইত্যাদি রাখবেন না। এগুলো Source Control-এর কাজ। কমেন্ট শুধুমাত্র কোড ও Design সম্পর্কে Technical Note-এর জন্য।
C2
সেকেলে কমেন্ট (Obsolete Comment)
পুরোনো ও ভুল কমেন্ট দ্রুত আপডেট বা মুছে ফেলুন। এগুলো কোড থেকে দূরে সরে গিয়ে বিভ্রান্তি তৈরি করে।
C3
অপ্রয়োজনীয় কমেন্ট (Redundant Comment)
কোড নিজেই যা বলে দিচ্ছে, সেটা কমেন্টে আবার লেখা অর্থহীন। যেমন i++; // increment i
C4
খারাপভাবে লেখা কমেন্ট (Poorly Written Comment)
কমেন্ট লিখলে ভালো করে লিখুন। সংক্ষিপ্ত, সুনির্দিষ্ট ও সঠিক ব্যাকরণে।
C5
কমেন্ট-আউট কোড (Commented-Out Code)
এটি একটি ভয়াবহ অভ্যাস। কেউ মুছতে সাহস করে না কারণ ভাবে অন্য কেউ হয়তো দরকার। সাহস করে মুছে ফেলুন — Source Control-এ সব আছে।

পরিবেশ সংক্রান্ত Environment (E1–E2)

E1
Build-এ একাধিক ধাপ (Build Requires More Than One Step)
প্রজেক্ট Build করতে একটি মাত্র কমান্ড লাগবে। অনেক জায়গা থেকে ফাইল খুঁজতে হলে সমস্যা।
E2
Test-এ একাধিক ধাপ (Tests Require More Than One Step)
সব Unit Test একটি মাত্র কমান্ড বা IDE-তে একটি বাটন ক্লিকে চলবে।

ফাংশন সম্পর্কিত Functions (F1–F4)

F1
বেশি Argument (Too Many Arguments)
ফাংশনে যত কম Argument তত ভালো। শূন্য সবচেয়ে ভালো, তারপর এক, দুই, তিন। তিনের বেশি এড়িয়ে চলুন।
F2
Output Argument
Argument সাধারণত Input হিসেবে পড়া হয়। ফাংশন কিছু পরিবর্তন করতে চাইলে নিজের Object-এর State পরিবর্তন করুন।
F3
Flag Argument
Boolean Argument মানে ফাংশন একাধিক কাজ করে। এটি বিভ্রান্তিকর, বাদ দিন।
F4
Dead Function
যেসব মেথড কেউ কল করে না সেগুলো মুছে ফেলুন। ভয় পাবেন না — Source Control আছে।

সাধারণ নিয়ম General (G1–G36)

G1
একটি ফাইলে একাধিক ভাষা
একটি Source File-এ যতটা সম্ভব কম ভাষা রাখুন।
G2
সুস্পষ্ট আচরণ বাস্তবায়িত নয় (Obvious Behavior Is Unimplemented)
Principle of Least Surprise অনুসরণ করুন।
G3
সীমান্তে ভুল আচরণ (Incorrect Behavior at the Boundaries)
প্রতিটি Boundary Condition-এর জন্য Test লিখুন। শুধু Intuition-এর উপর নির্ভর করবেন না।
G4
নিরাপত্তা ব্যবস্থা Override করা
Compiler Warning বন্ধ করা, Failing Test বন্ধ করা — এগুলো চেরনোবিলের Safety Override-এর মতোই বিপজ্জনক।
G5
Duplication
এটি এই বইয়ের সবচেয়ে গুরুত্বপূর্ণ নিয়মগুলোর একটি। DRY Principle (Don't Repeat Yourself) মেনে চলুন। তিন রূপ: হুবহু একই কোড, বারবার একই switch/case, এবং একই রকম Algorithm কিন্তু ভিন্ন কোড।
G6
ভুল Abstraction Level-এ কোড
Base Class-এ শুধু উচ্চ-স্তরের ধারণা রাখুন, নিম্ন-স্তরের বাস্তবায়ন Derivative-এ।
G7
Base Class Derivative-এর উপর নির্ভরশীল
Base Class-এর Derivative সম্পর্কে কিছু জানা উচিত নয়।
G8
অতিরিক্ত তথ্য প্রকাশ (Too Much Information)
Interface ছোট রাখুন। কম মেথড, কম Variable, কম Coupling।
G9
Dead Code
যে কোড কখনো Execute হয় না তা মুছে ফেলুন।
G10
লম্বদূরত্ব (Vertical Separation)
Variable তার প্রথম ব্যবহারের ঠিক আগে Declare করুন। Private Function তার প্রথম ব্যবহারের ঠিক নিচে Define করুন।
G11
সঙ্গতি (Inconsistency)
একবার কোনো নিয়ম মেনে চললে সবসময় মানুন।
G14
Feature Envy
কোনো মেথড যদি অন্য ক্লাসের Variable ও Function বেশি ব্যবহার করে, তাহলে সেটি সেই ক্লাসে থাকা উচিত।
G15
Selector Argument
calculateWeeklyPay(false) দেখে কেউ বুঝবে না false কী করে। আলাদা আলাদা ফাংশন লিখুন: straightPay() ও overTimePay()।
G16
ঢাকা উদ্দেশ্য (Obscured Intent)
Magic Number, Hungarian Notation, সংক্ষিপ্ত Variable নাম — সব কোডের উদ্দেশ্য লুকিয়ে ফেলে।
G19
ব্যাখ্যামূলক Variable ব্যবহার করুন
জটিল হিসাবকে Intermediate Variable-এ ভাগ করুন অর্থবহ নাম দিয়ে।
G20
Function-এর নাম তার কাজ বলবে
date.add(5) থেকে বোঝা যায় না ৫ দিন যোগ হচ্ছে নাকি ৫ ঘণ্টা। plusDays(5) অনেক স্পষ্ট।
G23
Polymorphism-কে Switch/Case-এর চেয়ে বেশি পছন্দ করুন
ONE SWITCH Rule: একটি নির্দিষ্ট ধরনের Selection-এর জন্য একটিমাত্র switch statement থাকবে।
G25
Magic Number-এর বদলে Named Constant
86400 এর বদলে SECONDS_PER_DAY ব্যবহার করুন।
G28
Conditional-কে Encapsulate করুন
if (timer.hasExpired() && !timer.isRecurrent()) এর বদলে if (shouldBeDeleted(timer)) লিখুন।
G29
Negative Conditional এড়িয়ে চলুন
if (buffer.shouldCompact()) লিখুন, if (!buffer.shouldNotCompact()) লিখবেন না।
G30
ফাংশন একটি কাজ করবে
একটি ফাংশনে Loop, Check, ও Action সব মিশিয়ে ফেলবেন না। আলাদা আলাদা ফাংশনে ভাগ করুন।
G36
Transitive Navigation এড়িয়ে চলুন
Law of Demeter মেনে চলুন। a.getB().getC().doSomething() লিখবেন না। শুধু নিজের সরাসরি সহযোগীকে কল করুন।

নামকরণ Names (N1–N7)

N1
বর্ণনামূলক নাম বেছে নিন
নাম হলো Software-এর Readability-র ৯০%। ভালো নাম কোডের গল্প বর্ণনায় পরিণত করে।
N2
সঠিক Abstraction Level-এর নাম
Modem interface-এ dial(String phoneNumber) না লিখে connect(String connectionLocator) লিখুন।
N5
বড় Scope-তে বড় নাম
৫ লাইনের Loop-এ i ঠিক আছে। কিন্তু বড় Scope-তে দীর্ঘ, সুনির্দিষ্ট নাম ব্যবহার করুন।
N7
নাম Side-effect প্রকাশ করবে
getOos() শুধু Get করে না, তৈরিও করে। তাই নাম হবে createOrReturnOos()।

টেস্টিং Tests (T1–T9)

T1
অপর্যাপ্ত টেস্ট
"যথেষ্ট মনে হচ্ছে" এটি ভুল মাপকাঠি। যা ভাঙতে পারে তার সবকিছু টেস্ট করুন।
T2
Coverage Tool ব্যবহার করুন!
Coverage Tool টেস্টিং-এর ফাঁকা দেখায়। সবুজ মানে Covered, লাল মানে Uncovered।
T5
Boundary Condition টেস্ট করুন
Algorithm-এর মধ্যভাগ সাধারণত ঠিক থাকে, সমস্যা হয় সীমান্তে।
T6
Bug-এর কাছে পুঙ্খানুপুঙ্খ টেস্ট করুন
Bug একা আসে না, দলে বেঁধে আসে। একটি Bug পেলে সেই ফাংশনটি সম্পূর্ণ টেস্ট করুন।
T9
টেস্ট দ্রুত চলবে
ধীর টেস্ট চালানো হয় না। কাটে পড়লে প্রথমেই ধীর টেস্ট বাদ যায়।

★ মূল ধারণা সারসংক্ষেপ Key Concepts

★ Clean Code কোনো নিয়মের তালিকা মেনে চলা নয়
এই Heuristic-গুলো একটি মূল্যবোধ ব্যবস্থা নির্দেশ করে। পেশাদারিত্ব ও দক্ষতা আসে সেই মূল্যবোধ থেকে যা শৃঙ্খলাকে চালিত করে।
★ DRY — সবচেয়ে গুরুত্বপূর্ণ নিয়ম
Duplication দেখলে Abstraction তৈরি করুন — Subroutine, Class, Template Method, বা Strategy Pattern ব্যবহার করুন।
★ নাম হলো Readability-র ৯০%
বর্ণনামূলক, সঠিক Abstraction Level-এর, দ্ব্যর্থহীন নাম ব্যবহার করুন।
★ টেস্ট সবকিছুর ভিত্তি
Coverage Tool ব্যবহার করুন, Boundary Condition টেস্ট করুন, Bug-এর কাছে পুঙ্খানুপুঙ্খ টেস্ট করুন।
