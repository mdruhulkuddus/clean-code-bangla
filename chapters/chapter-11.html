Systems
by Robert C. Martin

এই অধ্যায়ে বলা হয়েছে — সিস্টেম লেভেলেও clean code-এর চর্চা দরকার। Object তৈরি (construction) ও ব্যবহার (use) আলাদা রাখতে হবে। Dependency Injection (DI), AOP (Aspect-Oriented Programming), এবং POJO-ভিত্তিক ডিজাইন সিস্টেমকে flexible ও testable রাখে। Big Design Up Front (BDUF) এড়িয়ে incrementally সিস্টেম তৈরি করতে হবে।

শহর তৈরির উপমা How Would You Build a City?

আপনি কি একা একটি শহরের সব বিষয় সামলাতে পারবেন? সম্ভবত না। তবু শহরগুলো চলে — কারণ বিভিন্ন দল বিভিন্ন অংশ সামলায়: পানি ব্যবস্থা, বিদ্যুৎ, যানবাহন, আইন-শৃঙ্খলা। কেউ বড় চিত্র দেখে, কেউ খুঁটিনাটি দেখে।

সফটওয়্যার টিমও এভাবে সংগঠিত, কিন্তু তাদের তৈরি সিস্টেমে প্রায়ই সেই Separation of Concerns থাকে না। Clean code নিচের স্তরে (function, class) সাহায্য করে — এই অধ্যায়ে আমরা উঁচু স্তরে (system level) clean থাকার কথা বলব।

নির্মাণ ও ব্যবহার আলাদা করুন Separate Constructing a System from Using It

নির্মাণ (construction) আর ব্যবহার (use) দুটো একেবারে আলাদা প্রক্রিয়া। একটি হোটেল নির্মাণের সময় ক্রেন, সিমেন্ট, শ্রমিক থাকে — আর নির্মাণ শেষে সুন্দর কাচের দেয়াল, রঙ, অতিথি থাকে। সফটওয়্যারেও startup process (object তৈরি ও dependency wiring) আর runtime logic আলাদা রাখা উচিত।

বেশিরভাগ application-এ startup code runtime logic-এর সাথে মিশে থাকে। যেমন:

✗ Lazy Initialization — সমস্যাযুক্ত 
public Service getService() {
    if (service == null)
        service = new MyServiceImpl(...);
    return service;
}

এটা Lazy Initialization — ভালো দিক হলো যতক্ষণ object দরকার না ততক্ষণ তৈরি হয় না। কিন্তু সমস্যা হলো MyServiceImpl-এর ওপর hard-coded dependency তৈরি হয়ে গেছে। টেস্ট করতে গেলে এই method-এর আগেই mock object বসাতে হবে। আর এটা SRP-ও ভাঙে।

Main আলাদা করো Separation of Main

সব construction logic main function-এ (বা main থেকে ডাকা module-এ) রাখুন। বাকি system ধরে নেবে যে সব object ঠিকমতো তৈরি ও wire করা হয়েছে। Dependency arrow গুলো সব main থেকে দূরে যাবে — application-এর main সম্পর্কে কিছু জানার দরকার নেই।

Factory Pattern Factory Pattern

কখনো কখনো application-কেই ঠিক করতে হয় কখন কোন object তৈরি হবে। সেক্ষেত্রে Abstract Factory pattern ব্যবহার করা হয় — যাতে application object তৈরির সময় নিয়ন্ত্রণ করতে পারে, কিন্তু তৈরির বিস্তারিত জানতে না হয়।

Dependency Injection (DI) Dependency Injection

Dependency Injection (DI) কী?

Dependency Injection হলো Inversion of Control (IoC)-এর একটি প্রয়োগ। এতে একটি object নিজে তার dependency তৈরি করে না — বাইরে থেকে setter method বা constructor argument দিয়ে dependency "ইনজেক্ট" করা হয়। DI container (যেমন Spring) চাহিদামতো object তৈরি করে এবং একে অপরের সাথে wire করে দেয়।

JNDI lookup হলো আংশিক DI — object নিজে directory server-এ request করে service খোঁজে। আসল DI-তে class নিজে কিছু করে না, সম্পূর্ণ passive থাকে:

// JNDI — আংশিক DI
MyService myService = (MyService)(jndiContext.lookup("NameOfMyService"));

// True DI — class passive, setter/constructor দিয়ে inject হয়

Spring Framework এ XML configuration file ব্যবহার করে object wire করা হয়। Lazy initialization-ও DI container-এ সম্ভব — বেশিরভাগ container চাহিদামতো object তৈরি করে।

স্কেল করো Scaling Up

শহর গ্রাম থেকে বড় হয়, গ্রাম বসতি থেকে। প্রথমে সরু রাস্তা থাকে, পরে চওড়া হয়। সফটওয়্যারও একই — প্রথম দিন থেকেই "ঠিক" সিস্টেম বানানো সম্ভব না। আজকের প্রয়োজন মেটাও, তারপর refactor ও expand করো। এটাই iterative agility-র মূলকথা।

মূল কথা

সফটওয়্যার সিস্টেম ভৌত (physical) সিস্টেম থেকে আলাদা। সঠিকভাবে concern আলাদা রাখলে সফটওয়্যারের architecture ধীরে ধীরে বাড়তে পারে।

EJB2 — একটি সাবধানমূলক উদাহরণ EJB2 — A Cautionary Tale

EJB1 এবং EJB2 architecture concern সঠিকভাবে আলাদা করতে পারেনি, তাই organic growth বাধাগ্রস্ত হতো। একটি simple Bank entity bean-এ interface, implementation class, XML deployment descriptor — সব মিলিয়ে অনেক boilerplate code লিখতে হতো। Business logic container-এর সাথে tightly coupled ছিল, তাই unit testing কঠিন ছিল।

Cross-Cutting Concerns Cross-Cutting Concerns

Cross-Cutting Concerns হলো সেই বিষয়গুলো যা অনেক object-এর মধ্যে ছড়িয়ে পড়ে, যেমন persistence, security, transaction। এগুলো modular ভাবে চিন্তা করা যায়, কিন্তু বাস্তবে একই কোড অনেক জায়গায় ছড়িয়ে দিতে হয়।

EJB architecture এই সমস্যা মোকাবেলায় যে পদ্ধতি ব্যবহার করেছিল, তা পরে Aspect-Oriented Programming (AOP) হিসেবে পরিচিত পায়। AOP-তে aspect নামক modular construct দিয়ে নির্ধারণ করা হয় সিস্টেমের কোন কোন পয়েন্টে behavior পরিবর্তন করতে হবে।

Pure Java AOP Frameworks Pure Java AOP Frameworks

Spring AOP এবং JBoss AOP-তে business logic POJO (Plain Old Java Object) হিসেবে লেখা হয়। POJO-গুলো শুধু domain logic-এ ফোকাস করে, enterprise framework-এর ওপর কোনো dependency থাকে না। Cross-cutting concerns (persistence, transaction, security) XML configuration file বা annotation দিয়ে declaratively যোগ করা হয়।

Spring configuration-এর উদাহরণ:

<beans>
    <bean id="appDataSource"
        class="org.apache.commons.dbcp.BasicDataSource"
        destroy-method="close"
        p:driverClassName="com.mysql.jdbc.Driver"
        p:url="jdbc:mysql://localhost:3306/mydb"
        p:username="me"/>

    <bean id="bankDataAccessObject"
        class="com.example.banking.persistence.BankDataAccessObject"
        p:dataSource-ref="appDataSource"/>

    <bean id="bank"
        class="com.example.banking.model.Bank"
        p:dataAccessObject-ref="bankDataAccessObject"/>
</beans>

EJB3 এই সমস্যার অনেকটা সমাধান করেছে — annotation ব্যবহার করে অনেক সহজভাবে entity define করা যায়:

@Entity
@Table(name = "BANKS")
public class Bank implements java.io.Serializable {
    @Id @GeneratedValue(strategy=GenerationType.AUTO)
    private int id;

    @Embeddable
    public class Address {
        protected String streetAddr1;
        protected String streetAddr2;
        protected String city;
        protected String state;
        protected String zipCode;
    }

    @Embedded
    private Address address;

    @OneToMany(cascade = CascadeType.ALL, fetch = FetchType.EAGER,
        mappedBy="bank")
    private Collection<Account> accounts = new ArrayList<Account>();

    public int getId() { return id; }
    public void setId(int id) { this.id = id; }

    public void addAccount(Account account) {
        account.setBank(this);
        accounts.add(account);
    }
    // ...
}

EJB2-র তুলনায় এই কোড অনেক পরিষ্কার — annotation-এর বাইরে শুধু পরিচ্ছন্ন Java code।

সিস্টেম Architecture Test-Drive করুন Test-Drive the System Architecture

যদি আপনার application-এর domain logic POJO দিয়ে লেখা থাকে, architecture concerns থেকে decoupled থাকে, তাহলে architecture-কে test-drive করা সম্ভব। "Naively simple" কিন্তু decoupled architecture দিয়ে শুরু করুন, দ্রুত working user stories deliver করুন, তারপর প্রয়োজনমতো infrastructure যোগ করুন।

সর্বোত্তম Architecture

সর্বোত্তম system architecture হলো — modularized domain of concern, যেখানে প্রতিটি domain POJO দিয়ে implement করা, এবং বিভিন্ন domain minimally invasive Aspect দিয়ে integrate করা। এই architecture test-driven হতে পারে।

সিদ্ধান্ত গ্রহণ অপটিমাইজ করুন Optimize Decision Making

বড় সিস্টেমে একজনের পক্ষে সব সিদ্ধান্ত নেওয়া সম্ভব নয়। সবচেয়ে যোগ্য ব্যক্তিকে দায়িত্ব দেওয়া উচিত। আর সিদ্ধান্ত যতটা সম্ভব দেরিতে নেওয়া উচিত — এটা অলসতা নয়, এটা সবচেয়ে বেশি তথ্য নিয়ে informed decision নেওয়ার সুযোগ।

Domain-Specific Languages (DSL) Domain-Specific Languages

Domain-Specific Language (DSL) হলো ছোট scripting language বা API যা দিয়ে কোড এমনভাবে লেখা যায় যে domain expert-ও সেটা পড়ে বুঝতে পারেন। ভালো DSL domain concept ও implementation code-এর মধ্যে communication gap কমিয়ে দেয়।

উপসংহার Conclusion

সিস্টেমও পরিষ্কার হতে হবে। ভারী architecture domain logic-কে চাপা দেয়, agility নষ্ট করে। সব abstraction level-এ intent পরিষ্কার হওয়া উচিত। POJO ব্যবহার করুন, aspect-like mechanism দিয়ে implementation concerns noninvasively যোগ করুন।

সবচেয়ে সহজ যেটা কাজ করবে সেটাই ব্যবহার করুন।

★ মূল ধারণা সারসংক্ষেপ Key Concepts

★ নির্মাণ ও ব্যবহার আলাদা করো
Object তৈরি (construction) ও ব্যবহার (use) আলাদা প্রক্রিয়া — startup logic আর runtime logic মিশিয়ো না।
★ Dependency Injection (DI)
Object নিজে dependency তৈরি করবে না — বাইরে থেকে inject করা হবে। এতে coupling কমে এবং testing সহজ হয়।
★ Incrementally বাড়াও
প্রথম দিন থেকেই "ঠিক" সিস্টেম বানানো সম্ভব না। আজকের প্রয়োজন মেটাও, তারপর refactor করো।
★ Cross-Cutting Concerns
Persistence, security, transaction — এগুলো AOP বা aspect-like mechanism দিয়ে modular ভাবে handle করো।
★ POJO-ভিত্তিক ডিজাইন
Business logic POJO দিয়ে লেখো — enterprise framework-এর ওপর dependency রাখো না।
★ সিদ্ধান্ত দেরিতে নাও
সবচেয়ে বেশি তথ্য নিয়ে informed decision নেওয়ার জন্য সিদ্ধান্ত যতটা সম্ভব দেরিতে নাও।
