ভালো সফটওয়্যার ডিজাইনের মূল কথা হলো — ক্লাস ছোট রাখো, প্রতিটি ক্লাসের একটিমাত্র দায়িত্ব থাকবে, এবং ক্লাসগুলো যেন একে অপরের থেকে যতটা সম্ভব স্বাধীন হয়। এই অধ্যায়ে Single Responsibility Principle (SRP), Cohesion, Open-Closed Principle (OCP), এবং Dependency Inversion Principle (DIP) নিয়ে আলোচনা করা হয়েছে।

ক্লাস সংগঠন Class Organization

Java convention অনুযায়ী একটি ক্লাসের শুরুতে variable-এর তালিকা থাকা উচিত। প্রথমে public static constant, তারপর private static variable, এবং তারপর private instance variable রাখা হয়। সাধারণত public variable রাখার কোনো ভালো কারণ নেই।

Variable-এর পরে public function গুলো আসবে। আর একটি public function যে private utility function ব্যবহার করে, সেটি ঠিক ওই public function-এর পরেই রাখা ভালো। এতে কোড পড়তে অনেকটা পত্রিকার মতো লাগে — ওপর থেকে নিচে পড়া যায় (এটাকে বলে Stepdown Rule)।

Encapsulation — তথ্য লুকানো Encapsulation

Encapsulation মানে হলো ক্লাসের ভেতরের variable ও utility function গুলো বাইরে থেকে লুকিয়ে রাখা। আমরা সবকিছু private রাখতে চাই, তবে এটা নিয়ে গোঁড়ামি করি না। যদি একটি টেস্টের জন্য কোনো variable বা function অ্যাক্সেস করা দরকার হয়, তাহলে সেটাকে protected বা package scope করা যায়। তবে প্রথমে privacy বজায় রাখার উপায় খুঁজতে হবে — encapsulation শিথিল করা সবসময় শেষ উপায়।

ক্লাস ছোট হওয়া উচিত! Classes Should Be Small!

ক্লাসের প্রথম নিয়ম — এটা ছোট হওয়া উচিত। দ্বিতীয় নিয়ম — এটা আরও ছোট হওয়া উচিত! Function-এ আমরা line গুনে সাইজ মাপি, কিন্তু ক্লাসের ক্ষেত্রে আমরা গুনি Responsibility অর্থাৎ দায়িত্বের সংখ্যা।

৫টি method — মনে হতে পারে এটা যথেষ্ট ছোট। কিন্তু আসলে এই ক্লাসেও অনেক বেশি দায়িত্ব আছে! ক্লাসের নাম দিয়েই বোঝা উচিত সে কী কাজ করে। যদি ক্লাসের জন্য একটি সংক্ষিপ্ত নাম খুঁজে পাওয়া না যায়, তাহলে সম্ভবত এটা বেশি বড়। Processor, Manager, Super এরকম নাম দেখলে বুঝতে হবে দায়িত্বের জটপাকানো অবস্থা।

ক্লাসের বর্ণনা ২৫ শব্দের মধ্যে লেখা উচিত — "যদি", "এবং", "অথবা", "কিন্তু" শব্দ ছাড়া। যেমন: "SuperDashboard শেষ ফোকাস হওয়া component-এর access দেয় এবং version ও build নম্বর ট্র্যাক করে।" এই "এবং" শব্দটিই ইঙ্গিত দেয় যে ক্লাসে একাধিক দায়িত্ব আছে।

Single Responsibility Principle (SRP) Single Responsibility Principle

SRP — Single Responsibility Principle

SRP বলে — একটি ক্লাস বা module-এর পরিবর্তনের কারণ শুধুমাত্র একটিই থাকা উচিত। মানে, প্রতিটি ক্লাসের একটিমাত্র দায়িত্ব থাকবে।

আগের SuperDashboard ক্লাসে দুটো কারণে পরিবর্তন আনতে হতে পারে — version information আপডেট করতে এবং Swing component ম্যানেজ করতে। তাই version-সংক্রান্ত method গুলো একটি আলাদা ক্লাসে রাখা উচিত:

✓ ভালো — আলাদা দায়িত্ব 
public class Version {
    public int getMajorVersionNumber()
    public int getMinorVersionNumber()
    public int getBuildNumber()
}

SRP অনেক গুরুত্বপূর্ণ একটি OO design principle, অথচ এটি সবচেয়ে বেশি লঙ্ঘিতও হয়। কেন? কারণ বেশিরভাগ সময় আমরা কোড কাজ করালেই থেমে যাই। কোড সংগঠিত ও পরিষ্কার করার কাজটি পরে করি না।

অনেকে মনে করেন যে অনেকগুলো ছোট ক্লাস থাকলে পুরো সিস্টেম বোঝা কঠিন হয়ে যায়। কিন্তু আসল কথা হলো — ছোট ছোট ক্লাস আর বড় ক্লাস, দুটোতেই শেখার পরিমাণ সমান। প্রশ্ন হলো: আপনি কি আপনার টুলবক্সে ছোট ছোট ড্রয়ারে সুন্দরভাবে সাজানো টুলস চান, নাকি একটা বিশাল ড্রয়ারে সব জিনিস ঢেলে রাখতে চান?

Cohesion — সংসক্তি Cohesion

Cohesion কী?

Cohesion মানে হলো একটি ক্লাসের method গুলো কতটা ক্লাসের instance variable ব্যবহার করে। যত বেশি variable ব্যবহার করে, ততই cohesive। যেখানে প্রতিটি method প্রতিটি variable ব্যবহার করে — সেটা সর্বোচ্চ cohesive ক্লাস।

নিচের Stack ক্লাসটি অত্যন্ত cohesive — তিনটি method-এর মধ্যে শুধু size() ছাড়া বাকি সবগুলো দুটো variable-ই ব্যবহার করে:

✓ উচ্চ Cohesion 
public class Stack {
    private int topOfStack = 0;
    List<Integer> elements = new LinkedList<Integer>();

    public int size() {
        return topOfStack;
    }

    public void push(int element) {
        topOfStack++;
        elements.add(element);
    }

    public int pop() throws PoppedWhenEmpty {
        if (topOfStack == 0)
            throw new PoppedWhenEmpty();
        int element = elements.get(--topOfStack);
        elements.remove(topOfStack);
        return element;
    }
}

যখন function ছোট করতে গেলে ক্লাসে instance variable জমা হতে থাকে এবং শুধু কিছু method সেগুলো ব্যবহার করে — তখন বুঝতে হবে ক্লাসের ভেতরে আরেকটি ক্লাস লুকিয়ে আছে। সেটা আলাদা করে বের করে আনতে হবে।

Cohesion বজায় রাখলে ছোট ছোট ক্লাস তৈরি হয় Maintaining Cohesion Results in Many Small Classes

বড় function ভাঙলে প্রায়ই ক্লাসও ভাঙতে হয়। ধরুন একটি বড় function-এর ভেতরে অনেক variable আছে। আপনি সেই function থেকে একটি অংশ আলাদা function-এ বের করতে চান, কিন্তু সেই অংশটি চারটি variable ব্যবহার করে। এই চারটি variable-কে instance variable বানালে নতুন function-এ কোনো argument পাঠাতে হবে না। কিন্তু এতে cohesion কমে যায়। যদি কিছু function নির্দিষ্ট কিছু variable শেয়ার করতে চায় — তাহলে তারা আসলে একটি আলাদা ক্লাস হতে চায়!

এটা বোঝাতে Knuth-এর PrintPrimes প্রোগ্রামের উদাহরণ দেওয়া হয়েছে। মূল কোডটি একটি বিশাল function:

✗ একটি বিশাল function 
package literatePrimes;

public class PrintPrimes {
    public static void main(String[] args) {
        final int M = 1000;
        final int RR = 50;
        final int CC = 4;
        final int WW = 10;
        final int ORDMAX = 30;
        int P[] = new int[M + 1];
        int PAGENUMBER;
        int PAGEOFFSET;
        int ROWOFFSET;
        int C;
        int J;
        int K;
        boolean JPRIME;
        int ORD;
        int SQUARE;
        int N;
        int MULT[] = new int[ORDMAX + 1];

        J = 1;
        K = 1;
        P[1] = 2;
        ORD = 2;
        SQUARE = 9;

        while (K < M) {
            do {
                J = J + 2;
                if (J == SQUARE) {
                    ORD = ORD + 1;
                    SQUARE = P[ORD] * P[ORD];
                    MULT[ORD - 1] = J;
                }
                N = 2;
                JPRIME = true;
                while (N < ORD && JPRIME) {
                    while (MULT[N] < J)
                        MULT[N] = MULT[N] + P[N] + P[N];
                    if (MULT[N] == J)
                        JPRIME = false;
                    N = N + 1;
                }
            } while (!JPRIME);
            K = K + 1;
            P[K] = J;
        }
        // ... printing logic ...
    }
}

Refactoring-এর পরে এটাকে তিনটি আলাদা ক্লাসে ভাগ করা হয়, প্রতিটির নিজস্ব দায়িত্ব:

✓ তিনটি আলাদা দায়িত্ব 
// PrimePrinter.java — মূল প্রোগ্রাম চালানোর দায়িত্ব
package literatePrimes;

public class PrimePrinter {
    public static void main(String[] args) {
        final int NUMBER_OF_PRIMES = 1000;
        int[] primes = PrimeGenerator.generate(NUMBER_OF_PRIMES);

        final int ROWS_PER_PAGE = 50;
        final int COLUMNS_PER_PAGE = 4;
        RowColumnPagePrinter tablePrinter =
            new RowColumnPagePrinter(ROWS_PER_PAGE,
                COLUMNS_PER_PAGE,
                "The First " + NUMBER_OF_PRIMES +
                " Prime Numbers");
        tablePrinter.print(primes);
    }
}
// PrimeGenerator.java — প্রাইম নম্বর তৈরির দায়িত্ব
package literatePrimes;
import java.util.ArrayList;

public class PrimeGenerator {
    private static int[] primes;
    private static ArrayList<Integer> multiplesOfPrimeFactors;

    protected static int[] generate(int n) {
        primes = new int[n];
        multiplesOfPrimeFactors = new ArrayList<Integer>();
        set2AsFirstPrime();
        checkOddNumbersForSubsequentPrimes();
        return primes;
    }

    private static void set2AsFirstPrime() {
        primes[0] = 2;
        multiplesOfPrimeFactors.add(2);
    }
    // ... বাকি method গুলো ...
}

লক্ষ্য করুন — প্রোগ্রামটা তিনটি দায়িত্বে ভাগ হয়ে গেছে: PrimePrinter execution environment সামলায়, RowColumnPagePrinter formatting-এর কাজ করে, আর PrimeGenerator prime number তৈরি করে। কোনো ক্লাসে পরিবর্তন দরকার হলে অন্য ক্লাসে হাত দেওয়া লাগবে না।

পরিবর্তনের জন্য সংগঠন Organizing for Change

প্রতিটি সিস্টেমে পরিবর্তন একটি চলমান প্রক্রিয়া। পরিবর্তন মানেই ঝুঁকি — বাকি সিস্টেম ভেঙে পড়তে পারে। Clean system-এ আমরা ক্লাস এমনভাবে সাজাই যাতে পরিবর্তনের ঝুঁকি কমে।

নিচের Sql ক্লাসটি SQL string তৈরি করে:

✗ একটি ক্লাসে সব দায়িত্ব 
public class Sql {
    public Sql(String table, Column[] columns)
    public String create()
    public String insert(Object[] fields)
    public String selectAll()
    public String findByKey(String keyColumn, String keyValue)
    public String select(Column column, String pattern)
    public String select(Criteria criteria)
    public String preparedInsert()
    private String columnList(Column[] columns)
    private String valuesList(Object[] fields, final Column[] columns)
    private String selectWithCriteria(String criteria)
    private String placeholderList(Column[] columns)
}

এই ক্লাসে নতুন ধরনের SQL statement (যেমন update) যোগ করতে গেলে পুরো ক্লাস "ওপেন" করতে হবে। এটা SRP লঙ্ঘন করে। সমাধান — প্রতিটি SQL operation-এর জন্য আলাদা ক্লাস:

OCP — Open-Closed Principle

Open-Closed Principle (OCP) বলে — ক্লাস extension-এর জন্য open থাকবে, কিন্তু modification-এর জন্য closed থাকবে। নতুন UpdateSql ক্লাস যোগ করলে বিদ্যমান কোনো ক্লাসে হাত দেওয়া লাগবে না।

পরিবর্তন থেকে বিচ্ছিন্নতা Isolating from Change

Concrete class-এ implementation detail থাকে, আর abstract class শুধু ধারণা প্রকাশ করে। একটি client class যদি সরাসরি concrete detail-এর ওপর নির্ভর করে, তাহলে সেই detail পরিবর্তন হলে client-ও ক্ষতিগ্রস্ত হবে। Interface ও abstract class ব্যবহার করলে এই সমস্যা এড়ানো যায়।

উদাহরণ: একটি Portfolio ক্লাস যদি সরাসরি TokyoStockExchange API-র ওপর নির্ভর করে, তাহলে টেস্ট করা কঠিন — কারণ stock-এর দাম প্রতি মুহূর্তে বদলায়। সমাধান — একটি interface তৈরি করা:

public interface StockExchange {
    Money currentPrice(String symbol);
}

Portfolio ক্লাস এখন এই interface-এর ওপর নির্ভর করবে, concrete class-এর ওপর নয়:

public Portfolio {
    private StockExchange exchange;
    public Portfolio(StockExchange exchange) {
        this.exchange = exchange;
    }
    // ...
}

এখন টেস্টে একটি mock implementation দেওয়া যায়:

public class PortfolioTest {
    private FixedStockExchangeStub exchange;
    private Portfolio portfolio;

    @Before
    protected void setUp() throws Exception {
        exchange = new FixedStockExchangeStub();
        exchange.fix("MSFT", 100);
        portfolio = new Portfolio(exchange);
    }

    @Test
    public void GivenFiveMSFTTotalShouldBe500() throws Exception {
        portfolio.add(5, "MSFT");
        Assert.assertEquals(500, portfolio.value());
    }
}
DIP — Dependency Inversion Principle

Dependency Inversion Principle (DIP) বলে — আমাদের ক্লাস concrete detail-এর ওপর নয়, বরং abstraction-এর ওপর নির্ভর করবে। এতে coupling কমে, টেস্ট করা সহজ হয়, এবং সিস্টেম আরও flexible হয়।

★ ক্লাস ছোট রাখো
ক্লাসের সাইজ মাপা হয় দায়িত্বের (Responsibility) সংখ্যা দিয়ে, লাইন সংখ্যা দিয়ে নয়।
★ Single Responsibility Principle (SRP)
একটি ক্লাসের পরিবর্তনের কারণ শুধুমাত্র একটিই থাকা উচিত — মানে প্রতিটি ক্লাসের একটিমাত্র দায়িত্ব।
★ Cohesion
ক্লাসের method গুলো যত বেশি instance variable ব্যবহার করে, ক্লাস তত cohesive। Cohesion কমলে ক্লাস ভাঙার সময় হয়েছে।
★ Open-Closed Principle (OCP)
ক্লাস extension-এর জন্য open থাকবে, কিন্তু modification-এর জন্য closed থাকবে।
★ Dependency Inversion Principle (DIP)
Concrete detail-এর ওপর নয়, abstraction-এর ওপর নির্ভর করো। এতে coupling কমে এবং testing সহজ হয়।
★ Encapsulation
ক্লাসের ভেতরের detail লুকিয়ে রাখো। Privacy শিথিল করা সবসময় শেষ উপায়।
