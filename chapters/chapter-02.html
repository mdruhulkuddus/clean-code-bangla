অর্থবহ নাম
Meaningful Names
by Tim Ottinger

Software এ সর্বত্র নাম ব্যবহার হয় — variable, function, argument, class, package, source file, directory — সবকিছুর নাম দিতে হয়। যেহেতু আমরা এত বেশি নামকরণ করি, তাই সেটা ভালোভাবে করা উচিত। নিচে কিছু সহজ নিয়ম দেওয়া হলো ভালো নাম তৈরির জন্য।

উদ্দেশ্য প্রকাশকারী নাম Use Intention-Revealing Names

নাম দেখে বোঝা উচিত এটি কেন আছে, কী করে, এবং কীভাবে ব্যবহৃত হয়। ভালো নাম বেছে নিতে সময় লাগে, কিন্তু পরে অনেক বেশি সময় বাঁচায়। যদি নামের পাশে comment লাগে, তাহলে নামটি তার উদ্দেশ্য প্রকাশ করছে না।

✗ খারাপ:
int d; // elapsed time in days
✓ ভালো:
int elapsedTimeInDays;
int daysSinceCreation;
int daysSinceModification;
int fileAgeInDays;

"d" নামটা কিছুই বলে না — দিনও মনে হয় না, অতিবাহিত সময়ও মনে হয় না। কিন্তু "elapsedTimeInDays" পড়লেই বোঝা যায় এটা দিনের হিসেবে অতিবাহিত সময়।

একটি উদাহরণ দেখুন — এই code কী করে বুঝতে পারেন?

✗ অস্পষ্ট code:
public List<int[]> getThem() {
    List<int[]> list1 = new ArrayList<int[]>();
    for (int[] x : theList)
        if (x[0] == 4)
            list1.add(x);
    return list1;
}

Code টি সহজ — কোনো জটিল expression নেই, indentation যুক্তিসঙ্গত, মাত্র তিনটি variable। কিন্তু কী হচ্ছে বুঝতে পারা যায় না! theList কী? x[0] == 4 মানে কী? return করা list কীভাবে ব্যবহার হবে?

ধরুন এটা minesweeper game এর code — theList হলো gameBoard, প্রতিটি cell একটি array, zeroth subscript হলো status, এবং 4 মানে "flagged"। এখন ভালো নাম দিলে:

✓ অর্থবহ নামসহ:
public List<int[]> getFlaggedCells() {
    List<int[]> flaggedCells = new ArrayList<int[]>();
    for (int[] cell : gameBoard)
        if (cell[STATUS_VALUE] == FLAGGED)
            flaggedCells.add(cell);
    return flaggedCells;
}

Code এর complexity একই আছে — একই সংখ্যক operator, constant, nesting level। কিন্তু এখন পড়লেই বোঝা যাচ্ছে কী হচ্ছে। আরো ভালো করতে পারি — Cell class তৈরি করে isFlagged() method দিয়ে:

✓ আরো ভালো — Cell class ব্যবহার করে:
public List<Cell> getFlaggedCells() {
    List<Cell> flaggedCells = new ArrayList<Cell>();
    for (Cell cell : gameBoard)
        if (cell.isFlagged())
            flaggedCells.add(cell);
    return flaggedCells;
}

ভালো নাম বেছে নেওয়ার শক্তি এটাই!

ভুল তথ্য এড়াও Avoid Disinformation

Programmer দের এমন নাম দেওয়া উচিত নয় যা ভুল ইঙ্গিত দেয়। কিছু উদাহরণ:

hp, aix, sco — এগুলো Unix platform এর নাম, তাই variable নাম হিসেবে ভুল ইঙ্গিত দেয়। hypotenuse এর জন্য hp ভালো abbreviation মনে হলেও, programmer দের কাছে এটা ভিন্ন অর্থ বহন করে।
accountList — যদি container টি আসলে List না হয়, তাহলে এই নাম ভুল ইঙ্গিত দেয় (List শব্দটি programmer দের কাছে নির্দিষ্ট অর্থ রাখে)। accounts বা accountGroup ভালো হবে।
খুব কাছাকাছি নাম — XYZControllerForEfficientHandlingOfStrings বনাম XYZControllerForEfficientStorageOfStrings — এদের পার্থক্য দ্রুত ধরা কঠিন।
ছোট হাতের l (এল) বা বড় হাতের O — এগুলো সংখ্যা 1 এবং 0 এর মতো দেখতে, তাই variable নাম হিসেবে ভয়ানক!

অর্থপূর্ণ পার্থক্য Make Meaningful Distinctions

Compiler satisfy করতে গিয়ে অর্থহীন নাম দেওয়া উচিত নয়।

Number-series naming (a1, a2, …) কোনো তথ্য দেয় না:

✗ a1, a2 — অর্থহীন:
public static void copyChars(char a1[], char a2[]) {
    for (int i = 0; i < a1.length; i++) {
        a2[i] = a1[i];
    }
}

a1 এবং a2 এর বদলে source এবং destination লিখলে অনেক ভালো হতো।

Noise words (Info, Data, a, an, the) অর্থহীন পার্থক্য তৈরি করে। Product, ProductInfo, ProductData — এদের মধ্যে কী পার্থক্য? Customer আর CustomerObject — কোনটা ব্যবহার করবো? variable নামে variable শব্দটা, table নামে table শব্দটা — সব redundant।

✗ কোনটা কোন কাজে?
getActiveAccount();
getActiveAccounts();
getActiveAccountInfo();

এই তিনটি function এর মধ্যে কোনটা ব্যবহার করতে হবে — programmer কীভাবে বুঝবে? নাম এমন হওয়া উচিত যে পাঠক বুঝতে পারেন পার্থক্যটা কোথায়।

উচ্চারণযোগ্য নাম Use Pronounceable Names

আমাদের মস্তিষ্কের একটি বিশাল অংশ শব্দ নিয়ে কাজ করে। নাম উচ্চারণ করতে না পারলে আলোচনা করা কঠিন হয়। "ওই bee cee arr three cee enn tee তে একটা pee ess zee kyew int আছে, দেখো!" — এভাবে কথা বলা হাস্যকর। Programming হলো social activity।

✗ উচ্চারণ অযোগ্য:
class DtaRcrd102 {
  private Date genymdhms;
  private Date modymdhms;
  private final String pszqint
      = "102";
}
✓ উচ্চারণযোগ্য:
class Customer {
  private Date
      generationTimestamp;
  private Date
      modificationTimestamp;
  private final String
      recordId = "102";
}

এখন সহকর্মীকে বলতে পারেন: "এই record এর generation timestamp আগামীকালের date দেখাচ্ছে — এটা কীভাবে হলো?" বুদ্ধিদীপ্ত আলোচনা এখন সম্ভব!

খুঁজে পাওয়া যায় এমন নাম Use Searchable Names

একটি অক্ষরের নাম বা numeric constant খুঁজে বের করা কঠিন। MAX_CLASSES_PER_STUDENT সহজে grep করা যায়, কিন্তু 7 নম্বরটি অনেক জায়গায় থাকতে পারে। e নামের variable সর্বত্র পাওয়া যাবে কারণ e ইংরেজির সবচেয়ে সাধারণ অক্ষর।

নিয়ম:
নামের দৈর্ঘ্য তার scope এর আকারের সাথে সামঞ্জস্যপূর্ণ হওয়া উচিত। ছোট method এর local variable একটি অক্ষরের হতে পারে, কিন্তু একাধিক জায়গায় ব্যবহৃত variable বা constant এর নাম search-friendly হতে হবে।
✗ অ-searchable:
for (int j=0; j<34; j++) {
    s += (t[j]*4)/5;
}
✓ Searchable:
int realDaysPerIdealDay = 4;
const int WORK_DAYS_PER_WEEK
    = 5;
int sum = 0;
for (int j=0;
    j < NUMBER_OF_TASKS;
    j++) {
  int realTaskDays =
    taskEstimate[j]
    * realDaysPerIdealDay;
  int realTaskWeeks =
    (realdays
    / WORK_DAYS_PER_WEEK);
  sum += realTaskWeeks;
}

WORK_DAYS_PER_WEEK খুঁজে বের করা কত সহজ! কিন্তু 5 খুঁজতে গেলে সব জায়গায় 5 এর ব্যবহার বাছাই করতে হবে।

Encoding এড়াও Avoid Encodings

Hungarian Notation (HN) মানে হলো variable নামের সাথে type এর সংকেত জুড়ে দেওয়া। আগে দরকার ছিল যখন compiler type check করতো না। আধুনিক ভাষায় (Java, C# ইত্যাদি) এর কোনো দরকার নেই — IDE এবং compiler type মনে রাখে এবং enforce করে। HN এখন code পড়তে কঠিন করে এবং নাম বা type পরিবর্তন করাও কঠিন হয়।

Member prefix (m_) — আগে member variable চেনাতে m_ prefix দেওয়া হতো। এখন class এবং function ছোট রাখলে এর দরকার নেই। আধুনিক IDE member variable আলাদা রঙে দেখায়।

✗ পুরোনো ধাঁচ — m_ prefix:
public class Part {
  private String m_dsc;
  // The textual description
  void setName(String name) {
      m_dsc = name;
  }
}
✓ আধুনিক ধাঁচ — পরিষ্কার নাম:
public class Part {
  String description;
  void setDescription(
      String description) {
    this.description
        = description;
  }
}

মানুষ দ্রুত prefix ignore করতে শিখে যায় এবং অর্থবহ অংশটুকুই দেখে। Prefix শেষ পর্যন্ত অদৃশ্য clutter হয়ে দাঁড়ায় — পুরোনো code র চিহ্ন।

Interface ও Implementation: IShapeFactory এর বদলে ShapeFactory ব্যবহার করুন। Interface এ I prefix না দিয়ে implementation এ suffix দিন — ShapeFactoryImp। ব্যবহারকারীর জানার দরকার নেই এটা interface।

Mental Mapping এড়াও Avoid Mental Mapping

পাঠকের মস্তিষ্কে নামকে আরেকটি ধারণায় রূপান্তর করতে হবে না। Single-letter variable (i, j, k ছাড়া loop counter হিসেবে) এড়াও। r variable দিয়ে "lower-cased URL with host and scheme removed" মনে রাখা চালাকি হতে পারে, কিন্তু professional নয়। Professional programmer জানে — clarity is king।

Class ও Method এর নামকরণ

Class এর নাম: noun বা noun phrase হবে — Customer, WikiPage, Account, AddressParser। Manager, Processor, Data, Info এসব এড়াও। Class এর নাম verb হবে না।

Method এর নাম: verb বা verb phrase হবে — postPayment, deletePage, save। Accessor, mutator, predicate যথাক্রমে get, set, is prefix ব্যবহার করবে (javabean standard অনুযায়ী)।

উদাহরণ:
string name = employee.getName();
customer.setName("mike");
if (paycheck.isPosted())...

// Overloaded constructor এর বদলে static factory method ভালো:
Complex fulcrumPoint = Complex.FromRealNumber(23.0); // ✓ ভালো
Complex fulcrumPoint = new Complex(23.0);             // কম স্পষ্ট

আরেকটি গুরুত্বপূর্ণ নিয়ম — Don't Be Cute

HolyHandGrenade() র বদলে DeleteItems() বলো। whack() র বদলে kill() বলো। eatMyShorts() র বদলে abort() বলো। স্পষ্টতা সবসময় entertainment value এর উপরে। যা বলতে চাও তাই বলো, যা বলো তাই বোঝাও।

Pick One Word per Concept (প্রতি ধারণার জন্য একটি শব্দ)

একই ধারণার জন্য fetch, retrieve, get — তিনটি আলাদা শব্দ ব্যবহার করবেন না। একটি বেছে নিন আর সর্বত্র ব্যবহার করুন। কোন method নাম কোন class এ ব্যবহৃত সেটা মনে রাখা কঠিন। একইভাবে controller, manager, driver — একটি consistent lexicon (শব্দভাণ্ডার) রাখুন।

Don't Pun (দ্ব্যর্থতা তৈরি করো না)

একই শব্দ দুটি ভিন্ন কাজে ব্যবহার করবেন না। যদি add মানে দুটি মান যোগ করা হয়, তাহলে collection এ item ঢোকানোকে add বলবেন না — insert বা append বলুন। আমাদের লক্ষ্য হলো code যেন দ্রুত skim করা যায়, গভীর study না লাগে।

Solution Domain vs Problem Domain Names

Code পড়বে programmer — তাই computer science term (AccountVisitor, JobQueue) ব্যবহার করতে দ্বিধা করবেন না। কিন্তু যখন programming term নেই, তখন problem domain র নাম ব্যবহার করুন — তখন maintenance programmer domain expert কে জিজ্ঞেস করতে পারবে।

Context যোগ করো Add Meaningful Context

firstName, lastName, street, city, state, zipcode — সাথে দেখলে বোঝা যায় address। কিন্তু শুধু state দেখলে? সমাধান — Address class তৈরি করুন। Prefix (addrState) ও চলে, কিন্তু class ভালো।

যথা Context যোগ করো না Don't Add Gratuitous Context

"Gas Station Deluxe" app র প্রতিটি class এ GSD prefix দেওয়ার দরকার নেই — IDE তে G টাইপ করলেই সব class র লম্বা list আসবে! ছোট নাম সাধারণত ভালো, যতটুকু পরিষ্কার।

★ মূল ধারণা সারসংক্ষেপ Key Concepts

★ Intention-Revealing Names
নাম দেখেই বোঝা যাবে এটা কেন আছে আর কী করে। Comment লাগলে নাম ভালো নয়।
★ Avoid Disinformation
ভুল ইঙ্গিত দেয় এমন নাম এড়াও। List না হলে accountList বলো না।
★ Meaningful Distinctions
নাম আলাদা হলে অর্থও আলাদা হতে হবে। a1/a2 বা Info/Data noise words।
★ Pronounceable Names
নাম উচ্চারণ করতে পারতে হবে — programming হলো social activity।
★ Searchable Names
Scope যত বড়, নাম তত search-friendly হতে হবে।
★ No Encodings
Hungarian Notation, m_ prefix, I prefix — আধুনিক IDE তে সব আর দরকার নেই।
★ One Word per Concept
একই ধারণার জন্য সর্বত্র একই শব্দ ব্যবহার করো। fetch/retrieve/get — একটি বেছে নাও।
★ Clarity over Cleverness
চালাক নাম নয়, স্পষ্ট নাম। Professional দের কাছে স্পষ্টতাই রাজা।
