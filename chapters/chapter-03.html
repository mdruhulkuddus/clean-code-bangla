অধ্যায় ৩
ফাংশন
Functions
by Robert C. Martin

Programming র শুরুর দিকে আমরা routine, subroutine ব্যবহার করতাম। তারপর program, subprogram, function। এখন শুধু function একটিই আছে। Function হলো যে কোনো program র প্রথম সংগঠন স্তর। এগুলো ভালোভাবে লেখা এই অধ্যায়ের বিষয়।

লেখক FitNesse (একটি open-source testing tool) থেকে একটি বড়, জটিল function দেখিয়ে শুরু করেছেন (Listing ৩-১)। সেটা এত বড় ও লোকমোকে যে ৩ মিনিটে বোঝা যায় না — duplicated code, অদ্ভুত string, নানা ধরনের data type ও API মেশানো, doubly nested if statement, flag দিয়ে নিয়ন্ত্রিত। তারপর দেখিয়েছেন কীভাবে method extraction, renaming, ও restructuring করে পরিষ্কার করা যায়:

✓ Refactored (পুনর্গঠিত) version:
public static String renderPageWithSetupsAndTeardowns(
    PageData pageData, boolean isSuite
) throws Exception {
    boolean isTestPage = pageData.hasAttribute("Test");
    if (isTestPage) {
        WikiPage testPage = pageData.getWikiPage();
        StringBuffer newPageContent = new StringBuffer();
        includeSetupPages(testPage, newPageContent, isSuite);
        newPageContent.append(pageData.getContent());
        includeTeardownPages(testPage, newPageContent, isSuite);
        pageData.setContent(newPageContent.toString());
    }
    return pageData.getHtml();
}

এটাকে আরো ছোট করা যায়:

✓ আরো ছোট version:
public static String renderPageWithSetupsAndTeardowns(
    PageData pageData, boolean isSuite) throws Exception {
    if (isTestPage(pageData))
        includeSetupAndTeardownPages(pageData, isSuite);
    return pageData.getHtml();
}

FitNesse না জানলেও বোঝা যায় — এই function কোনো test page এ setup ও teardown page include করে HTML render করে। এটাই clean function র শক্তি।

ছোট করো! Small!

Function র প্রথম নিয়ম — ছোট হতে হবে। দ্বিতীয় নিয়ম — তার চেয়ে ছোট হতে হবে।

লেখক ৪ দশক ধরে বিভিন্ন আকারের function লিখেছেন — ৩০০০ লাইনের বিশাল function থেকে ১০০-৩০০ লাইনের function, ২০-৩০ লাইনের function। অভিজ্ঞতা থেকে শিখেছেন function খুব ছোট হওয়া উচিত। ২০ লাইনই বেশি!

Kent Beck র একটি Java/Swing program (Sparkle নামে) এ প্রতিটি function ছিল মাত্র ২, ৩ বা ৪ লাইন। প্রতিটি স্পষ্টভাবে বোধগম্য। প্রতিটি একটি গল্প বলে। প্রতিটি পরেরটির দিকে নিয়ে যায়। এতো ছোট আপনার function হওয়া উচিত!

Block ও Indenting

if, else, while ইত্যাদির block ১ লাইনের হওয়া উচিত — সেই লাইনটি হবে একটি function call যার নাম descriptive। এতে enclosing function ছোট থাকে আর documentary value যোগ হয়। Function র indent level ১ বা ২ র বেশি হওয়া উচিত নয় — এতে পড়তে ও বুঝতে সহজ হয়।

একটি কাজ করো Do One Thing

মূল নীতি

FUNCTIONS SHOULD DO ONE THING. THEY SHOULD DO IT WELL. THEY SHOULD DO IT ONLY.

এই পরামর্শটি ৩০ বছরের বেশি পুরোনো। কিন্তু "one thing" কী — সেটা বোঝা কঠিন। Listing ৩-৩ কি একটি কাজ করে? তিনটি কাজ বলা যায় — page test কিনা দেখো, setup/teardown include করো, HTML render করো।

পরীক্ষা:
function কে একটি সংক্ষিপ্ত TO paragraph হিসেবে বর্ণনা করুন:

"TO RenderPageWithSetupsAndTeardowns, আমরা দেখি page একটি test page কিনা, যদি হয় তাহলে setup ও teardown যোগ করি, ও page একটি HTML এ render করি।"

যদি function শুধু সেই কাজগুলোই করে যা তার নামের স্তরে — তাহলে সে একটি কাজ করছে। কারণ function লেখার মূল কারণই হলো একটি বৃহত্তর ধারণাকে পরবর্তী abstraction level র কিছু ধাপে ভাগ করা।

আরেকটি পরীক্ষা: function থেকে যদি আরেকটি function বের করা যায় যার নাম implementation র পুনরুক্তি নয় (শুধু restatement নয়), তাহলে আসল function একাধিক কাজ করছে।

প্রতি Function একটি Abstraction Level

Function র ভেতরে সব statement একই abstraction level এ হওয়া উচিত। যেমন:

  • • getHtml() — উচ্চ abstraction
  • • String pagePathName = PathParser.render(pagePath) — মধ্যম abstraction
  • • .append("\n") — নিম্ন abstraction

এগুলো একই function এ মিশিয়ে ফেললে পাঠক বুঝতে পারে না কোনটা মূল ধারণা আর কোনটা খুঁটিনাটি বিবরণ। আরো খারাপ — Broken Window র মতো, একবার বিস্তারিত মিশতে শুরু করলে আরো বিস্তারিত জমতে থাকে।

The Stepdown Rule

Code ওপর থেকে নিচে গল্পের মতো পড়া যাওয়া উচিত। প্রতিটি function এর পরে তার পরবর্তী abstraction level র function থাকবে। এটাকে TO paragraph এর মতো ভাবুন:

Setup ও teardown include করতে, আমরা setup include করি, তারপর test page content, তারপর teardown include করি।

Setup include করতে, suite setup include করি (যদি suite হয়), তারপর regular setup।

Suite setup include করতে, parent hierarchy তে "SuiteSetUp" page খুঁজি এবং সেই page এর path সহ include statement যোগ করি।

এই নিয়ম শেখা কঠিন কিন্তু অত্যন্ত গুরুত্বপূর্ণ — এটাই function ছোট রাখার এবং "one thing" করানোর চাবিকাঠি।

Switch Statement সমস্যা Switch Statement

Switch statement ছোট রাখা কঠিন — এগুলো স্বভাবতই N টি কাজ করে। আমরা switch statement পুরোপুরি এড়াতে পারি না, কিন্তু নিশ্চিত করতে পারি যে প্রতিটি switch একটি low-level class এ লুকানো থাকে এবং কখনো পুনরাবৃত্তি হয় না। সমাধান — polymorphism (বহুরূপিতা)।

✗ Switch statement এর সমস্যা:
public Money calculatePay(Employee e) throws InvalidEmployeeType {
    switch (e.type) {
        case COMMISSIONED: return calculateCommissionedPay(e);
        case HOURLY:       return calculateHourlyPay(e);
        case SALARIED:     return calculateSalariedPay(e);
        default: throw new InvalidEmployeeType(e.type);
    }
}

এই function এর সমস্যাগুলো:

  • ১। বড় — নতুন employee type যোগ করলে আরো বড় হবে
  • ২। একাধিক কাজ করে
  • ৩। Single Responsibility Principle (SRP) ভঙ্গ করে — পরিবর্তনের একাধিক কারণ আছে
  • ৪। Open Closed Principle (OCP) ভঙ্গ করে — নতুন type যোগ করলে পরিবর্তন করতে হবে
  • ৫। একই structure এর আরো function থাকবে (isPayday, deliverPay)
✓ সমাধান — Abstract Factory + Polymorphism:
public abstract class Employee {
    public abstract boolean isPayday();
    public abstract Money calculatePay();
    public abstract void deliverPay(Money pay);
}
-----------------
public interface EmployeeFactory {
    public Employee makeEmployee(EmployeeRecord r)
        throws InvalidEmployeeType;
}
-----------------
public class EmployeeFactoryImpl implements EmployeeFactory {
    public Employee makeEmployee(EmployeeRecord r)
        throws InvalidEmployeeType {
        switch (r.type) {
            case COMMISSIONED: return new CommissionedEmployee(r);
            case HOURLY:       return new HourlyEmployee(r);
            case SALARIED:     return new SalariedEmploye(r);
            default: throw new InvalidEmployeeType(r.type);
        }
    }
}

Switch statement এখন factory র ভেতরে লুকানো। calculatePay, isPayday, deliverPay — সব polymorphically dispatch হবে Employee interface দিয়ে। বাকি system কে switch দেখতে হবে না।

বর্ণনামূলক নাম Use Descriptive Names

testableHtml এর বদলে SetupTeardownIncluder.render — এটি অনেক ভালো নাম কারণ এটি function কী করে তা বলে। Function যত ছোট এবং focused হবে, descriptive নাম বেছে নেওয়া তত সহজ।

লম্বা descriptive নাম > ছোট রহস্যময় নাম। লম্বা descriptive নাম > লম্বা descriptive comment।

নাম বেছে নিতে সময় দিন। IDE তে rename সহজ — বিভিন্ন নাম চেষ্টা করুন। Consistent naming রাখুন — includeSetupAndTeardownPages, includeSetupPages, includeSuiteSetupPage — এই phraseology একটি গল্প বলে।

Function Argument Function Argument

Function argument এর আদর্শ সংখ্যা:

সংখ্যানামমূল্যায়ন
শূন্য (niladic)কোনো argument নেইসবচেয়ে ভালো
এক (monadic)একটি argumentভালো
দুই (dyadic)দুটি argumentগ্রহণযোগ্য
তিন (triadic)তিনটি argumentএড়ানো উচিত
তিনের বেশি (polyadic)বহু argumentবিশেষ কারণ ছাড়া কখনো নয়

Argument বুঝতে কষ্ট হয় — তারা function নামের চেয়ে ভিন্ন abstraction level এ থাকে। Test করতেও কষ্ট হয় — সব combination cover করতে হয়। Output argument input argument এর চেয়ে বুঝতে কঠিন।

Common Monadic Forms (একটি argument এর সাধারণ রূপ)

একটি argument পাঠানোর সাধারণ কারণ: প্রশ্ন করা (boolean fileExists("MyFile")), রূপান্তর করা (InputStream fileOpen("MyFile")), অথবা event (void passwordAttemptFailedNtimes(int attempts))। এই তিন form এ ভিন্ন কিছু এড়ানো উচিত।

Flag Argument — কুৎসিত!

Boolean parameter function এ পাঠানো সত্যিই খারাপ অভ্যাস। এটা চিৎকার করে বলে function একাধিক কাজ করে — true হলে এক কাজ, false হলে আরেক। render(true) পড়লে কিছু বোঝা যায় না। সমাধান:

render(true) → renderForSuite() এবং renderForSingleTest() — দুটি আলাদা function

Dyadic ও Triad Function

দুই argument এর function বুঝতে একটু কষ্ট হয়। writeField(name) সহজে বোঝা যায়, কিন্তু writeField(outputStream, name) এ পাঠক প্রথম parameter ignore করতে শেখে — আর ignore করা মানে bug লুকানোর জায়গা তৈরি।

Point(0, 0) ঠিক আছে — coordinate এর দুটি component থাকাটাই স্বাভাবিক। কিন্তু assertEquals(expected, actual) সমস্যাযুক্ত — কতবার expected আর actual এর জায়গা গুলিয়েছেন?

তিনটি argument এর সমস্যা দ্বিগুণেরও বেশি। assertEquals(message, expected, actual) — কতবার message কে expected মনে করেছেন?

Argument Object — সমাধান

যখন function এ দুই-তিনের বেশি argument লাগে, সম্ভবত কিছু argument একটি class এ wrap করা উচিত:

✗ তিনটি argument:
Circle makeCircle(
    double x, double y,
    double radius);
✓ Argument Object:
Circle makeCircle(
    Point center,
    double radius);

x ও y একসাথে যায় — তাদের একটি ধারণা হিসেবে নাম দেওয়া (Point) cheating নয়, বরং উচিত।

Side Effect থেকে সাবধান Have No Side Effects

Side effect মানে হলো মিথ্যা বলা। আপনার function প্রতিশ্রুতি দেয় একটি কাজ করবে, কিন্তু সে চুপিসারে আরো কিছু করে — নিজের class এর variable বদলায়, parameter বদলায়, বা global state বদলায়। এটি temporal coupling (সময়গত সংযোগ) এবং order dependency তৈরি করে।

✗ Side effect খুঁজুন:
public class UserValidator {
    private Cryptographer cryptographer;

    public boolean checkPassword(String userName, String password) {
        User user = UserGateway.findByName(userName);
        if (user != User.NULL) {
            String codedPhrase = user.getPhraseEncodedByPassword();
            String phrase = cryptographer.decrypt(codedPhrase, password);
            if ("Valid Password".equals(phrase)) {
                Session.initialize();  // ← এটাই side effect!
                return true;
            }
        }
        return false;
    }
}

checkPassword নাম বলছে সে password check করবে। কিন্তু সে লুকিয়ে Session.initialize() করছে! ভুল সময়ে এই function ডাকলে session data হারিয়ে যেতে পারে। নাম হওয়া উচিত checkPasswordAndInitializeSession — যদিও সেটা "Do one thing" ভঙ্গ করে।

Output Argument

appendFooter(s) — এটা কি s কে footer হিসেবে append করে, নাকি s এ footer append করে? Function signature না দেখে বোঝা যায় না — এটা cognitive break তৈরি করে। OO তে সমাধান সহজ: report.appendFooter() — this কেই output argument হিসেবে ব্যবহার করুন।

Command Query Separation Command Query Separation

Function হয় কিছু করবে (command — object এর state পরিবর্তন), অথবা কিছু জানাবে (query — object সম্পর্কে তথ্য return) — দুটো একসাথে নয়।

✗ Command ও Query একসাথে:
public boolean set(String attribute, String value);
// ব্যবহার করলে বিভ্রান্তি:
if (set("username", "unclebob"))...
// set কি verb (সেট করো) নাকি adjective (সেট করা আছে)?
✓ আলাদা করো:
if (attributeExists("username")) {
    setAttribute("username", "unclebob");
}

Error Code এর বদলে Exception Prefer Exceptions to Returning Error Codes

Error code return করলে caller কে তাৎক্ষণিকভাবে error handle করতে হয়, ফলে deeply nested structure তৈরি হয়। Exception ব্যবহার করলে happy path আলাদা থাকে:

✗ Error code — deeply nested:
if (deletePage(page) == E_OK) {
 if (registry.deleteReference(
     page.name) == E_OK) {
  if (configKeys.deleteKey(
      page.name.makeKey())
      == E_OK) {
   logger.log("page deleted");
  } else {
   logger.log("configKey err");
  }
 } else {
  logger.log("ref failed");
 }
} else {
 logger.log("delete failed");
 return E_ERROR;
}
✓ Exception — পরিষ্কার:
try {
    deletePage(page);
    registry.deleteReference(
        page.name);
    configKeys.deleteKey(
        page.name.makeKey());
} catch (Exception e) {
    logger.log(
        e.getMessage());
}

Try/Catch Block আলাদা করো

Try/catch block কুৎসিত — normal processing এবং error processing মিশিয়ে ফেলে। তাই try এবং catch এর body আলাদা function এ রাখা উচিত:

✓ পরিষ্কার separation:
public void delete(Page page) {
    try {
        deletePageAndAllReferences(page);
    } catch (Exception e) {
        logError(e);
    }
}

private void deletePageAndAllReferences(Page page) throws Exception {
    deletePage(page);
    registry.deleteReference(page.name);
    configKeys.deleteKey(page.name.makeKey());
}

private void logError(Exception e) {
    logger.log(e.getMessage());
}

delete function শুধু error processing করে — সহজে বোঝা যায়। deletePageAndAllReferences function শুধু page মুছে ফেলার কাজ করে — error handling ignore করা যায়। সুন্দর separation!

Error Handling Is One Thing

Error handling নিজেই "one thing" — তাই error handling function এ try keyword প্রথম শব্দ হওয়া উচিত আর catch/finally block র পরে আর কিছু থাকা উচিত নয়।

Error.java Dependency Magnet

Error code সাধারণত একটি enum এ সংজ্ঞায়িত থাকে। এই class একটি dependency magnet — যথেষ্ট class একে import করে। Error enum পরিবর্তন হলে সব class recompile ও redeploy করতে হয়। তাই programmer রা নতুন error code যোগ না করে পুরোনোগুলো reuse করে — খারাপ! Exception ব্যবহার করলে নতুন exception class যোগ করা যায় recompile ছাড়াই (Open Closed Principle)।

নিজেকে পুনরাবৃত্তি করো না Don't Repeat Yourself — DRY

Duplication (পুনরাবৃত্তি) হলো software র সব মন্দের মূল। Listing ৩-১ এ একটি algorithm চারবার পুনরাবৃত্তি হয়েছে — SetUp, SuiteSetUp, TearDown, SuiteTearDown র জন্য। কেউ code ভুলে তোলে, algorithm পরিবর্তন করতে চারবার করতে হয়, ভুলের চার গুণ সম্ভাবনা।

Database normal form, object-oriented programming, structured programming, Aspect Oriented Programming, Component Oriented Programming — সবকিছুই duplication কমানোর কৌশল। Subroutine আবিষ্কারের পর থেকে software development র সব নতুন উদ্ভাবন source code থেকে duplication দূর করার প্রচেষ্টা।

Function কীভাবে লিখবেন? How Do You Write Functions Like This?

Software লেখা যে কোনো লেখার মতো। প্রথম draft হয় বড়, জটিল — যথেষ্ট indenting, nested loop, লম্বা argument list, যেমনতেমন নাম, duplicated code। কিন্তু সাথে সাথে সেই code র unit test ও থাকে যা প্রতিটি line cover করে।

তারপর সেই code কে massage করা হয় — function ভাঙা হয়, নাম পরিবর্তন হয়, duplication দূর হয়, method ছোট হয়, পুনর্বিন্যাস হয়। কখনো পুরো class আলাদা করা হয় — সবসময় test pass রেখে।

মনে রাখুন

কেউ প্রথমবারেই clean function লেখে না। আমিও মনে করি নিজে পারি না।

উপসংহার Conclusion

প্রতিটি system একটি domain-specific language দিয়ে তৈরি যা programmer রা সেই system বর্ণনা করতে ব্যবহার করেন। Function হলো সেই ভাষার verb (ক্রিয়াপদ), class হলো noun (বিশেষ্য)।

Master programmer রা system কে program হিসেবে না, বরং গল্প হিসেবে ভাবেন। তারা তাদের chosen programming language ব্যবহার করে যথেষ্ট সমৃদ্ধ ও expressive ভাষা তৈরি করেন যা সেই গল্প বলতে পারে।

এই অধ্যায়ের নিয়মগুলো মানলে আপনার function গুলো ছোট, সুন্দর নামের, ও সুন্দরভাবে সাজানো হবে। কিন্তু কখনো ভুলবেন না — আসল লক্ষ্য হলো system র গল্প বলা, আর আপনার লেখা function গুলো যেন একটি পরিষ্কার ও সুনির্দিষ্ট ভাষায় সুন্দরভাবে মিলেমিশে সেই গল্প বলতে সাহায্য করে।

★ মূল ধারণা সারসংক্ষেপ Key Concepts

★ Small Functions
Function ছোট রাখো — ২০ লাইনই বেশি! ২-৪ লাইনই আদর্শ।
★ Do One Thing
প্রতিটি function একটিমাত্র কাজ করবে, সেটা ভালোভাবে করবে, শুধু সেটাই করবে।
★ One Abstraction Level
Function র ভেতরে সব statement একই abstraction level এ থাকবে।
★ Stepdown Rule
Code ওপর থেকে নিচে গল্পের মতো পড়া যাবে — প্রতিটি function পরবর্তী abstraction level এ নিয়ে যায়।
★ Switch → Polymorphism
Switch statement Abstract Factory তে লুকিয়ে polymorphism ব্যবহার করো।
★ Few Arguments
Argument যত কম তত ভালো। ০ সেরা, ১ ভালো, ২ গ্রহণযোগ্য, ৩+ এড়াও।
★ No Flag Arguments
Boolean parameter ব্যবহার করো না — function কে দুটি আলাদা function এ ভাগ করো।
★ No Side Effects
Function যা বলে শুধু তাই করবে — লুকিয়ে অন্য কিছু নয়। Side effect মানে মিথ্যা বলা।
★ Command-Query Separation
Function হয় কিছু করবে, নাহয় কিছু জানাবে — দুটো সাথে নয়।
★ Exception > Error Code
Error code র বদলে exception ব্যবহার করো — happy path পরিষ্কার থাকে।
★ DRY (Don't Repeat Yourself)
Duplication হলো software র সব মন্দের মূল। একই কাজ দুইবার লেখো না।
★ Writing Clean Functions is Iterative
কেউ প্রথমবারেই clean function লেখে না। প্রথমে কাজ করো, তারপর refactor করো — test pass রেখে।
