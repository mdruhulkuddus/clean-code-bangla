Boundaries
by James Grenning

আমরা যে সফটওয়্যার তৈরি করি, তার পুরোটা আমরা নিজেরা নিয়ন্ত্রণ করি না। কখনো third-party package কিনি, কখনো open source ব্যবহার করি, কখনো নিজের কোম্পানির অন্য টিমের তৈরি component ব্যবহার করি। এই "বাইরের" কোডকে নিজের কোডের সাথে পরিষ্কারভাবে সংযুক্ত করাটাই boundary management।

Third-Party Code ব্যবহারের সমস্যা Using Third-Party Code

Interface provider (যে লাইব্রেরি তৈরি করে) চায় তার interface যতটা সম্ভব broad (বিস্তৃত) হোক — যেন অনেক ধরনের user ব্যবহার করতে পারে। অন্যদিকে, user চায় তার নির্দিষ্ট প্রয়োজনে focused interface। এই টানাপোড়েন boundary-তে সমস্যা তৈরি করে।

উদাহরণ হিসেবে Java-র Map দেখো। Map-এর অনেক method আছে — clear(), put(), remove() ইত্যাদি। তুমি হয়তো চাও কেউ যেন Map থেকে কিছু delete না করতে পারে, কিন্তু clear() method সবার কাছে উন্মুক্ত!

যদি তোমার application-এ Sensor-এর একটা Map দরকার হয়, তুমি হয়তো এভাবে লিখবে:

✗ খারাপ 
Map sensors = new HashMap();

// অন্য জায়গায় ব্যবহার:
Sensor s = (Sensor)sensors.get(sensorId);

Generics ব্যবহার করলে একটু ভালো হয় (Map<Sensor>), কিন্তু মূল সমস্যা থেকে যায় — Map-এর পুরো interface সবার কাছে exposed। একটা ভালো সমাধান হলো Map-কে একটা class-এ wrap করা:

✓ ভালো 
public class Sensors {
    private Map sensors = new HashMap();

    public Sensor getById(String id) {
        return (Sensor) sensors.get(id);
    }
    //snip
}

এই approach এর সুবিধা হলো: boundary interface (Map) লুকানো আছে। Map এর API পরিবর্তন হলে শুধু Sensors class পরিবর্তন করতে হবে, বাকি application-এ কোনো প্রভাব পড়বে না। এই interface tailored এবং constrained — প্রয়োজনের বাইরে কিছু করার সুযোগ নেই। ফলে কোড বোঝা সহজ এবং ভুল করা কঠিন।

গুরুত্বপূর্ণ পরামর্শ

প্রতিটা Map ব্যবহার এভাবে wrap করতে হবে এমন নয়। কিন্তু Map বা অন্য boundary interface পুরো system-এ pass করো না। এটাকে ব্যবহারকারী class বা তার কাছের class গুলোর মধ্যে সীমাবদ্ধ রাখো। Public API থেকে return বা argument হিসেবে boundary interface পাঠানো এড়িয়ে চলো।

Boundary খোঁজা ও অনুসন্ধান Exploring and Learning Boundaries

নতুন third-party library ব্যবহার করতে গেলে documentation পড়ি, কোড লিখি, debug করি — এটা সময়সাপেক্ষ। Third-party code শেখাও কঠিন, integrate করাও কঠিন — দুটো একসাথে করা দ্বিগুণ কঠিন।

একটা ভালো পদ্ধতি হলো Learning Tests লেখা। Production code-এ সরাসরি পরীক্ষা না করে, ছোট ছোট test লেখো যেগুলো third-party API কে তুমি যেভাবে ব্যবহার করতে চাও সেভাবে call করে।

Learning log4j — একটা উদাহরণ Learning log4j

ধরো, তুমি Apache log4j ব্যবহার করতে চাও। প্রথমে একটা সহজ test লেখো:

@Test
public void testLogCreate() {
    Logger logger = Logger.getLogger("MyLogger");
    logger.info("hello");
}

রান করলে error আসবে — Appender দরকার। আরেকটু পড়ে ConsoleAppender যোগ করো:

@Test
public void testLogAddAppender() {
    Logger logger = Logger.getLogger("MyLogger");
    ConsoleAppender appender = new ConsoleAppender();
    logger.addAppender(appender);
    logger.info("hello");
}

আবার সমস্যা — Appender-এর output stream নেই! আরও ঘাঁটাঘাঁটি করে শেষমেশ কাজ করলো:

@Test
public void testLogAddAppender() {
    Logger logger = Logger.getLogger("MyLogger");
    logger.removeAllAppenders();
    logger.addAppender(new ConsoleAppender(
        new PatternLayout("%p %t %m%n"),
        ConsoleAppender.SYSTEM_OUT));
    logger.info("hello");
}

এভাবে পরীক্ষা-নিরীক্ষা করে একটা সম্পূর্ণ test suite তৈরি হয়:

Listing 8-1: LogTest.java
public class LogTest {
    private Logger logger;

    @Before
    public void initialize() {
        logger = Logger.getLogger("logger");
        logger.removeAllAppenders();
        Logger.getRootLogger().removeAllAppenders();
    }

    @Test
    public void basicLogger() {
        BasicConfigurator.configure();
        logger.info("basicLogger");
    }

    @Test
    public void addAppenderWithStream() {
        logger.addAppender(new ConsoleAppender(
            new PatternLayout("%p %t %m%n"),
            ConsoleAppender.SYSTEM_OUT));
        logger.info("addAppenderWithStream");
    }

    @Test
    public void addAppenderWithoutStream() {
        logger.addAppender(new ConsoleAppender(
            new PatternLayout("%p %t %m%n")));
        logger.info("addAppenderWithoutStream");
    }
}

এখন আমরা জানি console logger কীভাবে initialize করতে হয়। এই জ্ঞান নিজের logger class-এ encapsulate করে বাকি application-কে log4j-র boundary থেকে insulate (আলাদা) করা যায়।

Learning Tests বিনামূল্যের চেয়েও ভালো Learning Tests Are Better Than Free

Learning tests-এর কোনো অতিরিক্ত খরচ নেই — API তো শিখতেই হতো। এবং এদের একটা বড় সুবিধা আছে: third-party package-এর নতুন version এলে এই test গুলো রান করলেই বোঝা যায় কোনো behavioral difference আছে কিনা।

এই test গুলো verify করে যে third-party package আমাদের প্রত্যাশা অনুযায়ী কাজ করছে। Boundary tests ছাড়া পুরোনো version-এ আটকে থাকার প্রবণতা তৈরি হয়।

এখনো তৈরি হয়নি এমন Code ব্যবহার করো Using Code That Does Not Yet Exist

আরেক ধরনের boundary আছে — জানা ও অজানার মধ্যকার সীমানা। কখনো কখনো boundary-র অপর পাশে কী আছে সেটা এখনো জানা যায়নি।

লেখক একটা radio communication system-এর উদাহরণ দেন। তাদের একটা "Transmitter" subsystem দরকার ছিল, কিন্তু সেটার API এখনো তৈরি হয়নি। তারা আটকে না থেকে নিজেদের interface তৈরি করে ফেললো:

তারা চেয়েছিলেন transmitter-কে বলতে: "এই frequency-তে transmitter চালু করো এবং এই data stream থেকে analog representation পাঠাও।" তাই নিজেদের Transmitter interface তৈরি করলেন যার transmit method frequency আর data stream নেয়।

Adapter Pattern

যখন প্রকৃত API তৈরি হলো, তখন একটা TransmitterAdapter লেখা হলো যেটা নিজেদের interface আর আসল API-র মধ্যে সেতু হিসেবে কাজ করে। API পরিবর্তন হলে শুধু Adapter পরিবর্তন করলেই হবে। এটা testing-এও সুবিধা দেয় — FakeTransmitter দিয়ে সহজেই test করা যায়।

পরিষ্কার Boundary Clean Boundaries

Boundary-তে মজার ব্যাপার ঘটে — পরিবর্তন হয়। ভালো software design এমনভাবে করা হয় যাতে পরিবর্তনের জন্য বিশাল বিনিয়োগ ও rework না লাগে।

Boundary code-এ পরিষ্কার separation ও expectation-defining test দরকার। তোমার নিজের নিয়ন্ত্রণে আছে এমন কিছুর উপর নির্ভর করা ভালো, যেটার উপর নিয়ন্ত্রণ নেই তার উপর নয়।

Third-party boundary manage করতে: কোডে যত কম জায়গায় third-party reference থাকে তত ভালো। Map-এর মতো wrap করতে পারো, অথবা Adapter ব্যবহার করতে পারো। যেভাবেই হোক — তোমার কোড তোমার ভাষায় কথা বলবে, boundary জুড়ে consistent ব্যবহার নিশ্চিত হবে, আর third-party code পরিবর্তন হলে maintenance point কম থাকবে।

★ মূল ধারণা সারসংক্ষেপ Key Concepts

★ Third-party code সরাসরি ছড়িয়ে দিও না
Boundary interface (যেমন Map) সরাসরি পুরো system-এ পাস করো না, wrap করো।
★ Learning Tests লেখো
তৃতীয়-পক্ষের library শেখার জন্য ছোট ছোট test লেখো। এটা বিনামূল্যে শেখার একটা উপায়, আর নতুন version এলে behavioral difference ধরতে সাহায্য করে।
★ Adapter Pattern ব্যবহার করো
এখনো তৈরি হয়নি এমন API-র জন্য নিজের interface define করো, পরে Adapter দিয়ে সংযোগ করো।
★ Boundary তে পরিবর্তন হয়
তাই boundary code পরিষ্কারভাবে আলাদা রাখো এবং test দিয়ে protect করো।
★ Boundary Interface Wrap করো
Map-এর মতো broad interface-কে নিজের class-এ wrap করো যাতে implementation details লুকানো থাকে এবং API পরিবর্তনের প্রভাব সীমিত থাকে।
★ নিজের নিয়ন্ত্রণে থাকো
তোমার কোড তোমার ভাষায় কথা বলবে। Third-party reference যত কম জায়গায় থাকবে, maintenance তত সহজ হবে।
